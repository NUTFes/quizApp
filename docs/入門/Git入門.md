# Git入門 — 共同開発の道具としてのGit

このドキュメントは **Gitを触ったことがない人** 向け。「Gitとは何か」「なぜ必要か」「最低限どのコマンドを覚えればよいか」だけを扱う。

うちのチームでの**具体的な進め方**(Issueを取る → ブランチを切る → PRを出す)は [`開発フローガイド.md`](../ガイドライン/開発フローガイド.md) にある。**このファイルを読んでから、そちらへ進む。**

---

## 1. なぜGitが要るのか

複数人で1つのアプリを作るときに起きる問題を考えてみる。

**問題1: 上書き事故**
AさんとBさんが同じファイルを編集して、順番に共有フォルダへ置いたら、後から置いた人の変更で先の人の変更が消える。

**問題2: 壊したときに戻せない**
「昨日までは動いていたのに、今日いじったら動かなくなった。どこをいじったか覚えていない。」

**問題3: 誰がいつ何を変えたか分からない**
「この行、なんでこう書いてあるんだろう?」が誰にも答えられなくなる。

Gitはこの3つをまとめて解決する道具。やっていることは一言でいうと、

> **ファイルの変更履歴を、全部・順番に・理由付きで記録する**

これだけ。記録があるから、消えた変更を復元でき、昨日の状態に戻せて、誰がなぜ変えたかを追える。

## 2. 一番大事な考え方 — 「手元」と「GitHub」は別の世界

初心者が最初に混乱するのはここなので、先に押さえる。

Gitでは、**同じリポジトリ(プロジェクトの入れ物)のコピーが2箇所にある**。

```
  【手元(ローカル)】                    【GitHub(リモート)】
  自分のPCの中                            インターネット上の共有場所
  自分だけが見える                        チーム全員が見える
  ここで編集・記録する      ── push ──▶   ここに送って共有する
                            ◀── pull ──   みんなの変更をもらってくる
```

**重要な性質: 手元で作業しても、GitHubには何も起きない。**
記録(コミット)を作っただけでは、それは自分のPCの中にあるだけ。**`push` して初めてチームに見える。**

逆に、他の人がGitHubに変更を送っても、自分の手元は自動では新しくならない。**`pull` して初めて自分の手元に届く。**

「作業したのに他の人から見えない」「他の人の変更が自分の手元に無い」の9割はこれが原因。

## 3. 用語 — 最低限の6つ

| 用語 | 意味 | 例えると |
|---|---|---|
| **リポジトリ** | プロジェクト1個分の入れ物(履歴を含む) | 作品のフォルダ+全記録 |
| **コミット** | 変更の記録1個。「何を変えたか」+「なぜ変えたか(メッセージ)」 | セーブポイント |
| **ブランチ** | 履歴の枝分かれ。他の人の作業と分離した作業場所 | 作業用のコピー本 |
| **リモート** | GitHub側のリポジトリ。うちでは `origin` という名前 | 共有場所の住所 |
| **clone** | GitHubのリポジトリを自分のPCに丸ごと複製する(最初の1回だけ) | 作品を借りてくる |
| **マージ** | 枝分かれした変更を合流させる | 作業した内容を本編に取り込む |

### ブランチをもう少しだけ

うちで一番よく使う概念なので補足する。

`main` という枝が**本編**。ここは**常に動く状態**を保つ約束になっている(→ [`開発フローガイド.md`](../ガイドライン/開発フローガイド.md))。
何か作るときは、`main` から**自分専用の枝を生やして**、そこで作業する。

```
main    ──●──●──●─────────────●──   ← 本編。常に動く
              └──○──○──○──┘        ← 自分の枝。ここで自由に失敗できる
                (自分の作業)      ↑ 完成したら本編に合流(マージ)
```

なぜ枝を分けるのか。**自分が途中の・壊れた状態のコードを、他の人に影響させないため。** 枝の中なら何度失敗してもよく、完成したものだけを本編に返す。これが問題1(上書き事故)の解決策。

## 4. 最低限のコマンド8つ

順番が意味を持つので、**日常の流れの順**に並べる。

### 準備(最初の1回だけ)

```bash
# 自分が誰かをGitに教える(コミットに名前が刻まれる)
git config --global user.name "あなたの名前"
git config --global user.email "GitHubに登録したメールアドレス"

# GitHubからリポジトリを手元に複製する
git clone https://github.com/NUTFes/quizApp.git
cd quizApp
```

> **認証で止まったら**
> `clone` や `push` のときにユーザー名/パスワードを聞かれることがある。GitHubは**パスワードでは通らない**(2021年に廃止された)。
> 一番簡単なのは **GitHub CLI** を入れて `gh auth login` を1回実行する方法。詰まったらPMに聞く。ここで消耗する必要はない。

### 日常の流れ

```bash
# ① 最新の本編を取り込む(作業を始める前に必ず)
git switch main
git pull

# ② 自分の枝を作って、その枝に移動する
git switch -c feat/12-monitor-question-view

# ③ ここでコードを編集する ───────────

# ④ いま何を変えたか確認する
git status

# ⑤ 記録する対象を選ぶ(. は「変更した全部」)
git add .

# ⑥ 記録を作る(メッセージは日本語1行でよい)
git commit -m "モニタの出題画面を追加"

# ⑦ GitHubへ送る
git push
```

### コマンドの意味を1行ずつ

| コマンド | やっていること | なぜ要るか |
|---|---|---|
| `git pull` | GitHubの最新を手元に取り込む | 古い本編から枝を生やすと、後で合流が面倒になる |
| `git switch -c 名前` | 新しい枝を作って移動 | `-c` は create の c。`-c` 無しだと既存の枝への移動 |
| `git status` | いま何を変えたかの一覧 | **困ったらまずこれ**。Gitは今の状況を必ず教えてくれる |
| `git add .` | 記録する対象を選ぶ | 「変更した」と「記録する」は別の操作。選んでから記録する |
| `git commit -m "..."` | 記録を1個作る | メッセージは未来の自分とチームへの説明 |
| `git push` | 手元の記録をGitHubへ送る | **これをやるまでチームには見えない** |

### なぜ `add` と `commit` が分かれているのか

「変更した10ファイルのうち、関係のある3ファイルだけを1つの記録にまとめたい」ができるようにするため。
ただし**初心者のうちは `git add .`(全部)で構わない**。1つの作業に集中していれば、変更したファイルは全部その作業のものだから。

### コミットはどのくらいの粒度で作るのか

**「意味のある一区切り」ごと。** 迷ったら細かく作ってよい。
うちは **squash merge**(→ [`GitHub運用ガイド.md`](../ガイドライン/GitHub運用ガイド.md))なので、**枝の中のコミットは本編に残らない**。だから「きれいなコミットを作らなきゃ」と気負う必要はまったくない。`main` に残るのはPR1個=コミット1個だけ。

## 5. よくあるトラブル

### 「間違えて `main` で作業してしまった」

よくある。まだコミットしていないなら、そのまま枝を作れば変更ごと持っていける。

```bash
git switch -c feat/12-なんとか   # 変更を持ったまま新しい枝へ移動できる
```

すでに `main` でコミットしてしまった場合は**自力で直そうとせず、PMに声をかける**。無理に戻そうとして履歴を壊すほうが被害が大きい。

### 「push しようとしたら拒否された」

エラーに `rejected` や `non-fast-forward` と出る。意味は「**GitHub側に、自分の手元にない変更がある**」。
自分の枝で1人で作業しているなら、まず起きない。起きたら以下:

```bash
git pull        # 相手の変更を取り込んでから
git push        # もう一度送る
```

### 「コンフリクト(競合)と言われた」

**同じファイルの同じ行を、2人が別々に変えた**ときに起きる。Gitは「どちらが正しいか」を判断できないので、人間に聞いてくる。

ファイルの中に次のような印が入る:

```
<<<<<<< HEAD
自分が書いた行
=======
相手が書いた行
>>>>>>> main
```

**やること**: 正しい形に手で書き直し、`<<<<<<<` `=======` `>>>>>>>` の3行を消す。そして `git add` → `git commit`。

**予防策**: うちのルール「**1タスク = 1フォルダ**」(→ AGENTS.md §6)は、そもそも同じファイルを2人が触らないようにしてコンフリクトを構造的に防ぐためのもの。ルールを守っていればほぼ起きない。

起きて分からなくなったら、**触らずにPMへ**。慌てて消すと相手の作業が消える。

### 「何かよく分からない状態になった」

```bash
git status      # まずこれ。Gitは大抵、次に何をすればいいか教えてくれる
```

それでも分からなければ聞く。**うちには「30分詰まったら質問する」ルールがある。** Gitで詰まるのは全員が通る道で、恥ずかしいことではない。

## 6. コマンドが苦手ならGUIでよい

**VS Code の左サイドバーにある「ソース管理」タブ**(枝分かれのアイコン)から、`add` / `commit` / `push` はボタンで全部できる。
枝の切り替えも左下の枝名をクリックするだけ。**コマンドを覚えることは目的ではない**ので、GUIで進めて構わない。

ただし `git status` が何を見ているかだけは理解しておくと、GUIの画面も読めるようになる。

---

## 7. まとめ — これだけ覚えれば始められる

1. **手元とGitHubは別の世界。** `push` するまでチームには見えない
2. **作業の前に `git pull`、作業は必ず自分の枝で**
3. **編集 → `add` → `commit` → `push`** の4拍子
4. **困ったら `git status`、それでもダメなら30分で質問**
