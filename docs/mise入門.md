# mise入門 — なぜDockerだけじゃなくmiseも使うのか

このプロジェクトの開発環境は「Docker Desktop と mise を入れる → `git clone` → `mise run up`」で動く設計になっている。
Dockerは聞いたことがあっても mise は初めて、という人向けに「miseが何をする道具なのか」を説明する。

---

## 1. 結論: Dockerとmiseはライバルではなく役割が違う相棒

| 道具 | 役割 | たとえると |
|---|---|---|
| **Docker** | アプリを動かす**箱**(実行環境)を用意する | 調理器具一式が揃ったキッチン |
| **mise** | その箱を操作する**人間側のコマンド**を整える | キッチンの使い方が1枚にまとまったメニュー表 |

Dockerは「フロント・バック・DBが全員のPCで同じように動く」ことを保証してくれる。
でも、**Dockerを操作するのは結局人間**で、そこには2つの問題が残る。miseはその2つを解決する。

---

## 2. miseの仕事① タスクランナー: 長いコマンドに短い名前を付ける

Dockerだけで開発すると、日常的にこういうコマンドを打つことになる:

```
docker compose up -d --build
docker compose exec backend migrate -path /app/migrations -database $DATABASE_URL up
docker compose down -v db && docker compose up -d db && ...
```

これを**全員が正確に覚える(またはREADMEからコピペし続ける)のは現実的でない**。
打ち間違いや「`--build` を付け忘れて古いままだった」のような事故も起きる。

miseを使うと、プロジェクト直下の `mise.toml` にコマンドを登録して短い名前で呼べる:

```toml
[tasks.up]
description = "開発環境を起動"
run = "docker compose up -d --build"

[tasks."db:migrate"]
description = "マイグレーションを適用"
run = "docker compose exec backend migrate -path /app/migrations -database $DATABASE_URL up"
```

メンバーが覚えるのはこれだけ:

```
mise run up          # 起動
mise run down        # 停止
mise run db:migrate  # DB更新
mise tasks           # 何ができるか一覧を見る(忘れてもこれで思い出せる)
```

ポイントは **「コマンドの中身を知らなくても操作できる」** こと。
中身(Dockerの正しい呼び出し方)はまとめ役が一度だけ書き、全員はメニュー名だけ覚えればいい。

> 似た道具に Makefile や npm scripts があるが、それらの現代版+次の②も兼ねるのが mise。

---

## 3. miseの仕事② バージョン固定: 「私のPCだと動かない」の残り半分を潰す

Dockerがあれば実行環境は揃う。でも実は**コンテナの外**で使う道具が残っている:

- エディタ(VS Code)の補完・エラー表示が使う Node や Go
- 手元でちょっと `pnpm install` したり `go get` したりする時の Node / Go

これらのバージョンが人によってバラバラだと、「Aさんのエディタではエラーが出ないのにBさんでは出る」「入れたパッケージのlockファイルが人によって変わる」という地味に厄介な問題が起きる。

miseは `mise.toml` に書いたバージョンを**そのプロジェクトのフォルダ内でだけ**自動で有効にする:

```toml
[tools]
go = "1.25"
node = "22"
pnpm = "latest"
```

新メンバーは `mise install` と1回打つだけで、指定バージョンのGo/Node/pnpmが揃う。
別プロジェクトで違うバージョンを使っていても衝突しない(フォルダを出れば元に戻る)。

---

## 4. 「Dockerだけで管理」と比べたときの新メンバー体験

### Dockerだけの場合

1. README を読む(長い)
2. Nodeを自分で入れる(バージョンは各自バラバラ)
3. READMEから長いコマンドをコピペして起動
4. 以後、操作のたびにREADMEを探す

### Docker + mise の場合

1. Docker Desktop と mise を入れる
2. `git clone` → `mise install` → `mise run up`
3. ブラウザを開くと動いている
4. 以後の操作は `mise tasks` で一覧を見て選ぶだけ

**README の環境構築手順が10行以内**に収まるのがゴール(開発環境policyより)。
初心者チームでは「環境構築でつまずいて最初の1週間が溶ける」のが最大のリスクなので、そこを構造的に潰すための投資と考えてほしい。

## 5. 仕組みの話: 「直接 pnpm と打ってるのにバージョンが揃う」のはなぜ?

`mise run lint` の中身は `pnpm --dir frontend lint` で、一見「そのPCに入っているpnpm」が動きそうに見える。それでもバージョンが揃うのは、**`pnpm` と打ったときにどの実体が起動するかをmiseがすり替えている**から。

### 前提: コマンド名は「住所帳(PATH)」で解決される

ターミナルで `pnpm` と打つと、PCは **PATH** という住所リスト(フォルダの一覧)を**上から順に**探して、最初に見つかった「pnpm」という実行ファイルを起動する。

```
PATH = [ フォルダA, フォルダB, フォルダC, ... ]
         ↑ 上から順に探し、最初に見つけたものを使う
```

自分でNodeを入れた人は、この住所帳のどこかに「自分で入れたバージョンのpnpm」がいる。入れた時期が人によって違うから、バージョンがバラバラになる — これが素の状態の問題。

### miseは住所帳の先頭に割り込む

1. `mise install` は、mise.toml指定バージョンのGo/Node/pnpmを**mise専用の倉庫**(`~/.local/share/mise/installs/` 配下)に保管する。PCに既に入っている別バージョンとは共存(上書きしない)
2. **プロジェクトのフォルダに cd した瞬間**、miseがそのフォルダの mise.toml を読み、指定バージョンの置き場所を**PATHの先頭に差し込む**

```
quiz-app/ の中にいるとき:
PATH = [ miseの倉庫のpnpm 10.x ←先頭に割り込み, 自分で入れたpnpm 9.x, ... ]
→ 「pnpm」と打つと必ず 10.x が動く

フォルダを出ると:
PATH = [ 自分で入れたpnpm 9.x, ... ]  ←元通り
```

これが「フォルダ内でだけ有効」「別プロジェクトと衝突しない」のからくり(フォルダごとに違うmise.tomlを読んで、差し込む中身を変えているだけ)。
さらに `mise run` のタスクは、miseが必ずこの環境を整えてから実行するので、タスク経由なら確実に固定バージョンで動く。

### それでも漏れる2つの経路と、塞ぎ方

| 穴 | 何が起きるか | 塞ぎ方 |
|---|---|---|
| miseのセットアップ自体をサボった人 | PATHに割り込みが入らず、自前のpnpmが動く | READMEのセットアップ手順に組み込む+CIが最後の関門になる |
| CI(GitHubのサーバー) | GitHubのマシンには何も入っていない | CI設定でも**同じmise.tomlを読んで**ツールを入れる(mise公式のGitHub Actions連携がある) |

つまりバージョン固定の実体は「**mise.tomlという1つのファイルを、全員の手元とCIの全箇所が参照する**」こと。ファイルを1箇所直せば全員が揃い、逆に「揃っていない状態」を作るほうが難しい構造になっている。

## 6. よくある質問

**Q. mise自体のインストールは?**
Windowsの人はWSL2の中に、Macの人はそのままインストールする。手順はリポジトリのREADMEに載せる。1回やれば以後のプロジェクトでも使い回せる。

**Q. miseのコマンドを打つと結局Dockerが動いてるの?**
そのとおり。`mise run up` の中身は `docker compose up -d --build`。miseは「呼び出し方を整理する層」であって、実行環境そのものはDockerが担う。

**Q. mise.toml は誰が書くの?**
まとめ役が用意する。メンバーが編集する必要は基本ない(「このコマンドも登録してほしい」という要望は歓迎)。
