# 画面・要件 完全版

技大祭クイズ大会アプリの「何を作るのか」を確定させたドキュメント。
運営側とのヒアリングで決まった内容をすべて反映してあり、**このファイルが画面仕様の正**。
会話に参加していなかった人が最初に読む前提で書いてある。

---

## 1. イベントの概要(まずこれを知らないと始まらない)

技大祭で行う**リアルタイムクイズ大会**のためのアプリを作る。ただし、よくある「スマホで回答するクイズアプリ」では**ない**。

### ゲームのルール: 勝ち残り × 移動形式

- 会場を **2×2 の4エリア**に分割し、各エリアが選択肢に対応する
- 参加者は正解だと思う選択肢の**エリアへ実際に歩いて移動**して回答する
- 誤答者は脱落していく勝ち残り式。**正誤の判定・脱落の管理はすべて運営スタッフの人力**で行う

### 規模と当日の体制

| 項目 | 内容 |
|---|---|
| 参加者数 | 例年 約200人(敗者復活には100〜150人) |
| モニタ | 85インチ(環社棟から借用)。ステージのホワイトボードより大きい |
| 司会(MC) | **紙の台本だけを見る**。アプリは操作しない |
| アプリ操作 | **裏方(情報局員)1人**が管理者画面を操作する |
| 制限時間 | **30秒固定**で表示する。時間切れで**画面は「締切」表示に変わる**が、**フェーズは自動では進まず**、正答表示は裏方の操作(→§4) |

## 2. アプリがやること・やらないこと

ここがこのアプリの一番の特徴。**回答機能がない**。

### やること

- モニタに問題・選択肢・残り時間・正答を表示する
- 参加者のスマホにも同じ内容を表示する(モニタが見えない人向けのミラー)
- 裏方の操作で、**全端末の画面を一斉に切り替える**
- 問題データをスプレッドシートから取り込む

### やらないこと(確定)

| やらないこと | 代わりにどうするか |
|---|---|
| スマホからの回答送信 | エリアへの移動で回答(人力判定) |
| 正誤判定・脱落管理 | 運営スタッフの目視 |
| 早押しの自動判定 | モニタの問題文表示+人力判定 |
| 敗者復活の抽選・管理 | 会場運営+Google Form+紙 |
| アンケートの集計 | Google Form(アプリはリンクを置くだけ) |
| ログイン・参加者登録 | 一切なし。QRを読んでページを開くだけ |

「やらないこと」が多いのは手抜きではなく設計判断。**当日確実に動くことが最優先**で、人力で回る部分はアプリにしない。

## 3. 3つの画面

アプリには3つの画面(URL)がある。1つのWebアプリの中でページが分かれているだけ。

```
                 ┌──────────────────┐
   裏方 ──操作──> │  バックエンド(サーバー)  │
 【管理者画面】    │  「今の状態」を1つだけ持つ │
                 └─────────┬────────┘
                           │ 状態を一斉配信(SSE)
              ┌────────────┴────────────┐
              ▼                         ▼
        【モニタ画面】               【スマホ画面】
        85インチ・会場の主役          参加者の手元のミラー
```

| 画面 | 誰が見る | 役割 |
|---|---|---|
| **モニタ画面** | 会場全員 | **主役**。問題・選択肢・タイマー・正答・演出をすべて表示 |
| **スマホ画面** | 参加者 | モニタの内容を手元でも見られるようにするミラー。**ボタンや入力は一切ない(見るだけ)** |
| **管理者画面** | 裏方1人 | 進行の操作盤。問題を出す・正答を出す・スプシ同期 |

## 4. 進行の流れ(フェーズ)

イベントの進行は4つの**フェーズ**で表す。今どのフェーズかはサーバーが1つだけ記憶していて、裏方の操作で切り替わる。全端末はそれに従って表示を変えるだけ。

| フェーズ | 意味 | モニタ・スマホの表示 |
|---|---|---|
| `waiting` | 開始前 | 「まもなく始まります」+参加用QRコード |
| `question` | 出題中 | 問題文・選択肢・残り時間(30秒)のカウントダウン。**残り0秒になると「締切」表示に変わる**(下記) |
| `answer` | 正答発表 | 問題と選択肢はそのまま、**正答だけハイライト**+正解演出+解説(あれば) |
| `finished` | 終了後 | 終了メッセージ+**アンケート(Google Form)への誘導**。参加用QRと問題番号は出さない(下記) |

```
waiting ──> question ──> answer ──> question ──> … ──> finished
        出題ボタン    正答表示ボタン   次の問題を出題
        (すべて裏方の操作で進む。フェーズの自動遷移はしない)

           question フェーズの中身:
             問題表示 ──(残り0秒。各端末が自分で判定)──> 締切表示
                                                          │
                                          裏方が「正答表示」を押す
                                                          ▼
                                                       answer へ
```

1問ずつ `question → answer` を繰り返し、最後の問題が終わったら `finished` にする。

### 締切表示(2026-08-14 追加)

時間切れの瞬間に画面が何も変わらないと、会場の空気が途切れる。**残り0秒になったら「締切!」の表示に切り替え**、司会者が煽ってから裏方が正答表示ボタンを押す、という間を作る。

**これはフェーズではなく、`question` フェーズの中の表示状態**。`close` のようなフェーズは追加しない。

- **判定は各端末が自分で行う**。カウントダウンはもともとサーバーが秒数を送らず、`serverTime` / `questionStartedAt` / `timeLimitSec` から各端末が計算している(→ API仕様書 §0)。「残り0秒になった」はその計算結果を読むだけなので、サーバーに聞く必要がない
- **途中参加・再接続した端末でもズレない。** `questionStartedAt` を受け取れば同じ結果を計算できるため。同じ理由で `askedCount`(=今何問目)は逆に**計算で復元できない**ので、あちらはサーバーが配る。**「配られたデータから計算で復元できるか」が、フロントで判定してよいかの基準**
- **サーバー側の実装は不要。** サーバーがタイマーで自分から状態を変える仕組みは、v1では一切持たない
- **裏方が早めに締め切ることはできない**(時間ちょうどでのみ切り替わる)。制限時間は会場全員がカウントダウンを見ているため、裏方の裁量が入る余地がないと判断した。必要になったら後から `close` フェーズを足せる

判定式(フロント):

```ts
const isClosed = phase === 'question' && remaining <= 0
```

### フェーズごとの表示要素(2026-08-16 追加)

`finished` の表示要素が「アンケート誘導」としか決まっておらず、**参加QRを出し続けるのか**が未定だった。あわせて全フェーズ分を1つの表にまとめる。

| 表示要素 | `waiting` | `question` | `answer` | `finished` |
|---|---|---|---|---|
| 参加用QR(`joinUrl`) | ✅ 大きめ | ✅ 右上に固定 | ✅ 右上に固定 | ❌ **出さない** |
| アンケートQR(`VITE_SURVEY_URL`) | ❌ | ❌ | ❌ | ✅ |
| 問題番号「第N問」(`askedCount`) | ❌ | ✅ | ✅ | ❌ |
| 問題文・選択肢 | ❌ | ✅ | ✅ | ❌ |
| 残り時間 / 締切 | ❌ | ✅ | ❌ | ❌ |

**なぜ `finished` で参加QRを消すか**

- 参加QRは「**途中参加者向け**」(→§6)。終わったクイズに参加する人はいない
- `finished` では**アンケートQRを出す**(→§6)。同じ画面にQRが2つ並ぶと、参加者がどちらを読めばよいか分からない。85インチを遠くから見るので事故りやすい

> **APIは全フェーズで `joinUrl` を送る**(→ API仕様書 §2.2.1)。キーを消さないのがAPIの原則なので、**「送るかどうか」ではなく「画面に出すかどうか」の話**。フロント側で出し分ける。

**なぜ `waiting` / `finished` で問題番号を出さないか**

`finished` へは `reset {"to":"finished"}` でしか入らず(→ API仕様書 §0の遷移図)、`reset` は全問の `asked` を `false` に戻す。したがって **`askedCount` は必ず `0`** になる。素直に表示すると「**第0問**」と出てしまう。`waiting` も同じ理由で `0`。

**アンケートURLはstateに入らない**

`VITE_SURVEY_URL`(フロントの環境変数)から読む。サーバーは送らない。当日までURLが決まらず(→§11)、決まってもアプリの再デプロイなしに差し替えたいため。

## 5. 問題形式と画面レイアウト

### 問題形式は4種類

| 形式 | 内容 | 選択肢の配置 |
|---|---|---|
| 4択 | 4つから選ぶ | **2×2**(会場の4エリアと同じ位置関係) |
| 2択(あるなし等) | 2つから選ぶ | **ステージに対して左右**の2つ |
| ○× | ○か×か | **左右**の2つ |
| 早押し | 司会の読み上げに合わせて問題文を少しずつ表示 | 下記参照 |

**選択肢の画面上の配置=会場のエリアの位置関係**、がこのアプリの根幹。参加者は画面を見て「自分はあっちのエリアだ」と分かる。
(注意: 手書きラフでは2択が上下配置になっていたが、**左右が正**)

### 早押し形式の特別ルール

- 問題文は**モニタにのみ**表示する。**スマホには表示しない**(手元で先に読めてしまうと早押しにならないため)。スマホには「モニターをご覧ください」を表示する
- 問題文は一度に全部出さず、**区切りごとに少しずつ表示**する。司会の読み上げ速度に合わせて、裏方が「次を表示」ボタンで送る
- 誰が早かったかの判定はアプリではやらない(人力)

### 問題文の「区切り」の仕組み

問題文はスプレッドシート上で `/`(スラッシュ)を入れて区切る。

```
スプシに書く:  第1回技大祭が開催されたのは/西暦何年?/
画面での表示:  「第1回技大祭が開催されたのは」→(ボタン)→「西暦何年?」
```

## 6. 各画面の仕様

### モニタ画面(85インチ)

- 問題文(早押しは順次表示)・選択肢(2×2 または 左右)・残り時間
- **「第3問」のように今何問目かを表示**する。**分母(全N問)は出さない** — 勝ち残りの進み具合を見て当日その場で出題数を増減させるため、先に総数を確定できない。データ上は `askedCount` フィールド(→ API仕様書 §1)。**サーバーが配る値をそのまま出すだけで、フロントで数えてはいけない**(QRから途中参加した端末が別の数を表示してしまう)
- **残り0秒になったら「締切!」表示に切り替える**(→§4)。問題文と選択肢は出したまま、タイマー部分を締切表示に変える。この状態で司会者が煽り、裏方が正答表示を押すまで待つ
- **画面右上に参加用QRコードを表示**(途中参加者向け)。`waiting` / `question` / `answer` の3フェーズで出し、**`finished` では出さない**(→§4)
- 正答発表時: 正答の選択肢をハイライト+**正解演出**(企画側が制作する動画をアプリが再生するだけ。パチンコ風演出も同様)
- 待機中:「まもなく始まります」
- 終了後: アンケートQR/リンク(`VITE_SURVEY_URL` から生成。**stateには含まれない**)。**参加用QRは消し、アンケートQRに差し替える**(QRが2つ並ぶと、どちらを読むか分からなくなるため)

### スマホ画面(参加者用ミラー)

- モニタとほぼ同じ内容の縦画面版。**操作要素ゼロ**
- 「次へ」ボタンはない。画面はすべて自動で切り替わる
- モニタと同じく**今何問目かを表示**する(`askedCount`)。途中参加でもモニタと同じ数字になる。**`waiting` / `finished` では出さない**(必ず `0` になるため。→§4)
- モニタと同じく**残り0秒で「締切」表示**に切り替える(→§4)。途中参加でもモニタと同じ瞬間に切り替わる
- 早押し問題のときは問題文の代わりに「モニターをご覧ください」
- 解説は**ある問題だけ**表示(ほとんどの問題は解説なし。ない時にレイアウトが不自然にならないよう注意)。データ上は `explanation` フィールド(→ API仕様書 §1)。**answer フェーズでしか配信されない**
- 会場マップ(どのエリアがどの選択肢か)は、操作がないので**画面上部など触らない場所**に配置。見やすさは試行錯誤する
- リロードしても・途中から開いても、その瞬間の画面に自動で追いつく

### 管理者画面(裏方専用)

情報局員が使うものなので、**自分たちが使いやすいように設計してよい**(ただし「身内用だから雑でいい」は禁止。当日焦っている状態で使うものなので、むしろ使いやすさ優先)。

- 問題リスト(ID・問題文・難易度)から**問題を選んで出題**する方式
  - 「次へ」ではなく「この問題を出す」と指定する方式なので、ボタンを2回押しても事故らない
- 「次を表示」ボタン: 早押しの問題文を1区切り進める
- 「正答を表示」ボタン: **確認ポップアップを1回挟む**(誤操作で正答が漏れるのが一番怖いため)
- 「リセット」: 進行を最初に戻す
- 「スプシ同期」ボタン: 問題データをスプレッドシートから取り込む。エラーがあれば行番号つきで表示
- 今モニタに映っている画面のプレビュー
- パスワードで保護する(参加者がURLを推測して操作できないように)

## 7. ずるができない仕組み(情報の出し分け)

「スマホの通信をこっそり覗けば正答が分かるのでは?」への対策。

**サーバーが、送る相手によって中身を変えて配信する:**

| 受け取る側 | 出題中の正答 | 早押しの問題文 |
|---|---|---|
| 管理者画面 | 届く(確認用) | 届く |
| モニタ | **届かない** | 届く(表示する場所だから) |
| スマホ | **届かない** | **届かない** |

スマホ側で「隠して表示している」のではなく、**そもそもデータが手元に届いていない**ので、詳しい人がブラウザの開発者ツールを開いても見えない。正答が届くのは正答発表フェーズになった瞬間。

## 8. 問題データの作り方(運営メンバー向け)

問題はGoogleスプレッドシートに1行1問で書く。列は以下のとおり。

| 列 | 内容 | 必須 |
|---|---|---|
| number | 表示用のクイズ番号(一度付けたら変えない) | ✅ |
| type | four_choice / two_choice / arunashi | ✅ |
| text | 問題文(順次表示したい位置に `/` を入れる) | ✅ |
| choiceA〜choiceD | 選択肢(形式により使う数が変わる。2択はC・Dを空欄) | 形式による |
| correct | 正解の**列名**(`A` `B` `C` `D`) | ✅ |
| difficulty | `簡単` / `普通` / `難しい` | ✅ |
| explanation | 解説(**任意**。ある問題だけ画面に表示される) | |
| imageUrl | 問題画像のパス(任意) | |
| imageA〜imageD | 選択肢画像のパス(任意) | |

> **正は [`API仕様書.md`](./API仕様書.md) §3.5.6。** 迷ったらそちらを見ること。この表は運営メンバー向けの要約。

- 出題順は決めない。**当日その場で「この問題を出す」と選ぶ**方式なので、順番の列は無い
- 制限時間の列も無い。既定は30秒で、変えたいときは管理者画面の入力欄で指定する

書き終わったら管理者画面の「同期」ボタンで取り込む。**書き間違いが1つでもあると取り込まれず、どの行の何が悪いか表示される**ので、直してもう一度押せばよい。
