KK# 技術スタック 完全版

このアプリで使う技術と、その選定理由をまとめた確定版ドキュメント。
**これまで HTML と CSS しか触ったことがない人でも読めるように書いてある**ので、知らない単語が出てきても安心して読み進めてほしい。

---

## 1. まず全体像: Webアプリは「3つの場所」で動く

HTML/CSS で作ってきたページは、すべて**ブラウザの中**で表示されるものだった。
Webアプリはそれに加えて、あと2つの場所が登場する。

```
┌──────────────┐      ┌──────────────┐      ┌──────────────┐
│ ① フロントエンド │ ⇄通信⇄ │ ② バックエンド  │  ⇄  │ ③ データベース │
│  (ブラウザの中)  │      │ (サーバーの中)   │      │  (データの倉庫)  │
└──────────────┘      └──────────────┘      └──────────────┘
  見た目と操作         記憶と判断の中枢        問題データの保管
  HTML/CSS/JSの世界     Goというプログラム       表形式でデータを保存
```

- **① フロントエンド** … 参加者・モニタ・管理者の画面。今まで学んできた HTML/CSS の延長線上にある世界
- **② バックエンド** … 会場に1台だけあるサーバーで動くプログラム。「今何問目か」を記憶し、「その操作をしていいか」を判断する**進行責任者**
- **③ データベース(DB)** … 問題文・選択肢・正答などを保存しておく倉庫。バックエンドだけが読み書きする

フロントとバックは**完全に別のプログラム**で、HTTPという通信でしか会話できない。この会話のルールを決めたものを **API** と呼ぶ(詳細は `docs/api.md` に書く)。

## 2. 採用技術一覧

| 場所 | 技術 | 一言でいうと |
|---|---|---|
| フロントエンド | **React** | HTMLを「部品」として組み立てるJavaScriptの道具 |
| 〃 | **TypeScript (TS)** | JavaScriptに「型」という安全装置を付けた言語 |
| 〃 | **Vite** | 開発用サーバー+完成品(静的ファイル)を作る道具 |
| 〃 | **React Router** | 1つのアプリ内で `/`(スマホ)・`/monitor`・`/admin` のページを切り替える道具 |
| 〃 | **Tailwind CSS** | CSSをクラス名の組み合わせで書くスタイル道具 |
| バックエンド | **Go(言語)+ Gin** | サーバー側プログラムの言語と、HTTP窓口の道具 |
| 〃 | **GORM + golang-migrate** | GoとDBの間の翻訳係+DBの構造変更の管理係 |
| リアルタイム通信 | **SSE (Server-Sent Events)** | サーバーから全端末への一方通行の実況中継 |
| データベース | **PostgreSQL** | 定番のデータベース |
| 問題データ入稿 | **Googleスプレッドシート → 同期ボタン** | 非エンジニアの運営メンバーが問題を作れる仕組み |
| 開発環境 | **Docker Compose + mise** | 全員のPCで同じ環境を一発で立ち上げる道具 |

## 3. フロントエンド: なぜこの組み合わせか

### React — 「画面を部品で組み立てる」

HTMLをそのまま書く代わりに、**「選択肢ボタン」「タイマー」「問題文カード」のような部品(コンポーネント)を作って組み合わせる**書き方をする。部品は「データを渡すと、それに応じたHTMLを返す」関数のようなもの。

同じ見た目を何度も使い回せて、「データが変わったら画面も自動で変わる」のが最大の特徴。今回のような「サーバーから届いた状態をそのまま映す」アプリと非常に相性がいい。

### TypeScript — 「JSに補完とエラー検出が付いたもの」

JavaScriptに「このデータには問題文(text)と選択肢(choices)が入っている」という**型**の情報を書き足せる言語。書き間違い(`text` を `txt` と打つ等)を実行前にエディタが教えてくれる。

**メンバーは型を「書く」必要はほぼない。** 型定義はまとめ役が用意するので、メンバーはその恩恵(補完・エラー検出)を受けながらコンポーネントを書くだけでいい。

### Vite — 「開発サーバー+ビルド道具」

2つの仕事をする:

1. **開発中**: 保存した瞬間にブラウザへ反映される開発サーバーを動かす
2. **完成時**: コードを**ただのHTML/CSS/JSファイルの束**に変換する(ビルド)

重要なのは2つ目で、**完成品は普通の静的ファイル**になる。本番サーバーで特別なものを動かし続ける必要がなく、配信するだけでいい。

### Tailwind CSS — 「クラス名でスタイルを書く」

```html
<button class="bg-blue-500 text-white rounded-lg px-4 py-2">
```

のように、あらかじめ用意されたクラスを組み合わせてデザインする。CSSファイルの設計(命名規則やファイル分割)を議論しなくて済み、見本のコピペで進めやすい。

### 不採用: Next.js

Reactの上位フレームワークとして候補に挙がったが、以下の理由で不採用にした:

1. Nextの強み(検索エンジン対策・初回表示高速化)を使う場面がない — QRコードから入る会場限定アプリに検索対策は無関係
2. 本番サーバーに常駐プログラムが増える — Viteなら静的ファイルを置くだけ
3. 追加の学習概念が多い — React学習済みメンバーがそのまま書き始められるViteの方が、学習リソースをGo側に回せる

## 4. バックエンド: なぜこの組み合わせか

### Go — サーバー側の言語

選定理由は技術的必然ではなく、**「Goを学びたい・アウトプットしたいバックエンド人材がいる」こと**。教えたい人がいる技術が最強。公式チュートリアル修了者がバックエンドリーダーを担う。

バックエンドの仕事は「受けて配る」だけではない。**このアプリの頭脳**として以下を担う:

| 役割 | 内容 |
|---|---|
| 記憶 | 「今何問目・どのフェーズか」を唯一の正として持つ(全端末はこれに従うだけ) |
| ルールの番人 | 「問題を出していないのに正答表示」のような不正な操作を拒否する |
| 門番 | 管理者の操作APIを、本物の管理者以外が叩けないようにする(認証) |
| 情報の出し分け | 未公開の正答・早押しの問題文を、参加者向けの配信から**抜いて**送る |
| 唯一の時計 | 残り時間の基準。各スマホの時計のズレに影響されない |
| 検品 | スプシ同期時に全行をチェックし、1件でも不備があれば取り込まない |
| 接続の世話 | 途中参加・リロードした端末に、その瞬間の状態を渡して追いつかせる |

### Gin — HTTPの窓口係

「`/api/state` にアクセスが来たらこの関数を呼ぶ」という振り分け(ルーティング)や、JSONデータの受け取り・返却を楽にする道具。Goの中で日本語の入門記事が最も多く、写経元に困らない。

### GORM — DBとの翻訳係

DBに話しかけるには本来SQLという専用言語が要るが、GORMを使うと `db.Find(&questions)` のような**Goの普通の書き方でDBを読み書き**できる。メンバーは最初、SQLをほぼ書かずに済む。

DBの構造(テーブル定義)の変更履歴は golang-migrate というツールで管理する。

### PostgreSQL — データベース本体

定番中の定番。開発でも本番でも同じものをDockerで動かす。

## 5. リアルタイム同期: SSE(このアプリの心臓部)

このアプリの本質は「**裏方がボタンを押すと、会場の全スマホ+モニタの画面が一斉に切り替わる**」こと。

普通のWeb通信は「クライアントが尋ねて、サーバーが答える」形しかできない。つまり**サーバー側から話しかける手段がない**。そこで SSE を使う。

### SSE = サーバーからの一方通行の実況中継

最初に1回接続したら**切らずに開けっぱなし**にし、サーバーが好きなタイミングでメッセージを流し込む。ラジオの実況中継のイメージ。

```
スマホ・モニタ:「つなぎっぱなしにするね」→(待機)
                     ↓ 裏方が「5番を出題」ボタンを押す
サーバー:「state: 5番出題!」 ← 全端末に一斉に届き、画面が切り替わる
サーバー:「timer: 残り29秒」
サーバー:「state: 正答表示!」
```

- ブラウザ標準の `EventSource` という機能で受信できる(追加ライブラリ不要)
- **切断されたらブラウザが自動で再接続**してくれる。再接続時にサーバーが現在の状態を送り直すので、**リロードしても・途中参加でも・電波が切れても、開いた瞬間に今の画面に追いつく**

### 不採用: WebSocket

双方向(クライアント→サーバーも送れる)の通信方式。チャットのような「お互いに送り合う」アプリでは必須だが、**このアプリは参加者から送るデータがゼロ**(回答は会場のエリア移動で行い、アプリは回答を受け付けない)。下り一方通行の SSE で要件を完全に満たせるため、より実装が重い WebSocket は不採用。

### 注意: ハートビート(実装必須)

SSEの弱点は「何も流れない時間が続くと、経路上の設備(Cloudflare)が約100秒で接続を切ってしまう」こと。対策として、**サーバーは15〜30秒ごとに合図(ハートビート)を全接続に流す**。これを忘れると「ローカルでは動くのに本番だけ動かない」事故になる。

## 6. 問題データの流れ: スプシ → DB

問題は運営メンバー(非エンジニア)が **Googleスプレッドシート** で作成し、管理者画面の**「同期」ボタン**でDBへ取り込む。

```
スプシ(入稿ツール) ──同期ボタン──> DB(本番の参照元) ──> バックエンドが配信
```

- **手動同期のみ**(自動の定期同期はしない)。本番中に誰かがスプシを触って問題が差し替わる事故を構造的に防ぐ
- 同期時は全行を検品し、**1件でもエラーがあればDBを一切変えず**、エラー一覧(行番号+理由)を表示する
- **本番中はDBだけを見る**。当日Googleに障害があってもイベントは動く

## 7. 開発環境: 全員のPCで同じ環境を一発起動

- **Docker Compose**: frontend / backend / db の3つの箱(コンテナ)をまとめて起動する。「私のPCでは動かない」問題を根絶する道具
- **mise**: コマンドの短縮登録とバージョン固定。`mise run up` で全部立ち上がる
- Windowsの人は WSL2 の中で開発する(セットアップ手順は開発環境ドキュメント参照)

```
git clone → mise install → mise run up → ブラウザで開くと動いている
```

を全員のゴールとする。

## 8. チーム分担の方針

TypeScriptやAPI設計など「難しい判断が要る場所」は構造的に1箇所へ隔離してあり、担当を分けている:

| 担当 | 書くもの |
|---|---|
| まとめ役 | 型定義(`types/`)・SSE/API受信の仕組み(`lib/`)・API仕様書 |
| フロントメンバー | 画面の部品(`features/` 内のコンポーネント)。渡されたデータを表示する部分 |
| バックエンドリーダー | Go側の設計・実装(SSE基盤はまとめ役とペアで) |
| バックメンバー | API仕様書どおりの個別エンドポイント実装 |

フロントメンバーは **React の書き方だけ**で参加でき、バックメンバーは **Goの文法+見本の写経**から始められるようになっている。
