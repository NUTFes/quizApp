# フロントエンド実装要件

> `docs/API仕様書.md`(契約)には書かない、**フロント側の実装で守るべきこと・決定済みの実装方針**をまとめたもの。
> 契約(JSONの形・エンドポイント)と食い違ったら仕様書が正。ここは「届いたデータをどう扱い・どう見せるか」の側。

## 1. データフローの大原則

- **「state を受け取って画面全体を再描画する」1つの流れだけで作る**。差分適用・独自の進行管理・フェーズ予測などのロジックをフロントに書かない(進行の頭脳はサーバーだけ)
- 型定義は仕様書から書き起こす(`src/types/`。まとめ役担当)。**キーは常に存在し、値が `null` / `[]` になる**契約なので、型もそのとおりに書く(Optionalの乱用をしない)
- `Phase` は `waiting` / `question` / `answer` / `revival-video` / `revival-entry` / `finished` の6種類。敗者復活中は `question` が `null` なので、問題画面の部品へ渡さず専用画面へ切り替える
- 未知の `type` 値が来ても白画面にならないようフォールバック表示を用意する(将来のtype追加への保険)

## 2. SSE 接続(§5)

- ブラウザ標準の `EventSource` を使う(ライブラリ不要)。接続口はまとめ役が `src/lib/` に共通実装し、各画面はそれを使うだけ
- 接続URL: モニタ `?view=monitor` / スマホ `?view=phone` / 管理者 `?token=` 付き専用URL
- **再接続成功時は必ず `GET /api/state` を1回叩いて再描画してから**受信を再開する(切断中の取りこぼし対策。契約上のフロント必須実装)
- `ping` イベントは無視してよい(接続維持用)

## 3. タイマー表示

サーバーは残り秒数を送ってこない。**クライアントが計算する**:

```
時計ずれ = 手元の現在時刻 - 受信したserverTime   ← state受信のたびに更新
残り秒数 = timeLimitSec - (手元の現在時刻 - 時計ずれ - questionStartedAt)
```

- 0になっても**何も起こさない**(0のまま表示。遷移はすべて裏方の操作)
- 端末の時計がずれていても `serverTime` 補正で全端末の残り時間表示が揃う、が狙い
- 最初の描画では `serverTime - questionStartedAt` から受信時点の残り時間を同期的に求める。`useEffect` 後まで0秒を返して締切表示を一瞬出してはいけない
- `timeLimitSec === null` は制限時間なし。残り時間は `null` として扱い、カウントダウンを表示せず、常に回答受付中とする

## 4. 認証まわりのUI(管理者画面)

- 起動時に `GET /api/admin/verify` → 401ならトークン入力画面を表示
- トークンは `localStorage` に保存し、以降の全リクエストの `Authorization: Bearer` ヘッダに付ける(リロードしても再入力不要にすること。当日の事故防止)
- どのAPIでも401が返ったらトークン入力画面に戻す
- ログアウト = `localStorage` から消すだけ(APIなし)

## 5. コーディング規約(セキュリティ)

- **`dangerouslySetInnerHTML` 禁止**。Reactの自動エスケープを素通しにする唯一の穴で、問題文に仕込まれたスクリプトがlocalStorageのトークンを盗むXSS経路になり得る。文字列は必ず通常のJSXで表示する

## 6. type別の表示ルール

| type | 選択肢の配置 | 備考 |
|---|---|---|
| four_choice | **2×2**(会場の4エリアと同じ位置関係) | 配置=エリア対応がゲームの根幹 |
| two_choice | **左右**(○×も同じ。textが「○」「×」なだけ) | 手書きラフの上下配置は誤り・左右が正 |
| arunashi | **左右** | `text` は書式 `ラベル:項目/項目`(ラベル区切り=コロン `:`、項目区切り=スラッシュ `/`)で来ることが保証されている。`:` でラベルと項目群に、`/` で各項目に分解してリスト表示してよい(v1は文字列そのまま表示でも可) |
| hayaoshi | **出さない** | スマホは `type` を見て**画面まるごと専用表示**に切り替え、「会場モニターをご覧ください」だけを出す(問題番号・ステータス・残り時間・選択肢は出さない。`textSegments` は常に空配列で届く → 画面・要件.md §6)。モニタは順次表示し、answer phase で `explanation` の内容を正解として表示する |

- 問題文は `textSegments` 配列を先頭から連結して表示(全typeで同じ処理。1要素の問題も同じコードで動く)

## 7. 画面ごとの要点

### モニタ(`/monitor`)
- 右上に参加用QR(`joinUrl` から生成)を `waiting` / `question` / `answer` で表示(途中参加者向け)。敗者復活中と `finished` では出さない
- `answer` フェーズ: 正答ハイライト+正解演出動画の再生(動画は企画側制作の静的アセット)
- `waiting`: 「まもなく始まります」+QR大きめ / `finished`: アンケート誘導(URLは `VITE_SURVEY_URL`)
- `revival-video`: `/videos/revival.mp4` を全画面・既定は `muted` で再生。ページを開いた時点から先読みし、フェーズ切り替え後に新しく読み込み始めない。再生終了でphaseは変えず、最後のコマで待つ。URLに `?revivalAudio=monitor` がある場合だけミュートを外す。音つき自動再生をブラウザに拒否された場合は、映像を止めず無音再生へフォールバックする
- `revival-entry`: 敗者復活フォームのQR(URLは `VITE_REVIVAL_URL`)。通常の参加用QRと同時に出さない

### スマホ(`/`)
- **操作要素ゼロ**(ボタン・入力一切なし)。すべて自動で切り替わる
- 会場マップは**作らない**(2026-08-28 廃止)。選択肢の配置がそのまま会場エリアの配置なので、別途マップを出す必要がない
- リロード・途中参加は SSE接続時の初回stateで自動で追いつく(特別な処理は§2の共通実装に任せる)
- `revival-video`: 動画は流さず「会場モニターをご覧ください」。`revival-entry`: `VITE_REVIVAL_URL` をタップで開くリンク(QRは自分のスマホでは読めないため)

### 管理者(`/admin` 相当。推測されにくいパスにする)
- 問題リストから**選んで出題**(`show-question`)。「次へ」方式にしない(連打事故防止は契約側で担保済み)
- 出題時の**秒数入力欄(初期値30。5〜120の整数のみ、空欄・小数など範囲外は送信前に画面で止める)**と「制限時間なし」チェックボックスを置く。チェック時は入力欄を無効化し、`timeLimitSec: null` を明示的に送る。早押し問題を選んだときは自動でチェックするが、手動で外して時間制限を付けられる
- **「正答を表示」と、問題データの投入(全置換)は確認ポップアップを1回挟む**(誤操作で正答が漏れる/問題データが消えるのが最悪の事故)
- `show-question` の成功後に出題SEを1回鳴らし、終了後から締切までチックタックをループ再生する。ただし制限時間なしではチックタックを鳴らさない。同じ問題を `question` / `answer` 中に出し直す場合だけ、出題前に「音を出す」「音を出さない」を選べるようにする。この選択は危険操作ではないため、正答確認とは色・文言・ボタン配置を明確に分ける
- 時間ありの `question` で、`OperationPanel` が表示と共有する残り時間が正数から0秒になった瞬間にチックタックを止め、チャイムを1回鳴らす。最初から締切済みの状態を受け取ったときは鳴らさず、問題IDと出題開始時刻の組で出題を識別し、次の問題と同じ問題のやり直しで再び鳴らす。残り時間を音用に再計算しない
- 「正答を表示」の確認を開いた時点でチックタックを止めてドラムロールを始める。キャンセルまたはAPI失敗ではドラムロールを止めるだけとし、API成功時だけ正答発表SEへ切り替える。`advance-text` と `reset` には音を付けず、出題SE・正答発表SEはAPI成功前に先行させない
- 「次を表示」(advance-text)/「リセット」(to選択。#108では行き先ごとに「待機画面」「終了」の2ボタンに分けた)
- `revival('video')` / `revival('entry')` を「敗者復活へ」→「参加受付へ」の順で操作できるようにする。`revival-entry` からは既存の `show-question` で次の問題へ戻る
- 通常は「敗者復活へ」のAPI成功後に `/videos/revival.mp4` を管理者PCで `<audio>` として先頭から再生する(音声だけの別ファイルは作らない)。API失敗時には再生しない。ファイル不在・再生拒否でも進行処理と映像を止めない
- phaseを変える全ボタン（「敗者復活へ」「参加受付へ」「待機画面」「終了」「出題」「正解」）では、APIを呼ぶ前に敗者復活音声を停止して再生位置を先頭へ戻す。さらに、別タブ操作にも備え、SSEで `revival-video` 以外のphaseを受け取った場合も停止する。「次を表示」はphaseを変えないため対象外
- URLに `?revivalAudio=monitor` がある場合、管理者は敗者復活音声を再生しない。モニタと同じクエリ判定を共通化し、片方だけ挙動が変わらないようにする
- 問題投入: GAS直送が基本だが、**貼り付け投入UI(テキストエリア+結果表示)**も作る(§3.5.5の代替手段。GASが使えない事態の保険)。最終投入日時と件数を表示
- 画像投入パネルは初回表示時に `GET /api/admin/images` を呼び、投入済み画像のファイル名・サイズ・更新日時を常に表示する。敗者復活動画は一覧APIを増やさず、初回表示時に認証不要の `/videos/revival.mp4` へ `HEAD` を送り、200なら現在の動画として表示する。どちらも未投入の場合は「まだ無い」ことが分かる文言を表示する
- エラー表示は `error.code` で分岐し、**ユーザーに見せる日本語文言はフロントが持つ**(`message` は表示に使わない)
- 現在モニタに映っている内容のプレビュー表示
- `CurrentStatus` の外観は [Figma「出題中の問題」パネル](https://www.figma.com/design/5H6rnQnOXO2Xk3xhKGVTOV?node-id=525-5682) に合わせる。最大幅440px・角丸24pxの白いカードに、24pxの紺色見出し、16pxの状態バッジ、12pxの詳細欄を配置する。既存の色・書体トークンを使用し、「第何問」「公開状況」「未公開」の表示も残す。長文ではカードを縦に伸ばし、狭い幅では見出しとバッジを折り返す。
- `SelectedQuestion` の外観は `CurrentStatus` と同じ角丸カード(最大幅440px・角丸24px)を流用するが、状態バッジは出さず、見出しは「選択中の問題(詳細)」とする(`ShowQuestionForm` の見出し「選択中の問題」と区別するため)。制限時間はAPI(`GET /api/admin/questions/:id`)のレスポンスに含まれないため表示しない。ID・問題形式・難易度・問題文(区切りを保ったまま)・問題画像・選択肢(画像含む)・正答を並べ、未選択・取得中は文言のみ、取得失敗は文言と「もう一度取得する」ボタンを表示する。

## 8. モック開発

バックエンド完成を待たず、仕様書のJSON実例をそのままモックデータにして画面を作る(固定stateを流すダミーSSE、または `msw`)。**仕様書に書かれたJSONと1文字も違わない形**で作ること(ずれるとバック結合時に全部やり直しになる)。
