# バックエンド実装要件

> `docs/API仕様書.md`(契約)には書かない、**バック側の実装で守るべきこと・決定済みの実装方針**をまとめたもの。
> 契約(JSONの形・エンドポイント)と食い違ったら仕様書が正。ここは「仕様書をどう実現するか」の側。

## 1. データ設計 — hayaoshi の「予約席」を最初から確保する

hayaoshi は v1 未実装だが、**データの形だけは最初から対応**しておく(後からnullable化するとDB制約・検証・フロント型の全層に波及するため):

- `choices` は**空配列を許容**する設計にする(DB制約・GORMモデル・検証すべて)
- `correctChoiceId` は **NULL許容**にする
- そのうえで v1 の投入バリデーションでは `type=hayaoshi` を `SYNC_VALIDATION_ERROR` で**明示的に弾く**(黙って通して壊れる状態を作らない)。フェーズ2でこの1行を外すのが「早押し解放」になる

## 2. 投入バリデーション(§3.5)の実装一覧

エラーは1件で止めず**全行分を `details` に集めて**返す。type別ルール:

| type | choices数 | correctChoiceId | 追加ルール |
|---|---|---|---|
| four_choice | 4 | choicesに存在必須 | — |
| two_choice | 2 | 同上 | — |
| arunashi | 2 | 同上 | `text` が書式 `ラベル:項目/項目`(ラベル区切り=コロン `:`、項目区切り=スラッシュ `/`)に従うこと。コロンが無い/ラベルが空/項目が0個 はエラー。一次チェックはGAS、サーバーも二重チェック |
| hayaoshi | 0(空配列) | null | **v1では一律エラー**(未対応メッセージ)。フェーズ2解放後は **`textSegments` が2要素以上であること**を必須にする(=スプシの問題文に `/` 区切りが入っていること。区切りのない早押しは全文が一度に出てしまい成立しないため、入稿時に弾く) |

共通: number重複 / textSegments空 / 型違い / questionsが空配列(→`INVALID_REQUEST`)。
このバリデーション群は**HTTPもDBも触らない純粋関数**として書く(テーブル駆動テストの好対象。メンバータスクに切り出せる)。

## 3. show-question の制限時間(§3.1)

- 省略時デフォルト **30秒はサーバーの定数**として持つ(フロントに持たせない)
- 受付範囲は **5〜120秒**。範囲外・数値以外は 400 `INVALID_REQUEST`

## 4. 配信の出し分け(§2.2 / §5)— サーバーで抜く

- 宛先別(管理者/monitor/phone)に**レスポンス用の構造体を分けて**組み立てる。「クライアントで隠す」は禁止 — **送らなかったものだけが安全**
- question フェーズ中、閲覧者向けには正解情報のキー自体を入れない(`answer: null`)
- (フェーズ2)hayaoshi のとき phone向けの `textSegments` は常に空配列
- キーは消さない原則: 値が無いときは `null` / `[]` で、宛先内のキー構成を常に一定に保つ

## 5. SSE 基盤

- 接続中クライアントの一覧を持つブロードキャスタを1つ(goroutine + channel)。**バックエンドリーダー+まとめ役のペア設計タスク**
- `ping` は**30秒ごとに必ず**流す。理由: 経路上のCloudflareが無通信約100秒で切断するため。忘れると「ローカルでは動くのに本番だけ動かない」事故になる(→ dev_policy/インフラ・デプロイ_policy.md)
- 状態変更API成功のたびに全宛先へ `state` を配信(宛先ごとに§4の出し分け適用)
- nginx側の `proxy_buffering off` が必要(本番構成の話だが、SSEが動かない時の容疑者として覚えておく)

## 6. 認証(§0)

- 実装はミドルウェア1つ: `Authorization: Bearer` の値が環境変数と一致するか毎リクエスト照合。セッション・DBは使わない
- 環境変数: `ADMIN_TOKEN`(管理者API全部)/ `IMPORT_TOKEN`(問題投入のみ。ADMIN_TOKENでも可)
- SSE管理者チャンネルのみ `?token=` クエリを照合
- `GET /api/admin/verify` は「トークン照合して `{ "ok": true }` を返すだけ」の最小実装でよい

### トークン運用ルール(実装ではなく当日運用。deploy.md にも転記予定)

1. トークンは長いランダム文字列で発行(推測できる単語は禁止)
2. 本番用は直前に発行し、イベント終了後に無効化(使い捨て)
3. 開発用と本番用は別の値

## 7. GAS まわり

- GASコードのコピーを **`tools/gas/` にコミット**し、Googleサーバー上のコードを更新したら必ず同期する(秘伝スクリプト化の防止)
- サーバーURL・トークンはGASのスクリプトプロパティに置く(コード直書き禁止)
- 投入APIは**冪等**(同じ内容を何度送っても同じ結果)を保証する — 全置換方式なので自然に満たせるが、テストで確認する

## 8. 静的画像(§6)

- `GET /images/...` で認証なし配信
- 投入時に参照先ファイルの存在チェックを行い、無ければ `warnings`(取り込みは成功させる)

## 9. その他の実装原則

- エラーレスポンスの `message` は開発者向けで自由に変えてよいが、**`code` は契約**(フロントが分岐に使う)。codeの追加・変更は仕様書を先に直す
- 日時はサーバー側で必ずタイムゾーン付きISO 8601で出力する(`time.Time` のJSON化の設定を最初に固める)
- EventState はDBに永続化し、サーバー再起動後も進行が復元できること(当日の障害復帰要件 → インフラpolicy I3)
