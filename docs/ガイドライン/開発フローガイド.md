# 開発フローガイド — この順にやれば開発が回る

**開発する人が読む手順書。** Issueを割り当てられてから、コードが `main` に入るまでを時系列で並べてある。
**上から順にそのとおりやれば、それで正しい。** 迷ったら考えずにこの順で進める。

| 読むもの | いつ読むか |
|---|---|
| [`Git入門.md`](../入門/Git入門.md) | Gitそのものが分からないとき。**先に読む** |
| **このファイル** | **開発するとき。常に開いておく** |
| [`レビューガイド.md`](./レビューガイド.md) | 自分がレビューする側になったとき |
| [`GitHub運用ガイド.md`](./GitHub運用ガイド.md) | 「なぜこのルールなのか」を知りたいとき |

---

## 全体像

```
① Issueを受け取る
      ↓
② main を最新にして、自分のブランチを切る
      ↓
③ コードを書く(commit は何回でもOK)
      │
      │   ┌─────────────────────────────────────────┐
      ├──▶│ 途中で作業を止めるとき                   │
      │   │   commit → push → Draft PR を作る(④)  │──┐
      │   └─────────────────────────────────────────┘  │
      │        ↑ 再開したら、同じブランチで③に戻る ─────┘
      ↓
⑤ 完成させて「Ready for review」にする
      ↓
⑥ CI(自動チェック)が緑になるまで直す
      ↓
⑦ レビューの指摘に対応する
      ↓
⑧ approve が付いたら、PMがマージする
      ↓
⑨ 後片付けをして、①へ戻る
```

**「PRは完成してから出す」ではない。** 作業を中断するたびにDraft PRを作っておき、完成したらそれを Ready に切り替える。これがうちの流れ。

---

## ① Issueを受け取る

**Issue = やることリストの1項目。** GitHubの「Issues」タブにある。

### Issueに書いてあること

| 項目 | 何が書いてあるか |
|---|---|
| ①ゴール | 完成した状態。画面の文言やレスポンスのレベルまで具体的に |
| ②触ってよいファイル | どのフォルダを編集するか |
| ③写経元・参考 | 真似できる既存コード、`docs/API仕様書.md` の該当節 |
| ④動作確認方法 | どうなったら完成か(curlコマンド、開く画面) |

**ここに書いていないことは、やらなくてよい。** 「ついでにあそこも直そう」はしない。

**④は必ず読む。** これが後で**PRに貼る証拠の内容そのもの**になる(→ ⑤-2)。

### ラベルの見方

| ラベル | 意味 |
|---|---|
| `good first issue` | 1ファイルで完結。見本をコピーして作れる。**最初の1個はこれから** |
| `easy` | 1つのfeatureフォルダ内で完結。設計の判断は不要 |
| `hard` | 複数箇所にまたがる/設計を含む。PM・リーダーが担当 |

領域ラベル(`frontend` / `backend` / `infra` / `docs`)で自分の担当を絞り込める。
**ラベルはPMが起票時に付ける。** 自分で付ける必要はない。

### やることリストに載せる

Issueを受け取ったら、**右側の Assignees に自分を入れる。**
**これが「私がやっています」の唯一の合図**で、作業の重複を防ぐ。

## ② ブランチを切る

**必ず、最新の `main` から切る。**

```bash
git switch main
git pull                                  # ← これを忘れると後で面倒になる
git switch -c feat/12-monitor-question-view
```

### ブランチ名の付け方

`種類/issue番号-短い説明` の形。

| 種類 | 使う場面 | 例 |
|---|---|---|
| `feat/` | 機能を追加する | `feat/12-monitor-question-view` |
| `fix/` | バグ・不具合を直す | `fix/34-timer-drift` |
| `docs/` | ドキュメントだけ変える | `docs/agents-md-update` |

- **Issueがあれば番号を入れる**(ブランチ名からIssueに辿れる)
- Issueを立てずに直す小さな修正なら、**番号は無くてよい**
- 説明部分は英数字とハイフン。日本語は避ける

**1ブランチ = 1 Issue = 1 PR。** 1つのブランチに複数のIssueの作業を混ぜない。

## ③ コードを書く

### 守るのは3つだけ

1. **新しい機能は新しいフォルダに作る**(フロント: `frontend/src/features/`、バック: `backend/internal/`)
2. **API仕様を変えるときは、先に [`API仕様書.md`](../実装要件/API仕様書.md) を直す**
3. **Issueに書かれていないことはやらない**

### コミットは気軽に

ブランチの中では何回コミットしてもよい。メッセージは**日本語1行**でよい。
うちは squash merge なので、**ブランチの中のコミットは `main` に残らない**。きれいに作ろうと気負う必要はない。

```bash
git add .
git commit -m "モニタの出題画面に選択肢の2×2配置を追加"
```

## ④ 作業を中断するとき — Draft PRにする(重要)

### ルール

> **その日の作業をやめるとき・数日空けるときは、`commit` → `push` → Draft PR を作るところまでやる。**

**完成していなくても出す。** これはうちの運用で一番守ってほしい習慣。

手元でコミットしただけの状態は**世界の誰からも見えない**(→ [`Git入門.md`](../入門/Git入門.md) §2)。この状態で止まると、PCが壊れたら消え、進捗が誰にも見えず、方向性が間違っていても完成するまで気づけない。
Draft PRなら**レビュワーに迷惑をかけずに**それを全部防げる。Draftは「まだ見なくていいですよ」という公式の合図なので、出しっぱなしで放置しても誰も困らない。

(なぜここまで徹底するのかの詳しい理由 → [`GitHub運用ガイド.md`](./GitHub運用ガイド.md))

### 手順1: コミットする

```bash
git add .
git commit -m "モニタ画面の選択肢の枠まで作った(途中)"
```

途中なので、メッセージは**「どこまでやったか」を自分向けに書けば十分**。

### 手順2: GitHubへ送る

```bash
git push -u origin feat/12-monitor-question-view
```

`-u origin ブランチ名` が必要なのは**そのブランチの初回だけ**。2回目以降は `git push` だけでよい。

### 手順3: GitHubの画面でDraft PRを作る

1. ブラウザで https://github.com/NUTFes/quizApp を開く
2. 画面上部の**黄色い帯**の中にある **「Compare & pull request」** という緑のボタンを押す
   - 帯が出ていない場合 → 上のタブの **「Pull requests」** → 緑の **「New pull request」** → `base: main` ← `compare: 自分のブランチ名` を選ぶ
3. タイトルと本文を書く(テンプレートが自動で入っている)
   - **途中なので全部埋めなくてよい。** 「やったこと」に今どこまでできているかを2〜3行書けば十分
   - `closes #12` は書いておく
4. ここが重要 → 一番下の緑のボタン **「Create pull request」の右にある ▼** をクリックする
5. ドロップダウンから **「Create draft pull request」** を選ぶ
6. ボタンの表示が **「Draft pull request」** に変わるので、それを押す

PRのタイトルの横に**灰色の「Draft」バッジ**が付いていれば成功。

> **コマンドでやる場合**(慣れてきたら)
> `gh pr create --draft` の1行で同じことができる。

### 2回目以降 — 再開して、また中断するとき

**PRを作り直す必要はない。** 一度Draft PRを作ったら、同じブランチにpushするだけで**PRの中身は自動で最新になる**。

```bash
git switch feat/12-monitor-question-view    # 再開

# ── コードを書く ──

git add .
git commit -m "選択肢の2×2配置まで完成"
git push          # ← これだけ。PRは勝手に更新される
```

### Draft PRのよくある疑問

**Q. Draftのうちに見てもらいたいときは?**
見てもらってよい。**Draftは「レビューしなくてもいい」であって「見てはいけない」ではない。** PRのコメント欄やSlackで「Draftですが、この方針で合ってますか」と一声かければいい。**初心者ほど早めにこれをやったほうがいい。**

**Q. Draftでも CI は走る?**
走る。**途中なので赤くてもまったく問題ない。** Ready for review にするまでに緑にすればいい。

**Q. 中途半端なコードを上げるのが恥ずかしい**
`main` には一切影響しないので、何を上げても壊れない。**むしろ途中経過が見えるほうがチームは安心する。**

**Q. 結局作らないことにしたPRは?**
PRページ下部の **「Close pull request」** で閉じればよい。

## ⑤ PRを完成させる

ここが**一番大事な章**。この章のとおりにやれば、レビューが12時間で返ってくる。

### なぜPRを丁寧に書くのか

うちのレビュワー4人のうち、**2人は開発環境を持っていない**(レビュー専門の経験者)。
つまりその2人は、**あなたのコードを手元で動かして確かめることができない。**

> **「本当に動くこと」を証明する責任は、PRを出す側にある。**

レビュワーが手元で動かす前提には立たない。**あなたが動かした証拠をPRに貼る。**
あなたは既に自分の環境で動かしているはずなので、**その画面をスクショするだけ**。追加作業はほとんどない。

### ⑤-1. 出す前の確認(3分)

**Issueの④動作確認方法を読み返す。**

**余計な変更が混ざっていないか確認する。**

```bash
git status      # 変更したファイルの一覧
git diff main   # main との差分を全部見る
```

Issueに関係ないファイルが混ざっていたら元に戻す。**「ついでに直した」はPRを分ける。**

**動くことを自分で確認する。**

```bash
mise run up     # 起動していなければ
```

Issueの④に書かれた手順を、**実際に自分で最後までやる**。ここで動かなければ、まだPRを出す段階ではない。

### ⑤-2. 動作確認の証拠を用意する ← ここが核心

#### 画面(フロントエンド)を変更した場合 → スクショ

**before / after の2枚**を撮る。

| 撮るもの | どうやって |
|---|---|
| before | 変更前の画面。撮り忘れたら `git stash` で一時的に戻して撮る |
| after | 変更後の画面 |

**スクショの撮り方**

| 環境 | 操作 |
|---|---|
| Windows | `Win` + `Shift` + `S` → 範囲を選択 → クリップボードにコピーされる |
| Mac | `Cmd` + `Shift` + `4` → 範囲を選択 → デスクトップに保存される |

**貼り方**: PRの本文の入力欄に、**そのまま貼り付け(Ctrl+V / Cmd+V)かドラッグ&ドロップ**。GitHubが自動でアップロードして画像として表示してくれる。ファイルをリポジトリに置く必要はない。

> **動きのあるもの(演出・タイマーなど)を見せたいとき**
> スクショを2〜3枚並べて「この順に変わります」と書けば十分。動画は不要。

#### API(バックエンド)を変更した場合 → `curl` の結果

**コマンドと、返ってきた結果の両方**を貼る。

```bash
curl -s http://localhost:3000/api/health
```

実行して、**打ったコマンドと出力をコピーして**、PRにこう貼る:

````
```bash
$ curl -s http://localhost:3000/api/health
{"status":"ok"}
```
````

バッククォート3つ(```)で挟むと、コードとして見やすく表示される。

**確認すべきこと**(Issueに指定がなければこの3つ):

1. 正常なリクエストで、期待どおりのJSONが返るか
2. [`API仕様書.md`](../実装要件/API仕様書.md) に書かれたとおりの**フィールド名**になっているか
3. わざと間違ったリクエストを送ったとき、仕様どおりのエラーが返るか

#### ドキュメントだけを変更した場合

証拠は不要。差分がそのまま内容なので、本文に「何を・なぜ変えたか」を書けばよい。

### ⑤-3. PR本文を埋める

テンプレートが自動で入っているので、上から埋める。

**「やったこと」**

- 何を作ったか / 直したかを**2〜3行**
- **`closes #12`** と書く(数字は自分のIssue番号)。マージ時にIssueが自動で閉じる

**「動作確認方法」**

⑤-2で用意した証拠をここに貼る。加えて、**環境がある人が追試できる手順**も1〜2行:

```
mise run up してから http://localhost:5173/monitor を開く
```

**「チェックリスト」**

自分で確認して `[x]` にする。

- [ ] 手元で動作確認した
- [ ] API仕様を変えたなら `docs/API仕様書.md` を先に直した

**嘘をつかない。** 確認していないなら空欄のままにして、その旨をコメントに書く。空欄は「まだ」の合図として機能するので問題ないが、確認していないのにチェックすると、レビューの前提が崩れる。

**タイトル**

**「何をしたか分かる日本語1行」。** これがそのまま `main` の履歴に残るので、ここだけ少し丁寧に書く。

| 良い例 | 悪い例 |
|---|---|
| モニタの出題画面に選択肢の2×2配置を追加 | 修正 |
| タイマーの端末時計ズレを serverTime で補正 | fix bug |
| 問題取得APIに `type` フィールドを追加 | いろいろ変更しました |

### ⑤-4. Ready for review にする

PRページの **「Ready for review」** ボタンを押す。**これが「レビューお願いします」の合図。**

### ⑤-5. レビュー依頼

**レビュワーは自動で指名される。** `.github/CODEOWNERS` の設定により、変更した場所に応じて自動でレビュー依頼が飛ぶ。自分で誰かを選ぶ必要はない。

| 変更した場所 | 自動指名される人 |
|---|---|
| `frontend/` | PM + ともちゃん |
| `backend/` | キンギョ + みゆちゃん |
| `docs/` | PM |
| その他(設定ファイルなど) | ともちゃん + みゆちゃん |

2人指名されるが、**approve は1件で通る**。早く見られるほうが見る。

**12時間たっても反応がなかったら、遠慮せず催促してよい。**
うちのレビューの約束は「**平日12時間以内に一次反応**」。開発期間が短いので、待つコストのほうが高い。Slackで「PR #23 のレビューお願いします」と一声かける。**催促は失礼ではなく、正しい行動。**

### ⑤-6. PRの大きさ

**目安: 差分400行を超えたら、分割できないか相談する。**

上限ではなく相談のトリガー。大きくなりそうだと分かった時点で、**Issueを先に分割する**のが正しい対処。作り終わってからは分けにくい。

## ⑥ CI(自動チェック)を緑にする

PRを出すと、GitHub上で自動チェックが走る(数分)。**緑のチェックマークが付けばOK。**

赤くなったら、その表示をクリックするとログが見られる。「どのファイルの何行目が何の違反か」が書いてある。直して push し直せば、自動でもう一度走る。

> **CIに落ちるのは恥ずかしいことではない。** `main` を壊さずに済んだ成功例。全員落ちる。

## ⑦ 指摘に対応する

### コメントの読み方 — prefix で強度が分かる

| prefix | 意味 | どうする |
|---|---|---|
| `must:` | 直さないとマージできない | **直す** |
| `imo:` | こうしたほうがいいと思う(提案) | 任意。直さなくてよい |
| `ask:` | 質問。意図が知りたいだけ | **返事だけでよい**。直す必要はない |
| `good:` | ここ良いですね | 何もしなくてよい |

**prefix が付いていないコメントは `imo:`(任意)として読んでよい。**
つまり、**必ず直さないといけないのは `must:` だけ。** 全部の指摘に応えなければ、と思う必要はない。

### 直したら

1. コードを直して `git add` → `git commit` → `git push`(PRは自動で更新される)
2. **指摘のコメントに一言返す。**「直しました」だけでよい
3. PRページ右上の Reviewers の横にある **🔄 マーク(Re-request review)** を押す。これが「もう一度見てください」の合図

### 納得できないときは反論してよい

**レビュワーが仕様を誤解していることは普通にある。** 特に経験者2人は開発に参加していないので、`docs/API仕様書.md` や `docs/画面・要件.md` の中身を把握していない。

「仕様書の§4にこう書いてあるので、これで合っています」と根拠を示して返せばよい。**言い返すことは失礼ではない。**

### 3往復ルール

> **同じ論点でコメントが3往復を超えたら、テキストで粘らずに通話するか、PMを呼ぶ。**

テキストの往復は時間がかかるうえに、お互い険悪になりやすい。3往復して噛み合わないのは、**たいてい前提がずれているだけ**で、5分話せば解決する。
言い出すのはどちらからでもよい。

---

## ⑧ マージ

**approve が付いたら、マージするのはPM。** あなたはマージボタンを押さなくてよい。

- approve するのはレビュワー(PM・リーダー・経験者2人)
- 最終的に `main` へ入れる操作はPMが行う
- `must:` が未解決のPRはマージされない

---

## ⑨ 後片付け

マージされるとGitHub側のブランチは自動で削除される。手元も片付ける:

```bash
git switch main
git pull
git branch -d feat/12-monitor-question-view
```

そして①に戻る。

## 提出前の最終チェック(慣れたらここだけ見ればよい)

- [ ] Issueに関係ない変更が混ざっていない
- [ ] 手元で動かして、Issueの④動作確認方法を最後までやった
- [ ] **証拠を貼った**(画面ならbefore/afterスクショ、APIなら`curl`のコマンドと結果)
- [ ] `closes #番号` を書いた
- [ ] タイトルが「何をしたか分かる日本語1行」になっている
- [ ] API仕様を変えたなら `docs/API仕様書.md` を先に直した
- [ ] Draftを Ready for review に切り替えた

## よくあるNGと直し方

| NG | なぜダメか | どうする |
|---|---|---|
| 証拠が「動作確認しました」の一文だけ | 環境を持たないレビュワーが判断できない | スクショか `curl` 結果を貼る |
| スクショがafterだけ | 何が変わったのか分からない | beforeも撮る(`git stash` で戻せる) |
| Issueと関係ない修正が混ざっている | レビューの範囲が分からず、差し戻しにくい | PRを分ける |
| 差分が1000行ある | レビュワーが読みきれない | 400行を目安に相談(→ ⑤-6) |
| タイトルが「修正」 | 履歴に残るので後から誰も分からない | 何をしたか1行で書く |
| レビューが来ないまま3日放置 | 締切が近づくだけ | **12時間で催促する** |
| 完成するまでpushしない | PCが壊れたら消える。進捗も見えない | **中断のたびにDraft PR(→④)** |

## 困ったときの早見表

| 状況 | どうするか |
|---|---|
| **今日の作業を終える / しばらく空ける** | **`commit` → `push` → Draft PR まで作る(→ ④)** |
| 作業を再開する | `git switch 枝名` で戻るだけ。PRは作り直さない |
| `main` で作業してしまった(コミット前) | `git switch -c 枝名` で変更ごと枝へ移せる |
| `main` でコミットしてしまった | **自力で戻さずPMへ** |
| push が拒否された | `git pull` してから `git push` |
| コンフリクトが出た | → [`Git入門.md`](../入門/Git入門.md) §5。分からなければ触らずに相談 |
| CIが赤い | ログをクリックして該当箇所を直し、push し直す |
| レビューが12時間来ない | **遠慮せず催促してよい**(Slackで一声) |
| `must:` と `imo:` の違いが分からない | → ⑦ |
| 議論が3往復して噛み合わない | テキストをやめて通話するかPMを呼ぶ |
| 30分詰まった | **質問する。これはルール。** |

## 最初の1周の練習

いきなり本番のIssueに入る前に、**練習用のIssue**を用意してある(READMEに自分の名前を追加するだけの内容)。
**全員、開発開始前にこれで1周する。** ①〜⑨を一度通しておけば、本番のIssueでは中身だけに集中できる。
