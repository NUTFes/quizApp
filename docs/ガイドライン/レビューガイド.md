# レビューガイド — レビューする側の手引き

**レビューをする人が読む。** PRを出す側の手順は [`開発フローガイド.md`](./開発フローガイド.md) にある。

---

## 0. レビューの目的 — 何のためにやるのか

**間違い探しではない。** 目的は2つだけ。

1. **`main` を壊さない** — 動かないコードが入ると、全員の手元が止まる
2. **書いた人以外にも読めるコードにする** — 本番直前に「これ誰も分からない」を作らない

そして、うちは**ほぼ初心者チーム**。だからもう1つ大事な前提がある。

> **レビューは教育の場でもあるが、和やかな雰囲気で**
> 指摘の数より、「次もPRを出そう」と思える状態で返すことのほうが優先度が高い。

---

## 1. 誰が何をレビューするか

### レビュワーは自動で指名される

`.github/CODEOWNERS` により、変更された場所に応じて自動でレビュー依頼が飛ぶ。

| 変更された場所 | 指名される人 |
|---|---|
| `frontend/` | PM + ともちゃん |
| `backend/` | キンギョ※ + みゆちゃん |
| `docs/` | PM |
| その他(設定ファイルなど) | ともちゃん + みゆちゃん |
※キンギョはほかにもタスクあると思うので、仮置きで、余裕あったらレビューもお願いする形です。

**2人指名されるが、approve は1件で通る。** 早く見られるほうが見ればよく、両方が見る必要はない。
自分が指名されたPRを他方が既にapproveしていたら、見なくてよい。

### 立場によって見る範囲が違う

うちのレビュワーは2種類いる。**同じものを見る必要はない。**

| レビュワー | 立場 | 主に見る観点 |
|---|---|---|
| PM / キンギョ | 開発に参加。仕様を細かいとこまで把握している | **②仕様どおりか** を中心に、①③も |
| ともちゃん / みゆちゃん | 開発に基本は参加しない。わからない仕様はPM、キンギョに相談 | **①動くか ③読めるか**。②は無理に見なくてよい |

**経験者2人へ:** `docs/API仕様書.md` や `docs/画面・要件.md` を読み込んでいないと分からない部分は、**飛ばしてよい**。「仕様と合っているかは分かりません」とコメントに書いて、それ以外の観点でapproveして構わない。仕様の整合はPMとリーダーが見る。

**全部を完璧に見ようとしないでほしい。** レビューが重くなって止まるほうが、チームにとって損失が大きい。

---

## 2. 何を見るか — 観点は3つだけ

### ① 動くか

- 明らかなバグ、条件の書き間違い、nullになりうる値の扱い漏れ
- **PRに貼られた証拠**(スクショ / `curl`の結果)が、Issueのゴールを満たしているか

### ② 仕様どおりか(仕様を把握している人のみ)

- [`API仕様書.md`](../実装要件/API仕様書.md) の契約(フィールド名・型・エラーコード)と合っているか
- [`画面・要件.md`](../実装要件/画面・要件.md) の仕様と合っているか
- **仕様を変える変更なのに、仕様書が直っていない** → これは `must:`

### ③ 他の人が読めるか

- 変数名・関数名から中身が想像できるか
- 置き場所が正しいか(新機能が `features/` や `internal/` の新フォルダに入っているか)
- 極端に複雑になっていないか

---

## 3. 何を見ないか(重要)

> **書式の指摘はしない。それはCIの仕事。**

インデント、クォート、改行位置、セミコロン。**これらは人間が指摘してはいけない。**

理由は [`CI・コードチェック入門.md`](../入門/CI・コードチェック入門.md) にあるとおり:

> 機械的に判定できることは全部機械にやらせて、人間のレビューは「動くか・設計がいいか」だけに集中させる

書式の指摘は、**レビュワーの時間を奪い、受け手を萎縮させ、しかも本当に見るべき問題から目をそらす**。
今回はこちらはlint に任せてしまいましょう。

同じく見ないもの:

- **好みの問題**(「自分ならこう書く」レベル) → どうしても言いたければ `imo:` を付ける
- **Issueに書かれていない改善要望** → 別Issueとして起票する。そのPRでやらせない

---

## 4. 動作確認はどこまでやるか

**レビュワーが手元で動かすのは任意。しかし、基本的には動かそう。**

- **動くことの証明は、PRを出す側の責任。** 証拠(スクショ / `curl`結果)をPRに貼るのが必須
- **レビュワーの実機確認は任意。** 環境がある人(PM・リーダー)が、余力があるときや疑わしいときだけやる

**証拠が貼られていなかったら、それ自体を指摘する。**

```
must: 動作確認の証拠(スクショか curl の結果)を貼ってください。環境が無いと動きを確認できません
```

これは厳しい指摘ではなく、**ルールとして決まっていること**([`開発フローガイド.md`](./開発フローガイド.md) ⑤-2)。遠慮なく書いてよい。

## 5. コメントの書き方

### prefix を必ず付ける

| prefix | 意味 | 相手の対応 |
|---|---|---|
| `must:` | 直さないとマージできない(バグ・仕様違反・証拠なし) | 直す |
| `imo:` | こうしたほうがいいと思う(提案) | 任意 |
| `ask:` | 質問。意図が知りたいだけ | 返事だけ |
| `good:` | ここ良いですね | なし |

**prefix の無いコメントは `imo:`(任意)として読まれる。** 必ず直してほしいものには、**忘れずに `must:` を付ける。**

### `must:` は本当に必要なものだけ

`must:` が5個も6個も付いたPRは、初心者にとっては「全部やり直し」に見える。
**バグと仕様違反以外は `imo:` で十分。** 好みや細かい改善は、いま直させなくてもプロジェクトは進む。

### `good:` を使う

初心者チームでは意識的に使ってほしい。**指摘だけが並ぶPRは、内容が正しくても人が続かない。**
これは余力あるとき、、、と言いたいけど積極的に！

```
good: エラーハンドリングまで書かれていて安心しました
good: フォルダの切り方が仕様どおりで読みやすいです
```

1つでいい。指摘の前に1つ入れるだけで、受け取り方がまったく変わる。

### 書き方の原則

| 原則 | 悪い例 | 良い例 |
|---|---|---|
| **人ではなくコードに向ける** | なんでここでこう書いたんですか | `ask:` この分岐はどういうケースを想定していますか |
| **理由を書く** | `must:` ここ直してください | `must:` `timeLimitSec` がnullの問題で落ちます。`?? 0` が要りそうです |
| **代案を出す** | `imo:` 読みにくいです | `imo:` この処理を関数に切り出すと読みやすいかもしれません |
| **断定しない** | これは間違っています | 私の理解だとここは〜になるはずですが、どうでしょう |

初心者相手だと、**「なぜダメか」を書かない指摘は、直せないうえに自信だけ削る。** 理由をひとこと添える。

## 6. レビューの手順(GitHubの操作)

1. PRのページを開き、**「Files changed」** タブを押す(変更された行だけが表示される)
2. 気になる行の左端に出る **青い「+」** を押すと、その行にコメントできる
3. コメントを書いて **「Start a review」**(2件目以降は「Add review comment」)
   - ここで「Add single comment」を選ぶと**1件ずつ即座に通知が飛ぶ**。まとめて送りたいので「Start a review」を使う
4. 全部見終わったら、右上の **「Review changes」** ボタンを押す
5. 総評を書いて、3つから選んで送信

| 選択肢 | いつ使うか |
|---|---|
| **Approve** | マージしてよい。`imo:` だけ残っていてもApproveしてよい |
| **Request changes** | `must:` があり、直してもらう必要がある |
| **Comment** | 質問だけ、または「仕様は分からないので他の人お願いします」のとき |

### Approve の基準

**完璧である必要はない。** 基準はこれだけ:

> **`main` に入っても壊れず、後から読める状態か。**

`imo:` の提案が残っていても Approve してよい。**「もっと良くできる」と「マージできない」は別。**

---

## 7. 期限 — 平日12時間以内に一次反応

開発期間が短いため、**依頼から平日12時間以内に何らかの反応をする。**

「一次反応」でよい。全部見終わっていなくてもよい。
気づいた人は遠慮なくslack で PM をメンションして。気づいてないだけの可能性がある。

- 見終わったなら Approve か Request changes
- 見る時間が取れないなら、**「今日は難しいので明日の朝見ます」の一言でよい**

**沈黙が一番良くない。** 出した側は、見られているのか忘れられているのか分からないまま待ち続けることになる。

12時間を過ぎたら**催促されるのが正常**。催促されても気にしなくてよいし、催促する側も遠慮しなくてよい。

---

## 8. 議論が長引いたら — 3往復ルール

> **同じ論点でコメントが3往復を超えたら、テキストで粘らずに通話するか、PMを呼ぶ。**

3往復して噛み合わないのは、**たいてい前提がずれているだけ**。5分話せば解決することが多い。
テキストの往復は時間がかかるうえ、お互い険悪になりやすい。

言い出すのはどちらからでもよい。

---

## 9. 反論されたら

**PRを出した側は、納得できなければ反論してよい**とガイドラインに書いてある([`開発フローガイド.md`](./開発フローガイド.md) ⑦)。

特に経験者2人は仕様書を把握していないので、**「仕様書にこう書いてあるので合っています」と返されることは普通に起きる。** それは正しいやりとりであって、失礼ではない。

根拠を示されたら素直に取り下げる。「なるほど、了解です」で終わってよい。

---

## 10. マージ

**マージするのはPM。** レビュワーは Approve までで、マージボタンは押さない。

- approve 1件 + CI緑 が揃った時点で、PMがマージする
- `must:` が未解決のPRはマージされない
- マージ後、ブランチは自動削除される

---

## 11. まとめ — レビュワーが覚えること

1. **観点は3つだけ**(動くか / 仕様どおりか / 読めるか)。**書式は見ない**
2. **仕様が分からない部分は飛ばしてよい。** 完璧に見ようとしない
3. **prefix を必ず付ける。** `must:` はバグと仕様違反だけ
4. **`good:` を1つ入れる**
5. **12時間以内に一次反応。** 見られないなら「明日見ます」でよい
6. **3往復したら通話**
