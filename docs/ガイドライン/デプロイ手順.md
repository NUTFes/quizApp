# デプロイ手順

本番(オンプレの Proxmox CT)にアプリを載せる手順書。方針の背景は
`dev_policy/インフラ・デプロイ_policy.md` を参照。ここは**手を動かす順番だけ**を書く。

> ⚠️ **当日はこのファイルを印刷して持つこと。** ネットワークが落ちた時、
> 手順書がブラウザの中にしかないと詰む。

---

## 0. 用語と前提

| 言葉 | 意味 |
|---|---|
| **ホスト** | Proxmox 本体。PVE の GUI で「>_ Shell」を開いた先 |
| **CT** | この上に作ったコンテナ。アプリはこの中で動く |
| **CTに入る** | ホストの Shell で `pct enter <VMID>` |

現在の構成:

> 🆕 本番と練習環境は**別々の物理 Proxmox ホスト**にある(ディスクを共有しない)。
> そのため両方を恒久的に並存させる運用にしている(→ `dev_policy/インフラ・デプロイ_policy.md`)。

```
本番(組織の Cloudflare に合流)        練習環境(自分たちのトンネル)
Cloudflare(運用者管理)                Cloudflare(自分たちのアカウント)
   │ quiz.○○○.jp                       │ quiz.pakuon.com
   ▼                                    ▼
Proxmox CT(本番ホスト)── ポート 8080  Proxmox CT(練習ホスト・pve03)
   │                                    └─ cloudflared ── 中から外へ繋ぐ
   ├─ frontend (nginx)  /     → ビルド済み静的ファイル
   │                    /api/ → backend へ中継(SSE用設定込み)
   ├─ backend  (Go)
   └─ db       (PostgreSQL)
```

どちらも同じ `docker-compose.prod.yml` を使う。練習環境は `.env.prod` に
`STG_CF_TUNNEL_TOKEN` を書くことで `docker-compose.stg-tunnel.yml` が重なり、
`cloudflared` が1つ増えるだけの違い。→ 「2.5 練習環境を外から見えるようにする」

> **SSH は現時点で使えない。** 校内ネットワークの外から SSH が通らず、
> PVE の GUI(Cloudflare Zero Trust 経由)だけが入口。作業はすべて
> ホストの Shell か CT の Console から行う。
> → 運用者に「Zero Trust 経由の SSH 公開」を依頼中(policy Q6)
>
> **2回目以降のデプロイは CT に入らなくてもできる。** CT 上のセルフホストランナーが
> GitHub に繋ぎに行く形の CD を用意した(承認制)。→ 「3.5 GitHub Actions から承認してデプロイする」

## 1. CT を作る(初回のみ)

ホストの Shell で:

```bash
git clone https://github.com/NUTFes/quizApp.git /root/quizApp-infra   # 初回のみ
VMID=202 HOSTNAME=quiz-prod bash /root/quizApp-infra/infra/create-ct.sh
```

スクリプトが事前確認 → CT作成 → Docker導入 → 検証 → 後始末まで行う。
**判定基準はスクリプトの最後に表示される。**特に:

- `Storage Driver` が `overlayfs` または `overlay2` であること(`vfs` なら要相談)
- `lvs` の `data` 行の `Data%` が **85% 未満**であること

通ったらスナップショットを取る:

```bash
pct snapshot 202 base-docker-ok
```

## 2. アプリを載せる(初回のみ)

CT に入る:

```bash
pct enter 202
```

```bash
git clone https://github.com/NUTFes/quizApp.git /opt/quizApp
cd /opt/quizApp
cp .env.prod.example .env.prod
chmod 600 .env.prod
```

`.env.prod` の値を埋める。生成はこれで:

```bash
openssl rand -hex 24      # POSTGRES_PASSWORD
openssl rand -hex 32      # ADMIN_TOKEN
openssl rand -hex 32      # IMPORT_TOKEN
```

> ⚠️ **`openssl rand -base64` は使わない。** `/` や `+` が
> `DATABASE_URL` の区切りとして解釈され、backend が DB に繋げずクラッシュ
> ループする。原因が分かりにくいので必ず `-hex` を使う(2026-08-25 に実際に踏んだ)。

> ⚠️ **ADMIN_TOKEN / IMPORT_TOKEN はイベント直前に発行し、終了後に無効化する。**
> 開発用と同じ値を使わない。ログ・スクショに残さない。
> 管理者画面のパス `/backstage-0248` は秘密ではない。**秘密なのはトークンだけ**。

編集したらデプロイ:

```bash
bash infra/deploy.sh
```

## 2.5 練習環境を外から見えるようにする(初回のみ)

本番は組織の Cloudflare に合流する(policy Q2)が、その依頼が通る前でも
**自分たちのドメインとトンネルがあれば練習環境を外部公開できる**。
CT は外から受信できないが、外への送信は通るため、`cloudflared` が
「中から外へ繋ぎに行って、その通り道で受け取る」形にすればよい。ポート開放も
証明書も要らない。

> 🔴 **`cloudflared tunnel --url` の使い捨てURL(quick tunnel)は使えない。**
> quick tunnel は **SSE 非対応**で、同時リクエストも **200 で頭打ち**になる。
> SSE は1接続がリクエストを開きっぱなしにするので、参加者200人の想定が
> そのまま上限にぶつかる。URL も再起動のたびに変わり QR と相性が悪い。
> **必ず「名前付きトンネル」を使う。**

### ① ドメインを用意する

Cloudflare Registrar で取ると、DNS も同じアカウントに入るので設定が1箇所で済む。
ダッシュボードのドメイン一覧で **Active** になるまで待つ。
`Pending Nameserver Update` のままだと ③ の DNS 登録が失敗する。

### ② トンネルを作ってトークンを取る

Cloudflare の画面は「アカウント全体の設定」と「ドメインごとの設定」が別階層で、
トンネルは前者にある。**ドメインをクリックして入った先には無い。**

1. https://dash.cloudflare.com/?to=/:account/tunnels を開く(左メニューの Networking > Tunnels)
2. **Create a tunnel** → コネクタの種類は **Cloudflared** を選ぶ
   (WARP Connector は社内ネットワーク全体を繋ぐ別物)
3. 名前を付けて保存する。名前は Cloudflare 内部の識別用で URL には出ない。
   環境が分かる名前(`quiz-stg` など)にしておくと本番用を足した時に取り違えない
4. コネクタのインストール画面で **Docker** タブを選ぶ。表示されるコマンドの
   `--token` の後ろの長い文字列がトークン。**これだけをコピーする**

> ⚠️ **画面のコマンドをそのまま実行しないこと。** compose の管理外のコンテナができ、
> CT を再起動しても復帰しない。さらに compose のネットワークに入らないため
> 転送先の `frontend` という名前を解決できず、結局つながらない。
>
> ⚠️ **この画面で Next が押せないのは正常。** コネクタが実際に繋がるまで
> 先に進めない作りなので、先に ③ を済ませる。トンネル自体は保存済みなので、
> 画面を閉じてもトークンは一覧から再表示できる。

### ③ CT 側に書いてデプロイする

```bash
vi .env.prod          # STG_CF_TUNNEL_TOKEN= に貼る
bash infra/deploy.sh
```

`deploy.sh` は `STG_CF_TUNNEL_TOKEN` があれば自動で `docker-compose.stg-tunnel.yml` を重ねる。
起動オプションを覚える必要はない。疎通確認に
`Registered tunnel connection` が出れば接続できている。

> ⚠️ **トークンはパスワードと同じ扱い。** これ1つでこのドメイン宛ての通信を
> 横取りできる。`.env.prod` だけに置き、git にもチャットにも貼らない。

### ④ ダッシュボードに戻ってホスト名を割り当てる

コネクタが **Connected** になったら、トンネルの **Routes** タブで
**Add route** → **Published application** を選び、次を入れて保存する。

| 項目 | 値 |
|---|---|
| Subdomain | `quiz` |
| Domain | 取得したドメイン |
| Service URL | `http://frontend:80` |

DNS の CNAME はここで自動的に作られるので、DNS 画面を手で触る必要はない。

### ⑤ ゾーン側の設定を確認する

**本番で運用者に依頼することになる内容(policy Q3・Q4)を、自分のゾーンで先に確かめておく。**

- **Bot Fight Mode を切る。** チャレンジが出ると `EventSource` は通過できず SSE が全滅する
- **`/api/*` を Cache Rule で Bypass にする。** キャッシュされると全端末が古い状態で固まる
- **「I'm Under Attack」モードは使わない**

無通信100秒での切断は backend の15秒ハートビートで既に防いでいる。

## 3. 2回目以降のデプロイ

> 普段は **3.5 の GitHub Actions からの承認**で行う。ここに書く CT の中での手動実行は、
> ランナーが止まっている時や、CD を設定する前の CT で使う。
>
> ⚠️ **CD を設定した CT では、手動でも `deploy` ユーザーで実行する**
> (`su - deploy -c "REF=main bash /opt/quizApp/infra/deploy.sh"`)。root で実行すると
> `.git` の中に root のファイルができ、次の CD が権限エラーで止まる。

```bash
pct enter 202
su - deploy -c "bash /opt/quizApp/infra/deploy.sh"                                # いまのブランチの最新
su - deploy -c "REF=main bash /opt/quizApp/infra/deploy.sh"                       # ブランチ指定
su - deploy -c "REF=rehearsal-2026-09-01 bash /opt/quizApp/infra/deploy.sh"       # タグ指定
```

> `REF` を省略すると、**CT がいまチェックアウトしているブランチ**をそのまま使う。
> 本番・リハーサルでは省略せず、必ずタグを書くこと。

### 本番・リハーサルは必ずタグを指定する

**デプロイ専用ブランチは作らない**(GitHub Flow を採用しているため。
→ `dev_policy/Git運用・CI_policy.md`)。代わりにタグで固定する。

```bash
# 手元で: デプロイしたい状態に印を付けて push
git tag -a rehearsal-2026-09-01 -m "通しリハーサル用"
git push origin rehearsal-2026-09-01
```

**ブランチはポインタが動くのでタグを使う。**「当日動いていたのはどれか」を後から
100%特定でき、戻すのも `REF=` を1つ前のタグに変えるだけで済む。

いま何が動いているかは CT の中で確認できる:

```bash
cat /opt/DEPLOYED_REF
```

続けてホストの Shell で:

```bash
pct fstrim 202
lvs                       # data 行の Data% を確認(85%未満をキープ)
```

`deploy.sh` がやっていること:

1. `git fetch` → `REF`(既定 = いまのブランチ、タグ可)を取得し、
   `docker-compose.prod.yml` があるか確認(無ければ REF 指定ミスとして停止)
2. `docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build`
3. **マイグレーション**(★アプリ起動より後、利用開始より前)
4. 疎通確認(`/`、`/api/health`、SSE)
5. 不要イメージの削除

## 3.5 GitHub Actions から承認してデプロイする

`main` の変更を、**CT に入らずに、毎回承認してから**反映する仕組み(`.github/workflows/cd.yml`)。

```
main にマージ → CI が通る
   │
   ▼
[deploy-stg]  承認待ち ── 承認 → 練習CTのランナーが deploy.sh を実行
              ※ Variables の STG_CD_ENABLED が true の時だけ
```

```
Run workflow でタグを指定
   │
   ▼
[deploy-stg]  承認待ち ── 承認 → 練習CTのランナーが deploy.sh を実行
   │ 成功      ※ Variables の STG_CD_ENABLED が true の時だけ
   ▼
[deploy-prod] 承認待ち ── 承認 → 本番CTのランナーが deploy.sh を実行
              ※ Variables の PROD_CD_ENABLED が true の時だけ
```

- **承認されるまで何も起きない。**ジョブは承認後に初めて CT に届く
- **`deploy-prod` はタグを指定した手動起動(Run workflow)の時しか動かない。**main への
  マージ(自動起動)からは練習環境までしか進まない。練習環境と本番は恒久的に並存する運用だが、
  それでもマージのたびに本番の承認依頼が直接来るのは避けたいための仕組み
- **本番に入るのはタグを指定して手動起動した時だけ。**同じ run の中で
  練習環境→本番の順に承認すれば、確かめたのと同じコミットが本番に入る
- **main に含まれるものしかデプロイできない。**手動起動でレビュー前のブランチを指定しても止まる
- CT は外から受信できないが、ランナーが「中から GitHub に繋ぎに行く」ので経路はいらない

### 仕組みを用意する(初回のみ)

> 🔴 **順番を守ること。①→②→③ の順に行い、③ のスイッチは最後に入れる。**
> `cd.yml` が参照した Environment がまだ無いと、GitHub は**保護ルールなしで自動作成する**。
> その状態でジョブが動くと承認なしで通過し、あとからランナーを登録した瞬間に
> 無承認でデプロイされうる。スイッチ(`STG_CD_ENABLED` / `PROD_CD_ENABLED`)が既定で
> OFF なのはこのため。

#### ① GitHub 側の設定(リポジトリの管理者が行う)

**Settings → Environments** で `stg` と `prod` の2つを作り、それぞれ次を設定する。

| 項目 | 値 | 理由 |
|---|---|---|
| Required reviewers | 承認できる人 | **これが「毎回の承認」の本体。**外すと承認なしでデプロイされる |
| Prevent self-review | OFF のまま | ON にすると、自分でマージしたものを自分で承認できない |
| Deployment branches and tags | **Selected branches and tags** → `main` だけ(**Protected branches only は使わない**) | 作業ブランチに置いた改変版の `cd.yml` からこの環境を使わせない。Protected branches only だと、将来 main 以外を保護した時にそのブランチからも使えてしまう。タグのパターンは足さなくてよい(手動起動も main から起動するため) |

**Settings → Actions → General** の **Fork pull request workflows from outside collaborators** を
**Require approval for all external contributors** にする。

> 🔴 **このリポジトリは Public で、書き込み権限を持つ人も多い。**CT 上で任意のジョブが動くと、
> CT の乗っ取りと `.env.prod` のトークン漏えいにつながる。次の4つで防いでいる。**どれも外さないこと。**
>
> 1. `ci.yml` は `ubuntu-latest` で動く(CT のランナーのラベルと一致しないので載らない)
> 2. `cd.yml` は main への push で CI が成功した時と、手動起動の時にしか動かない
> 3. 外部からの PR のワークフローは、承認するまで実行されない(上の設定)
> 4. **CT のランナーは「main の `cd.yml` のデプロイジョブ」以外を実行前に拒否する**(② のガード)
>
> 4 が要るのは、ランナーは**同じリポジトリの作業ブランチに置いた別のワークフローからも**
> `runs-on: [self-hosted, quiz-stg]` と書くだけで呼べてしまうため。Environment の承認は
> `environment:` を書いたジョブしか守らず、3 の設定も同じリポジトリのブランチには効かない。
> 本来は組織の runner group で使えるワークフローを絞るが、NUTFes は GitHub Free プランで
> runner group を作れないため、ランナー側のジョブ開始前スクリプトで代わりに弾いている。

#### ② CT にランナーとガードを登録する

ランナーは `deploy` ユーザー(docker グループ所属)で動かす。
まず CT に入り、root で `deploy` ユーザーを用意してファイルの持ち主を合わせる。

> ⚠️ **`deploy` ユーザーが無い CT がある。**`infra/create-ct.sh` で作った CT には作成済みだが、
> CT 201(quiz-stg)はスクリプトができる前(2026-08-24〜25)に手作業で作ったため存在しない。
> 無いまま `chown` すると `invalid user: 'deploy:deploy'` になる。下の最初の2行は、既にある場合は何もしない。

```bash
pct enter 201        # 練習環境。本番なら 202
id deploy >/dev/null 2>&1 || adduser --disabled-password --gecos "" deploy
usermod -aG docker deploy
su - deploy -c "docker ps"                 # エラーにならず一覧が出れば OK
chown -R deploy:deploy /opt/quizApp        # .env.prod も含む。git が「持ち主が違う」と拒否するため
touch /opt/DEPLOYED_REF && chown deploy:deploy /opt/DEPLOYED_REF
```

> ⚠️ **docker を使えるユーザーは、CT の中では root とほぼ同じ権限を持つ。**
> ランナーを root で直接動かすよりはましという程度。だからこそ ① の設定と
> 下のガードで「承認された CD のジョブ以外は CT で動かない」ことを守る。

続けて root のまま、**ガードを root 所有でコピーして置く**。

```bash
install -m 755 -o root -g root /opt/quizApp/infra/runner-job-guard.sh \
  /usr/local/sbin/quiz-runner-job-guard.sh
```

> ⚠️ **`/opt/quizApp/infra/runner-job-guard.sh` を直接指さないこと。**`/opt/quizApp` は
> `deploy` ユーザーが書き換えられるので、ガード自体を書き換えられる。
> `runner-job-guard.sh` を変更したら、このコピーをやり直す。

GitHub の **Settings → Actions → Runners → New self-hosted runner** を開き、**Linux / x64** を選ぶ。
画面に出るコマンドを `deploy` ユーザーで実行する。

```bash
su - deploy
# ↓ 画面の「Download」のコマンドをそのまま貼る(バージョンは画面のものを使う)
mkdir actions-runner && cd actions-runner
curl -o actions-runner-linux-x64-<版>.tar.gz -L https://github.com/actions/runner/releases/download/...
tar xzf ./actions-runner-linux-x64-<版>.tar.gz

# ↓ 画面の「Configure」のコマンドに、--name と --labels を足す
./config.sh --url https://github.com/NUTFes/quizApp --token <画面のトークン> \
  --name quiz-stg --labels quiz-stg --unattended

# ↓ ★ 常駐させる前に、ガードをランナーに設定する
cat >> .env <<'EOF'
ACTIONS_RUNNER_HOOK_JOB_STARTED=/usr/local/sbin/quiz-runner-job-guard.sh
QUIZ_RUNNER_ALLOWED_JOB=deploy-stg
EOF
exit
```

| 環境 | `--name` / `--labels` | `QUIZ_RUNNER_ALLOWED_JOB` |
|---|---|---|
| 練習環境 | `quiz-stg` | `deploy-stg` |
| 本番 | `quiz-prod` | `deploy-prod` |

> ⚠️ **ラベルとジョブ名を取り違えないこと。**`cd.yml` はラベルで行き先の CT を決めている。
> 練習CTに `quiz-prod` を付けると、本番の承認で練習CTにデプロイされる。

最後に root に戻ってサービスとして常駐させる(CT を再起動しても自動で起動する)。

```bash
cd /home/deploy/actions-runner
./svc.sh install deploy
./svc.sh start
./svc.sh status        # active (running) なら OK
```

GitHub の Runners 一覧で **Idle** と表示されれば登録完了。

> ガードを入れ忘れたランナーでは、`cd.yml` の「ランナーのガードを確認」で CD が失敗する。
> 無防備なまま使い続けることはないが、その間も**他のワークフローからは呼べてしまう**ので、
> **`.env` への追記は必ず `svc.sh start` より前に行う。**

> CT を作り直した時(障害復旧など)は、古いランナーを Runners 一覧から削除し、
> 新しい CT で ② をやり直す。

#### ③ スイッチを入れる

**Settings → Secrets and variables → Actions → Variables** で設定する。
**無い(または `true` 以外)** 状態ならそのジョブはスキップされる。

| 変数 | 入れてよい条件 |
|---|---|
| `STG_CD_ENABLED=true` | ① の `stg` の保護と、練習CTの ② が済んだ後 |
| `STG_CD_ENABLED=false` | 練習CTを廃止・または一時的に使えない間(**Variables から消すのではなく `false` にする**。消したままだと `deploy-prod` の判定が「練習環境がある」扱いになり、タグを指定しても本番に進めなくなる) |
| `PROD_CD_ENABLED=true` | **本番へのCDをしてよいと決まった後**。① の `prod` の保護と、本番CTの ② も済ませる |

> ⚠️ **`STG_CD_ENABLED` を明示的に `false` にしないと、本番だけを動かす(練習環境を飛ばす)ことはできない。**
> `deploy-prod` は「練習環境が成功した」か「`STG_CD_ENABLED=false` で練習環境がスキップされた」の
> どちらかでしか動かない。未設定や `true` 以外の値のままでは、練習環境が実行されないのに
> 本番も進まない状態になる(意図しない設定ミスで本番だけ通過してしまうのを防ぐため)。

`STG_CD_ENABLED=true` を入れたら、**Actions → CD → Run workflow** で `ref=main` を指定して1回動かし、
`deploy-stg` のログに `runner-job-guard: OK (deploy-stg)` が出ることを確認する
(ジョブ開始前の処理として、手順より前に表示される)。
`PROD_CD_ENABLED=true` を入れた後は、下の「本番に入れる」の手順でタグを指定して1回動かし、
`deploy-prod` のログに `runner-job-guard: OK (deploy-prod)` が出ることを確認する。

### 普段の操作: 承認する(練習環境)

1. PR を main にマージする。CI が通ると **Actions** タブに `CD <SHA>` が出る
2. 開くと `deploy-stg` が **Waiting** になっている。**Review deployments** → `stg` にチェック → **Approve and deploy**
3. ログは同じ画面に流れる。`deploy.sh` の出力(疎通確認まで)がそのまま見える

> **main へのマージからは本番には進まない。**`deploy-prod` はタグを指定した手動起動の時だけ
> 動く(下の「本番に入れる」)。マージ由来の run では常にスキップされる。

> **承認待ちは溜まる。**続けてマージすると、承認待ちの run が複数並ぶことがある。
> 入れたいものを承認し、古いものは Reject するかキャンセルする。
> 同じ CT へのデプロイが同時に走ることはない(`concurrency`)。

### 本番に入れる(タグを指定して手動起動)

**本番はタグを指定した手動起動(Run workflow)の時しか動かない。**main へのマージだけでは
`deploy-prod` は常にスキップされる(マージのたびに本番の承認依頼が来ないようにするため。上の流れ図を参照)。

1. 練習環境で確かめたコミットにタグを付けて push する(「本番・リハーサルは必ずタグを指定する」と同じ手順)
2. **Actions → CD → Run workflow** を押し、`ref` に**タグ名だけ**を入れて実行する
   (`refs/tags/` を付けたり、ブランチ名・SHA を指定すると本番はスキップされる)
3. 実行結果のサマリー(Step Summary)で「本番: 対象(タグ …)」になっていることを確認する
4. 通常は `deploy-stg` を承認 → 外から確かめる → `deploy-prod` を承認、の順で両方承認する。
   練習CTが一時的に使えない(`STG_CD_ENABLED=false`)場合のみ `deploy-prod` だけ承認待ちになる
5. CT の `/opt/DEPLOYED_REF` の `tags=` で、入ったタグ名を確認する

> **何が動いているかは `/opt/DEPLOYED_REF` と実行のサマリーで見る。**Environments の履歴に
> 表示されるコミットは実行時点の main を指すことがあり、タグで入れたコミットと一致しない場合がある。
>
> **ロールバックに古い run の「Re-run all jobs」は使わない。**再実行はタグの指す先を
> 解決し直すため、タグを付け替えていれば別のコミットが入る。逆に `deploy.sh` の版
> (`script_sha`)は元の run の版のまま固定され、直したいバグが `deploy.sh` 自体にあった
> 場合には反映されない。戻したい時は Run workflow で戻したいタグを指定して新しく実行する。

### (任意) 練習CTが使えない時だけ動かすモードをリハーサルする

練習環境と本番は別ホストで恒久的に並存するので、普段は上の「本番に入れる」の手順(`deploy-stg` →
`deploy-prod` の順に両方承認)を使う。**練習CTのランナー障害時などに `STG_CD_ENABLED=false` で
本番だけ動かす経路**は、本番CTの `quiz-prod` ランナーが登録できたら一度だけ動作確認しておくとよい
(必須ではない)。

1. Variables を `STG_CD_ENABLED=false`、`PROD_CD_ENABLED=true` にする
2. 次を確認する

   | 操作 | 期待する結果 |
   |---|---|
   | Run workflow `ref=<main に含まれるタグ>` | `deploy-stg` はスキップ、`deploy-prod` が `prod` の承認待ちになる → 承認 → `runner-job-guard: OK (deploy-prod)` → デプロイ成功、`/opt/DEPLOYED_REF` の `tags=` にタグ名が入る |
   | Run workflow `ref=main`(ブランチ名) | `deploy-prod` もスキップ(サマリーが「本番: 対象外」) |
   | `STG_CD_ENABLED` を Variables から消して `ref=<タグ>` | `deploy-prod` はスキップ(練習環境がある扱いになるため) |
   | `prod` の承認待ちの間に run を Cancel する | 何もデプロイされない |

3. 確認できたら `STG_CD_ENABLED=true` に戻す(通常運用に復帰)。

### CD でもホスト側の作業は残る

CT の中からはホストのコマンドを打てないので、**`pct fstrim` は自動化できない**。
何度かデプロイしたら、ホストの Shell で次を行う。

```bash
pct fstrim 201
lvs                       # data 行の Data% を確認(85%未満をキープ)
```

## 4. 動作確認

CT の中、またはホストの Shell から:

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/
curl -s http://localhost:8080/api/health
curl -sN --max-time 20 "http://localhost:8080/api/events?view=monitor"
```

最後のコマンドは、接続直後に `event: hello` が出て、**15秒後に `event: ping`** が流れれば成功。
このハートビートが Cloudflare の100秒切断を防ぐ生命線なので、必ず ping まで見る。

> ⚠️ **`?view=` を省くと 400 の JSON が返るだけで、SSE の確認にならない。**
> `view` は `monitor` か `phone` のどちらかが必須(`backend/internal/sse/handler.go`)。

トンネルを使っているなら、**外からも同じものが流れることを必ず確認する**。
ここが通れば「本番だけ画面が切り替わらない」の大半は潰せている。

```bash
curl -sN --max-time 20 "https://quiz.<自分のドメイン>/api/events?view=monitor"
```

> ローカルで ping まで見えるのに外から見えない場合は、経路のどこかがバッファしている。
> まず `docker compose ... logs cloudflared` を見る。

> CT の IP に直接ブラウザで到達できないのは想定どおり。トンネルか
> 組織の Cloudflare 経由でのみ開ける。

## 5. 当日の手順

### 前日〜当日朝

1. **本番用のタグを切る**(手元) → `git tag -a event-YYYY-MM-DD -m "本番"` → `git push origin <タグ>`
2. **本番トークンを発行**して `.env.prod` を更新 → `REF=event-YYYY-MM-DD bash infra/deploy.sh`
   (CD を使うなら、`.env.prod` の更新だけ CT で行い、デプロイは 3.5 の「本番に入れる」)

> ⚠️ **当日は event タグ以外で本番の Run workflow をしない・承認しない(凍結)。**
> `deploy-prod` は main へのマージからは進まないので、**練習環境がまだある間**は
> 練習環境向けの承認待ちが来ても放置してよい(本番には影響しない)。本番はタグを
> 指定した手動起動でしか動かないので、承認しなければ何も起きない点は変わらない。
3. **問題データを投入**(スプレッドシート同期 or 管理者画面)
4. **バックアップを2種類取る**

```bash
# CT の中: データだけのバックアップ
docker compose -f docker-compose.prod.yml --env-file .env.prod \
  exec -T db pg_dump -U quiz quiz > /root/quiz-$(date +%Y%m%d-%H%M).sql
```

```bash
# ホスト: 設定ごと丸ごと戻せるスナップショット
pct snapshot 202 before-event
```

**この2つは役割が違う。** スナップショットは「設定をいじって壊した」時に数十秒で丸ごと
戻せる。`pg_dump` は「データだけ戻したい」時に使う。**両方取る。**

5. ログを流す画面を用意しておく(CT の Console を別タブで開いておく)

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod logs -f
```

### イベント終了後

- `ADMIN_TOKEN` / `IMPORT_TOKEN` を無効化する(`.env.prod` を書き換えて再デプロイ)

## 6. 障害対応(★このページを印刷して持つ)

### アプリが応答しない

```bash
pct enter 202
cd /opt/quizApp
docker compose -f docker-compose.prod.yml --env-file .env.prod ps       # どれが落ちたか
docker compose -f docker-compose.prod.yml --env-file .env.prod logs --tail=50
docker compose -f docker-compose.prod.yml --env-file .env.prod restart   # 再起動
```

`EventState` は DB にあるので、**再起動しても進行状況は失われない**。

### CT ごと再起動する

```bash
# ホストの Shell
pct reboot 202
```

`restart: always` と `--onboot 1` を入れてあるので、コンテナは自動で復帰する。

### 設定をいじって壊した(最終手段)

```bash
# ホストの Shell。数十秒で丸ごと戻る
pct stop 202
pct rollback 202 before-event
pct start 202
```

### データだけ戻したい

```bash
pct enter 202
cd /opt/quizApp
cat /root/quiz-YYYYMMDD-HHMM.sql | docker compose -f docker-compose.prod.yml \
  --env-file .env.prod exec -T db psql -U quiz quiz
```

### 会場のネットが落ちた / Cloudflare が落ちた

→ **紙で進行する。** 復旧を待たない。判断者と切り替えのタイミングを事前に決めておく。

## 7. よくある詰まり

| 症状 | 原因と対処 |
|---|---|
| `docker compose up` が起動しない | CT の `nesting=1` が無い。ホストで `pct set <VMID> --features nesting=1,keyctl=1` → `pct reboot` |
| ディスクが一杯 | CT内 `docker system prune -af` → **ホストで `pct fstrim <VMID>`**。後者を忘れると容量が返らない |
| 画面が切り替わらない(接続はできる) | SSE のバッファリング。`frontend/nginx.conf` の `proxy_buffering off` を確認 |
| 一定人数から先が繋がらない | fd 上限。`docker-compose.prod.yml` の `ulimits.nofile` を確認(既定 1024 では足りない) |
| 全端末が古い画面のまま固まる | Cloudflare が `/api/*` をキャッシュしている(policy Q4) |
| SSE が全端末で繋がらない | Cloudflare の Bot Fight Mode / チャレンジ(policy Q3) |
| ログの時刻が9時間ずれる | コンテナ内 TZ。`docker-compose.prod.yml` の `TZ=Asia/Tokyo` を確認 |
| 直したはずの不具合が本番に残る | 古いタグをデプロイしている。`cat /opt/DEPLOYED_REF` で確認 |
| `docker-compose.prod.yml: no such file or directory` | `REF` が本番構成の入っていないブランチを指している。`REF=` を正しいタグ/ブランチにする |
| backend が `restarting` から戻らない | `POSTGRES_PASSWORD` に `/` や `+` が入り `DATABASE_URL` が壊れている。`-hex` で作り直し、`docker compose ... down -v` してから再デプロイ |
| 参加者のスマホで真っ白 | フロントに localhost が焼き込まれた可能性。`frontend/src/lib/config.ts` が相対パス対応か確認 |
| 外から 530 / 1033 が返る | `cloudflared` が繋がっていない。`logs cloudflared` で `Registered tunnel connection` を確認 |
| 外から 404 が返る | トンネルは繋がっているが Routes 未設定。Service URL は `http://frontend:80`(`localhost` ではない) |
| 外からだけ SSE が届かない | quick tunnel を使っていないか確認。使い捨てURLは SSE 非対応で 200接続で頭打ちになる |
| CD が `Waiting for a runner` のまま進まない | CT のランナーが止まっている。CT で `cd /home/deploy/actions-runner && ./svc.sh status`。本番なら `quiz-prod` のランナーが登録済みか確認 |
| CD の `deploy-stg` / `deploy-prod` が毎回スキップされる | `deploy-stg`: Variables の `STG_CD_ENABLED` が `true` でない。`deploy-prod`: ①`PROD_CD_ENABLED` が `true` でない(想定どおり、本番へのCDを止めている状態) ②main へのマージ由来の run(想定どおり、本番はタグを指定した手動起動でしか動かない) ③`ref` がタグ名になっていない・`refs/tags/` を付けている ④練習CTを廃止したのに `STG_CD_ENABLED` を「消した」だけで `false` にしていない。実行結果のサマリーの「本番: 対象/対象外」も手がかりになる |
| CD が「デプロイ対象のコミットが確定していません」で失敗する | resolve の出力(`sha` / `script_sha`)が空か不正な形式。resolve のジョブのログとサマリーを確認する |
| CD が「ランナーにジョブ開始前ガードが設定されていません」で失敗する | ランナーの `.env` にガードが無い。3.5 ② の `.env` 追記をして `./svc.sh stop && ./svc.sh start` |
| `deploy-stg` がいつまでも Queued のまま進まない(ランナー待ち) | `quiz-stg` のランナーが登録されていない/オフライン。CT で ランナーの `./svc.sh status` を確認。**練習CTを廃止済みで復旧の予定が無いなら、Variables の `STG_CD_ENABLED` を `false` に戻す**(true のままだと本番へも一生進めなくなる) |
| CT のランナーで `このランナーは CD(...)専用です` と失敗する | 想定どおりガードが弾いている。`cd.yml` 以外、または main 以外のブランチから CT のランナーを指定したジョブ |
| CD で `detected dubious ownership` / `Permission denied` | `/opt/quizApp` か `/opt/DEPLOYED_REF` の持ち主が `deploy` でない。3.5 ② の `chown` をやり直す(root で手動デプロイした後に起きやすい) |
| CD で `main に含まれていません` | 手動起動の `ref` にマージ前のブランチを指定している。マージしてから、またはタグを指定する |
| トンネルを設定したのに起動しない | `.env.prod` の `STG_CF_TUNNEL_TOKEN` が空。空だと `deploy.sh` は `cloudflared` を起動しない(②の出力で分かる) |
