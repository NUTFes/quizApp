# GitHub運用ガイド — なぜこの運用にしたのか

**この運用の設計意図をまとめた文書。** ルールの一つひとつについて「なぜそうしたか」「何を捨てたか」を記録してある。

- **手順を知りたい人は** → [`開発フローガイド.md`](./開発フローガイド.md)(こちらが実務の本体)
- **レビューをする人は** → [`レビューガイド.md`](./レビューガイド.md)

読まなくても開発はできる。ただし、

- ルールが窮屈に感じたとき
- ルールを変えたくなったとき
- 新しくチームに入った人に説明するとき

には、ここに戻ってくると判断の材料になる。**ルールは目的があって存在していて、目的が変われば変えてよい。**

---

## 1. 設計の前提 — 何を条件に決めたか

運用ルールに唯一の正解はない。**チームの条件が変われば正解も変わる。** うちの条件はこう。

| 条件 | 中身 |
|---|---|
| **スキル** | ほぼ初心者チーム。Git/GitHubの経験がない人が複数いる |
| **開発人数** | 3人 + PM(フロント1人 / バックエンドリーダー + 初心者1人 / インフラはPM単独) |
| **レビュー体制** | 4人(PM・バックエンドリーダー・開発に参加しない経験者2人) |
| **経験者2人の制約** | 開発環境を構築しない。**手元でコードを動かせない** |
| **期間** | 短い。学祭当日という動かせない締切がある |
| **PMの立場** | 実装もレビューもタスク切りもやる。**ここが詰まると全部止まる** |

この5つ、特に**「初心者中心」「期間が短い」「レビュワー2人が環境を持たない」**の3つが、以下のほぼ全ての決定の理由になっている。

---

## 2. 根本方針 — ルールは少なく、機械に守らせる

> **口頭のルールは守られない前提で設計する。機械的に判定できることは、全部機械にやらせる。**

初心者チームで「気をつけてね」は機能しない。悪意がなくても、忙しくなれば忘れるし、そもそも何に気をつけるべきかが分からない。

だから設計をこう分けた。

| 守らせ方 | 対象 | 具体例 |
|---|---|---|
| **機械が強制する** | 守られないと事故になるもの | mainブランチ保護、CI、squash merge固定、CODEOWNERS |
| **ドキュメントに書く** | 判断が要るもの、文化に関わるもの | レビューの観点、prefix記法、3往復ルール |
| **何も書かない** | どちらでもいいこと | コミットの粒度、書式(CIが直す) |

**1段目に置けるものは、なるべく1段目に置く。** ドキュメントに書いただけのルールは、読まれなければ存在しないのと同じだから。

そして裏返しとして、**メンバーが覚えるべきルールを極力減らす**。[`開発フローガイド.md`](./開発フローガイド.md) の①〜⑨だけ覚えればよく、それ以外は機械が止めてくれる。

## 3. 個別の決定とその理由

### 3-1. GitHub Flow(`main` + 作業ブランチのみ)

**決定**: `develop` などの中間ブランチを作らない。`main` と作業ブランチの2階層だけ。

**なぜ**: 中間ブランチは「リリース前の統合先」として意味を持つが、うちは**本番リリースが学祭当日の一度きり**。統合先を分ける必要がない。
一方で、初心者にとって「今どのブランチにいるか」「どこから切るか」は最初の躓きポイント。**階層が1つ増えるだけで混乱が倍**になる。

**捨てたもの**: リリース管理の柔軟性。うちには不要と判断した。

### 3-2. `main` ブランチ保護

**決定**: 以下を設定する。

| 設定 | なぜ |
|---|---|
| PR必須(approve 1件) | 誰の目も通らずに `main` に入る経路をなくす |
| CI通過必須 | ビルドが通らないコードを構造的に排除する |
| force push 禁止 | 履歴の破壊は復旧が難しく、初心者が最も事故りやすい操作 |
| **管理者にも適用** | **PMのうっかりも同じように防ぐ** |
| マージ後ブランチ自動削除 | 古いブランチが溜まると、どれが生きているか分からなくなる |

**なぜ「管理者にも適用」が重要か**: PMは急いでいるときほど「自分だけ直接pushすれば早い」と考えてしまう。そして**PMが例外を使い始めた瞬間、ルール全体の説得力が消える**。仕組みで自分を縛るのが一番安い。

**`main` が壊れたときの被害**: 全員が壊れたコードを `pull` して全員の手元が止まり、原因の切り分けにPMの時間が溶ける。**初心者チームでは復旧コストが特に高い**ので、予防に振り切る価値がある。

### 3-3. squash merge に統一

**決定**: マージ方式は Squash merge のみ。他の方式はGitHubの設定で**無効化する**。

**なぜ**:
- 初心者は「とりあえずコミット」「typo修正」のような細かいコミットを大量に作る。それが `main` の履歴に流れ込むと、後から履歴が読めなくなる
- squashなら **1 PR = 1コミット**。履歴がそのまま「何をやってきたか」の一覧になる
- 副次効果として、**メンバーがコミットの粒度やメッセージに悩まなくてよくなる**。これが地味に効く。初心者にとって「きれいなコミットを作らねば」は無視できない心理的負荷で、それを丸ごと免除できる

**設定で無効化する理由**: 「squashに統一しましょう」と口で言っても、マージ画面に3つボタンがあれば必ず誰かが別のを押す。**方針2(機械に守らせる)の適用例**。

### 3-4. 1ブランチ = 1 Issue = 1 PR / 1タスク = 1フォルダ

**決定**: 1つのブランチに複数の作業を混ぜない。新機能は `features/` や `internal/` に**新しいフォルダを切る**。

**なぜ**: コンフリクト(競合)対策。
コンフリクトは初心者が最も詰まるトラブルで、しかも**間違った直し方をすると他人の作業を消す**。解決方法を教えるより、**そもそも起きない構造を作る**ほうが確実。

同じファイルを2人が触らなければコンフリクトは原理的に起きない。だから**タスクの切り方の段階で、触るフォルダが重ならないようにする**。これはPM側の責任(Issueを切るときに②触ってよいファイルを指定する)。

**捨てたもの**: 既存コードの共通化・整理のしやすさ。多少重複しても、並行開発が止まらないほうを優先した。

### 3-5. Draft PRを「中断時の作法」にした

**決定**: 「見てほしいときに使う任意の機能」ではなく、**作業を中断するたびに必ず作るもの**とした。

**なぜ**: 任意の機能にしておくと、初心者は使わない。「まだ人に見せる段階じゃない」と判断するから。
そこで**必ず訪れるタイミング(作業の中断)に紐づけて、判断を不要にした。**

これで4つの問題が同時に解決する。

| 問題 | Draft PRがない場合 | ある場合 |
|---|---|---|
| 消失 | PCが壊れたら全部消える | GitHubに残る |
| 不可視 | 進捗が「順調です」しか分からない | 差分が見える |
| **手遅れ** | **完成後に方向性の間違いが判明する** | **途中でPMが軌道修正できる** |
| 忘却 | 数日空けると自分でも分からなくなる | PRに書いてある |

**特に3つ目**。初心者が3日かけて作ったものを「そもそも作り方が違う」と返すのは、本人にとって最悪の体験で、実際にやる気を折る。**Draft PRは技術的な仕組みというより、それを防ぐための装置**として入れている。

**PM側の運用**: Draft PRが出ていたら、**依頼されなくても時々覗く**。これはPMの仕事。

### 3-6. 動作確認の証拠は「PRを出す側」の責任にした

**決定**: PRに動作確認の証拠(スクショ / `curl`の結果)を貼るのを必須にし、**レビュワーが手元で動かすのは任意**とした。

**なぜ**: レビュワー4人のうち**2人が開発環境を持たない**から。
もし「レビュワーが手元で `mise run up` して確認する」を必須にすると、**レビューできる人がPMとバックエンドリーダーの2人に戻ってしまう**。それでは経験者2人を戦力にできず、PMがボトルネックになる。

そこで確認の負担を**出し手側に移した**。出し手は既に自分の環境で動かしているので、**追加コストはスクショを撮るだけ**。全体で見れば最も安い。

**副次効果**: 「動作確認しました」と口で書くのと、スクショを貼るのとでは、**実際に確認する率が変わる**。証拠を求めること自体が品質チェックとして機能する。

### 3-7. CODEOWNERSで自動指名

**決定**: `.github/CODEOWNERS` でレビュワーを自動指名する。ただし**必須化はしない**(approve 1件で通す)。

**なぜ**: 初心者にとって「誰にレビューを頼むか」は地味に大きなハードル。「忙しそう」「この人でいいのか」で止まる。**選択を消せば止まらない。**

指名は2人にしてある。1人だとその人が忙しいときに詰まるが、2人いれば早いほうが見られる。

**必須化しない理由**: CODEOWNERSの必須化(Require review from Code Owners)を入れると、**指名された特定の人のapproveが必要**になる。期間が短いうちのチームでは、それが待ち時間を生む。「誰か1人が見ればよい」のほうが速い。

### 3-8. approve は1件

**決定**: マージに必要なapproveは1件。

**なぜ**: 2件必須にすると品質は上がるが、**レビュー待ちが2倍**になる。うちは期間が短く、レビュワーの多くは他の作業も抱えている。
`main` 保護 + CI + 1件のレビューで、「壊れたコードが入る」事故はほぼ防げる。それ以上は費用対効果が悪い。

### 3-9. マージはPMが行う

**決定**: approveが付いたPRを `main` に入れる操作は、PMがまとめて行う。

**なぜ**: approveするのはレビュワー側であり、**マージの可否判断とタイミングの管理はPMの責任**だから。

具体的には:
- 複数のPRが同時にapproveされたとき、**どの順で入れるか**の判断が要る(依存関係があるとき)
- `must:` の指摘が本当に解消されているかの最終確認
- マージのタイミングを見て、他のメンバーに `git pull` を促せる

**捨てたもの**: 「自分の成果物を自分で `main` に入れる達成感」。これは実際に価値があるものだが、**進行管理の一元化を優先した**。もしメンバーのモチベーション面で問題が出たら、ここは見直してよい。

### 3-10. コメントのprefix記法(`must:` / `imo:` / `ask:` / `good:`)

**決定**: レビューコメントに強度を示すprefixを付ける。**prefixの無いコメントは `imo:`(任意)扱い**。

**なぜ**: 初心者は、指摘を**全部「必ず直さないといけないもの」として受け取る**。すると、
- 単なる提案や質問にも過剰に反応して疲弊する
- 指摘が5個並んだだけで「全部やり直し」に見えて、自信を失う

**強度を明示すれば、この誤読は構造的に消える。**

**「prefixなし = `imo:`」という既定値が肝**。レビュワーがprefixを付け忘れたときに、厳しい側ではなく**緩い側に倒れる**ようにしてある。付け忘れで人が萎縮するのを防ぐため。

**`good:` を入れた理由**: 指摘だけが並ぶPRは、内容が正しくても人が続かない。初心者チームでは**「次もPRを出そう」と思える状態で返すこと**が、指摘の精度より優先度が高い局面がある。

### 3-11. レビューは平日12時間以内に一次反応

**決定**: レビュー依頼から**平日12時間以内に何らかの反応**をする。「明日見ます」の一言でもよい。**催促は正しい行動**と明記する。

**なぜ12時間か**: 開発期間が短いから。24時間だと、PR1本のやり取りに丸2日かかる計算になり、締切から逆算すると回らない。

**なぜ「完了」ではなく「一次反応」か**: レビュワーは学業や他の作業を抱えている。「12時間以内に完全なレビュー」は守れない約束になり、守れない約束はルール全体の信頼を落とす。
出す側が本当に困るのは**レビューが遅いことより、見られているか分からないこと**。だから約束するのは反応の速さにした。

**催促を明文化した理由**: 初心者は催促を「失礼」と感じて待ち続ける。**「催促してよい」ではなく「催促は正しい行動」と書く**ことで、待ちぼうけを構造的に防ぐ。

### 3-12. 3往復ルール

**決定**: 同じ論点でコメントが3往復を超えたら、テキストをやめて通話するかPMを呼ぶ。

**なぜ**: 3往復して噛み合わないのは、**たいてい前提がずれているだけ**で、5分話せば終わる。テキストの往復は時間を溶かすうえに、初心者にとっては**詰められている**ように感じられて心理的な負荷が高い。

エスカレーション先を明示しておくのは、**当事者同士で決着をつけなくてよい**と保証するため。

### 3-13. ラベルはPMが付ける / 最初はPMが割り当てる

**決定**: 難易度・領域ラベルはPMが起票時に付ける。担当も最初はPMが割り当て、慣れたら自己申告に移行する。

**なぜラベルをメンバーに付けさせないか**: **初心者は自分にとっての難易度を判断できない。** 「簡単そう」と思って `hard` を取って詰まる、あるいは逆に自信がなくて何も取れない、のどちらかになる。難易度はタスクを設計した人が付けるのが正しい。

**なぜ最初は割当制か**: 「これ自分が取っていいのか」で止まるから。名指しされれば動ける。慣れて全体像が見えてきたら自己申告に切り替えるほうが、PMの負荷も下がる。

### 3-14. Issueテンプレートは2種類 / Markdown形式

**決定**: 「タスク」と「バグ報告」の2種類。Issue Forms(入力フォーム形式)ではなくMarkdownのまま。

**なぜ2種類か**: タスク用の「①ゴール ②触ってよいファイル ③写経元 ④動作確認方法」は**これから作るもの**の書式で、既存の不具合報告には当てはまらない。書式が合わないとテンプレを全消しして1行だけ書く運用になり、結局「再現手順が分からず直せない」となる。

**なぜ3種類目(質問用)を作らないか**: 質問はSlackのほうが速い。Issueにすると返事が遅くなり、質問しなくなる。

**なぜIssue Formsにしないか**: Formsは空欄を防げるが、**当面Issueを書くのはほぼPM自身**。書き手が自分なら、強制力より編集しやすさのほうが実利がある。メンバーが起票し始めて空欄が目立ったら移行する。

## 4. あえて採用しなかったもの

「検討したが入れなかった」ものの記録。同じ議論を繰り返さないため。

| 採用しなかったもの | 理由 |
|---|---|
| `develop` ブランチ | リリースが1回きり。階層が増えると初心者が混乱する(→3-1) |
| approve 2件必須 | 待ち時間が2倍。期間が短いうちでは費用対効果が悪い(→3-8) |
| CODEOWNERSの必須化 | 特定の人待ちが発生する(→3-7) |
| レビュワーによる実機確認の必須化 | レビュワー2人が環境を持たない(→3-6) |
| Issue Forms | 当面の書き手がPM自身(→3-14) |
| GitHub Projects(かんばん) | **保留**。4人ならIssue一覧で見渡せる。→ §5の見直し条件 |
| Conventional Commits(`feat:` 等の厳密な規約) | squash mergeなのでPRタイトルさえまともなら履歴は保たれる。初心者に覚えることを増やさない |
| 書式に関するレビュー指摘 | CIの仕事。人間がやると時間の無駄で、受け手も萎縮する |

## 5. 運用を見直すタイミング

ルールは条件に合わせて作ってある。**条件が変わったら見直す。** 見直しの引き金を先に決めておく。

| 引き金 | 見直す対象 |
|---|---|
| 未クローズのIssueが20個を超えた / Phase 1で並行作業が本格化した | **GitHub Projects の導入**(→4) |
| メンバーが自分でIssueを起票し始め、空欄が目立つ | **Issue Forms への移行**(→3-14) |
| メンバーが1人2〜3個のIssueをこなした | **担当の自己申告制への移行**(→3-13) |
| レビュー待ちが慢性的に12時間を超える | レビュワーの割り当て、approve要件、PRの粒度 |
| 「自分でマージしたい」という声が出る | **マージ主体**(→3-9) |
| ESLint / Prettier を導入した | CIのジョブ構成、PRチェックリスト、レビュー観点 |
