# CI・コードチェック入門 — なぜ機械にコードを見張らせるのか

このプロジェクトでは、PR(プルリクエスト)を出すたびにGitHub上でコードの自動チェックが走り、**チェックに落ちるとマージできない**仕組みにする。
「なぜそんな仕組みにするのか」「そもそもフォーマッターとかLintとか何が違うのか」を初心者向けに説明する。

---

## 1. CIとは何か

**CI (Continuous Integration)** = PRが出るたびに、GitHubのサーバー上でコードのチェックを自動実行する仕組み。うちでは **GitHub Actions** という機能を使う(リポジトリに `.github/workflows/ci.yml` という設定ファイルを置くだけで動く)。

なぜ入れるのか。Git運用policyの方針がすべて:

> 初心者チームなので、**ルールは少なく・機械に守らせる**。口頭ルールは守られない前提で設計する。

「コードの書き方を揃えてね」「壊れたコードをmainに入れないでね」を口頭で言っても、忙しくなると必ず崩れる。人間のレビュワー(先輩)に毎回スタイルの指摘をさせるのは時間の無駄だし、指摘される側も萎縮する。**機械的に判定できることは全部機械にやらせて、人間のレビューは「動くか・設計がいいか」だけに集中させる**のがCIの目的。

---

## 2. チェックの種類 — 4つの道具の違い

「コードをチェックする道具」には段階があり、それぞれ守るものが違う。

| 種類 | 何を守るか | 例えると | TSでの道具 | Goでの道具 |
|---|---|---|---|---|
| ① フォーマッター | **見た目**(インデント・改行・クォート) | 文書の書式設定 | Prettier | gofmt(Go標準搭載) |
| ② リンター | **危ないコードの癖**(未使用の変数、バグの温床パターン) | 文章校正 | ESLint | go vet(Go標準搭載) |
| ③ 型チェック | **データの形の整合性**(`text`を`txt`と打つ等) | 設計図の寸法チェック | tsc(TypeScript本体) | コンパイラが常時実施 |
| ④ ビルド | **そもそも完成品が作れるか** | 試し組み立て | vite build | go build |

### ① フォーマッター — 議論を消す道具

「インデントは2か4か」「クォートは ' か " か」のような**どちらでもいいこと**を、保存した瞬間に機械が全部統一する。正解を決めるのが目的ではなく、**議論とレビュー指摘をゼロにする**のが目的。人によって書式が違うと、PRの差分に「本当の変更」と「書式の揺れ」が混ざってレビューが地獄になる。

### ② リンター — バグの芽を指摘する道具

書式ではなく**中身の危険パターン**を指摘する。「宣言したのに使っていない変数(消し忘れ?)」「条件式に = と == の書き間違い」など。フォーマッターと違って自動では直さない(直すべきかは人間の判断だから)。

### ③ 型チェック — TypeScriptの本領

`docs/技術スタック.md` で説明した「型という安全装置」の検査。実行しなくても「このデータに `txt` というキーはない」を検出する。Goでは独立した道具は不要で、コンパイル(ビルド)自体が型チェックを兼ねる。

### ④ ビルド — 最後の確認

「コードを完成品に変換できるか」。①〜③を通っても、importの書き間違いなどでビルドが壊れることはある。

> ⑤としてテスト(vitest / go test)もあるが、v1ではジョブの枠だけ用意して中身は後から育てる(最初から高いハードルにしない)。

## 3. 同じチェックを「3つの場所」で段階的にかける

ここが設計の肝。**同じチェックを、気づくタイミングが早い順に3箇所**でかける。

```
【1】エディタ(書いた瞬間)     … 保存時にPrettierが自動整形、ESLint/tscのエラーが赤線で出る
【2】手元のコマンド(PR前)     … mise run lint / mise run test で一括確認
【3】CI(PRを出した後)         … GitHub Actionsが全チェックを実行。落ちたらマージ不可
```

なぜ3重にするのか: **問題は、見つかるのが早いほど直すのが安い**から。

- 【1】で気づけば直すのに3秒(赤線の場所を直すだけ)
- 【3】まで行くと、PRを出す → 数分待つ → 落ちる → 直す → push → また待つ、で1周10分以上

じゃあ【1】【2】だけでよくない? → ダメ。エディタ設定は人によって壊れるし、手元のコマンドは打ち忘れる。**【3】のCIだけが「絶対にすり抜けられない最後の関門」**。逆にCIだけだと毎回10分ループになって辛いので、【1】で快適にしておく。

だからリポジトリには次の3点セットをコミットする(全員のエディタで【1】が同じ動きをするように):

- ESLint / Prettier の設定ファイル(ルールブック本体)
- `.vscode/settings.json`(保存時に自動整形をON)
- `.vscode/extensions.json`(開いたときに必要な拡張機能を推奨表示)

## 4. うちのCIの構成(確定)

v1は**シンプルに・数分で終わる**ことを最優先にする。遅いCIは待たれなくなり、無視される。

| ジョブ | フロントエンド(TS) | バックエンド(Go) |
|---|---|---|
| lint | ESLint + Prettier(--check: 整形済みかの確認だけ) | gofmt チェック + go vet |
| typecheck | tsc --noEmit(変換はせず型検査だけ) | (go build が兼ねるので独立ジョブなし) |
| build | vite build | go build |
| test | 枠だけ用意(空テスト1本から) | 枠だけ用意 |

- トリガー: **PRを出したとき**と**mainにマージされたとき**
- mainブランチ保護と組み合わせる: 「**CIが緑 + approve 1人**」を満たさないとマージボタンが押せない。これが「mainは常に動く状態」の機械的な保証

---

## 5. メンバーの日常には何が起きるか(まとめ)

1. コードを書く → 保存すると勝手に整形され、ミスは赤線で出る(ほぼこれで完結)
2. PRを出す → CIが数分回る。緑になったらレビュー依頼
3. 落ちたら → CIのログに「どのファイルの何行目が何のルールに違反か」が出るので、直してpushし直すだけ。**CIに落ちるのは恥ずかしいことではなく、mainを壊さなかった成功例**
