# Figma・Tailwind スペーシング 再集計指示書

この文書は、**これまでの会話を読んでいないエージェント**が、救済問題（Repechage）を除外したスペーシング件数を再集計するための指示書である。

関連: [`Figma・Tailwindスペーシング対応表.md`](./Figma・Tailwindスペーシング対応表.md) / Issue #54

---

## 1. なぜ再集計するのか

対応表 §2・§5・§7 の集計は、**救済問題（Repechage）を含んだまま**行われた。その後、救済問題は実装対象外で確定した（対応表 §4）。

- **px 値の種類は判明している**（3画面合計 35 → 34。`160px` が消える）
- **件数は不明** — 救済問題の画面は `48px` などの共通値も使っており、既存の表からは分離できない

件数は Issue #54 の「4px グリッド外の値をどう整理するか」の判断根拠になるため、正確な数字が要る。

## 2. 最重要制約

### Figma は読み取り専用

- Figma Variables を作成・変更しない
- ノード、コンポーネント、Auto Layout、パディング、gap を変更しない
- Figma への書き込みツールを呼ばない

### px 値を丸めない・統合しない

読み取った値をそのまま記録する。`15px` と `16px` があれば2行として記録する。**統合の判断はこの作業の範囲外**（PM 承認が要る）。

### 既存の帰属付けを信用しない

対応表の「主な使用箇所」列は前回の作業者による記述で、**救済問題との境界が正確に切られていない可能性がある**。

具体的な既知のリスク:

> Mobile の `120px`（2件）は「開始前・待機系メッセージ」として記録されており、代表 node ID は `475:7003` `475:7012`。一方、救済問題の操作部分とされた `26px` の node ID は `475:7020` `475:7026` `475:7032` で、**両者は ID が隣接している**。同じフレーム群に属している可能性がある。

**どのノードが救済問題に属するかは、対応表の記述からではなく、Figma のフレーム階層から判定すること。**

## 4. 集計ルール

**対応表 §1 のルールをそのまま使う。**変更してはいけない。前回と数え方が変わると、§6 の検算が意味を失う。

### 対象

- Auto Layout の padding
- Item spacing / gap
- Web 実装で `padding` / `margin` / `gap` に相当する余白

### 対象外

- 固定 width / height
- アイコン・画像サイズ
- font-size / line-height / letter-spacing
- border-radius / border-width
- 色・影
- 絶対配置された装飾の位置調整（`Glow pink` の `190px` など）

### 件数の数え方

- 同じコンポーネントを複数画面で再利用していても、**コンポーネント定義は1件**として数える
- 画面直下のフレームやセクションは、**その都度1件**として数える
- 同じノードでも、`px` と `py` のように**方向が違う指定は別々に**数える
- node ID と指定方向で重複を除外する
- px 値は丸めず、Figma から読み取った値をそのまま記録する

## 5. 分類の定義

各スペーシング指定を、次の4区分のいずれか**ちょうど1つ**に割り当てる。

| 区分 | 内容 | 扱い |
| --- | --- | --- |
| **本体** | 下記3つ以外のすべて | **これが再集計の目的** |
| **救済問題** | `Mobile/Screen/Repechage/*` `Display/Screen/Repechage/*` 配下 | 実装対象外。本体から除く |
| **早押し** | `Display/Screen/Buzzer/*` 配下 | **フェーズ2用として保留。**本体から除くが、削除せず別枠で数える |
| **ステータスバー** | `Mobile/System/Status Bar`（`475:8171`）配下 | 実装対象外（端末OSの描画領域）。本体から除く |

### 判定の手順

1. Figma のフレーム階層をたどり、`Repechage` / `Buzzer` / `Status Bar` に**該当するフレームの node ID を先に全部列挙する**
2. 列挙した結果を、区分ごとの node ID リストとして出力する（後から人が検証できるようにするため）
3. そのうえで、各スペーシング指定がどのフレーム配下にあるかで区分を決める

### 判断に迷ったら

フレーム名から救済問題か本体かが判別できないノードがあった場合、**推測で振り分けず、「判定不能」として node ID と理由を列挙する**。件数を水増しも過少にもしない。

## 6. 検算（この作業の信頼性はここで決まる）

**「救済問題を含む」集計も同時に出力し、対応表 §2・§5・§7 の既存の表と突き合わせること。**

既存の表と一致すれば、数え方が前回と揃っていることが確認でき、「除外後」の数字も信用できる。一致しなければ、**除外後の数字を出す前に、不一致の原因を報告する。**

照合先の既存数値:

| 画面 | 異なる px 値 | スペーシング指定 |
| --- | ---: | ---: |
| `Screens/Mobile`（本体、ステータスバー除く） | 22種類 | 433件 |
| `Screens/Display` | 25種類 | 364件 |
| `admin` | 18種類 | 236件 |

既知の期待値（除外後）:

- 3画面合計の px 値の種類: **34種類**（`160px` が消える）
- Mobile: **21種類**（`26px` が消える）
- Display: **23種類**（`120px` `160px` が消える）

⚠️ ただし **`26px` と `120px` の帰属は §2 の理由で不確実**。上記と食い違った場合は、**指示書が間違っている可能性を優先して報告する**（自分の集計を期待値に合わせに行かない）。

## 7. 出力

対応表と同じ列構成で出力する。差分として読めることが重要なので、**列の順序と表記を変えない**。

### 7.1 画面ごとの表（本体のみ）

`Screens/Mobile` / `Screens/Display` / `admin` それぞれについて:

```
- 異なるpx値: N種類
- スペーシング指定: N件（コンポーネントの再利用を重複除外後）
- 使用値: `a / b / c ...px`
```

| px値 | 個数 | 種別・方向 | 主な使用箇所 | 代表node ID |
| ---: | ---: | --- | --- | --- |

方向表記は `p` / `px` / `py` / `pt` / `pr` / `pb` / `pl` / `gap` / `gap-x` / `gap-y`。

### 7.2 除外分の表

救済問題 / 早押し / ステータスバー それぞれについて、同じ列構成の表を出す。**どれだけ差し引いたかが分かる形にする。**

### 7.3 検算結果

| 画面 | 既存の表 | 今回（救済問題を含む） | 一致 |
| --- | ---: | ---: | :---: |

一致しない行があれば、原因の分析を添える。

### 7.4 判定不能リスト

§5 で判定できなかったノードの一覧（node ID / フレーム名 / 迷った理由）。

### 7.5 出力先

`dev_policy/Figma・Tailwindスペーシング再集計結果.md` として新規作成する。

**既存の `Figma・Tailwindスペーシング対応表.md` を書き換えない。** 突き合わせは人間が行う。

## 8. やってはいけないこと

- Figma を変更する
- px 値を丸める・統合する・トークン名を付ける
- 検算（§6）を省略して除外後の数字だけ出す
- 集計結果を期待値に合わせて調整する
- 対応表の「主な使用箇所」の記述を根拠に救済問題かどうかを判定する（フレーム階層で判定する）
- 既存の対応表ファイルを書き換える
- コミット、push、PR 作成
