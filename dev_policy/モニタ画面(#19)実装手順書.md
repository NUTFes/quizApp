# モニタ画面(#19) 実装手順書

Issue #19 の担当者向け。

**前提: #18（スマホ画面）が終わっていること。** モニタ画面はスマホ画面と同じ構造なので、**#18 で作ったものが見本になる。**

まず [`スマホ画面(#18)実装手順書.md`](./スマホ画面\(#18\)実装手順書.md) の §0〜§6 を読むこと。**この手順書は「スマホ画面との違い」だけを書いている。**

---

## 0. この画面の位置づけ

**このアプリの主役。** 会場の 85 インチ大画面に映る。

そして合格基準はたった1つ。

> **会場の後ろの席から読めるか。**

デザインが綺麗かどうかではない。**200人が同時に見て、全員が読めるか。**これだけ。

そして厄介なことに、**それは手元の PC では絶対に判断できない。** 27インチのモニタで「大きすぎる」と感じるサイズが、85インチを 20m 先から見ると小さかったりする。

> **通しリハーサルで実機確認するまで、文字サイズは「仮」だと思うこと。**
> 調整しやすい作り（サイズを1箇所で変えられる）にしておくと、当日楽になる。

---

## 1. スマホ画面との違い

| | スマホ(#18) | モニタ(#19) |
| --- | --- | --- |
| 向き | 縦 | **横** |
| 文字サイズ | 普通 | **極端に大きい**（`text-6xl` `text-8xl` あたり） |
| 参加用QR | 無し | **常時表示**（`waiting` / `question` / `answer`） |
| アンケートQR | リンクだけ | **QRで表示**（`finished`） |
| 正解演出 | 無し | **動画を再生**（企画側制作） |
| 会場マップ | あり | 無し（参加者が見るのはスマホ） |
| 解説 | あり | 仕様に記載なし。**PMに確認すること** |
| state の型 | `ViewerState` | `MonitorState`（= `ViewerState` + `joinUrl`） |

## 2. 使うもの

```tsx
import { useMonitorState } from '../../lib/useEventState'

const state = useMonitorState()   // MonitorState | null
```

`MonitorState` はスマホと**ほぼ同じ**。違いは `joinUrl` が1つ増えているだけ。

```ts
export type MonitorState = ViewerState & { joinUrl: string }
```

`useRemainingTime` の使い方も、`textSegments` の連結も、`type` 別の配置も**#18 と完全に同じ**。

### ⚠️ 早押しの「順次表示」は自分で実装しない

仕様に「早押しは問題文を順次表示」とあるが、**フロントで区切りを管理する必要はない。**

サーバーが `textSegments` に**すでに表示してよい分だけ**を入れて送ってくる。裏方が「次を表示」を押すたびに配列が1つ増えて届く。

**あなたは #18 と同じく `textSegments.join('')` するだけでよい。**

### 🚫 `features/phone/` の部品を import しない

「#18 に同じ `QuestionText` があるから使い回そう」と思うはず。**やらないこと。**

理由は3つ。

1. **寸法が全く違う。** 片方を直すともう片方が壊れる
2. **担当者が違う。** #18 の人が自分の画面を直したとき、モニタが巻き添えになる
3. **当日、片方だけ直したい場面が必ず来る。** 「モニタの文字だけ大きく」がリハで確実に起きる

**コードの重複より、当日の安全を優先する。**

## 4. QRコード（このイシュー固有の作業）

### 4-1. ライブラリを入れる必要がある

**QR を作るライブラリがまだ入っていない。**このイシューで追加する。

```bash
docker compose exec frontend pnpm add qrcode.react
```

**推奨は `qrcode.react` の `QRCodeSVG`。**

```tsx
import { QRCodeSVG } from 'qrcode.react'

<QRCodeSVG value={state.joinUrl} size={400} />
```

⚠️ **必ず SVG 版（`QRCodeSVG`）を使う。** Canvas 版だと 85 インチに拡大したときに**ぼやけて読み取れなくなる**。SVG なら何倍にしても輪郭が保たれる。

> `package.json` を変更するので、**PR にその理由を必ず書くこと。**

### 4-2. どのフェーズで何を出すか

| phase | QR |
| --- | --- |
| `waiting` | 参加用（`joinUrl`）**大きめ** |
| `question` | 参加用（`joinUrl`）右上に固定 |
| `answer` | 参加用（`joinUrl`）右上に固定 |
| `finished` | **アンケート用**（`VITE_SURVEY_URL`） |

**⚠️ `finished` では参加用QRを消す。** アンケートQRに**差し替える**。

> QR が2つ並ぶと、参加者がどちらを読めばいいか分からなくなる。**必ず1画面に1つ。**

### 4-3. 読み取れるか実機で確認する

QR は**小さいと読めない**。そして「読めるサイズ」は画面サイズと距離で決まる。

- リハーサルで、**会場の後ろの席から実際にスマホで読み取る**
- 読めなければサイズを上げる

**この確認をしていない QR は、無いのと同じ。**

## 5. 正解演出

`answer` フェーズで、正答のハイライトに加えて**演出動画**を再生する。

### ⚠️ 動画はまだ存在しない

企画側が制作中。**アプリは「再生する口」を用意するだけ。**

```tsx
// parts/CorrectEffect.tsx
<video src="/effects/correct.mp4" autoPlay muted playsInline />
```

- **動画が無くても画面が壊れないこと。** ファイルが 404 でも正答ハイライトと問題文は正常に出ること
- `muted` を付ける（付けないとブラウザが自動再生をブロックする）
- 音を出すかは PM に確認する（会場の音響と競合する可能性がある）

**動画が来るまでは、仮のファイルか、何も再生しない状態で作る。** 動画待ちで手を止めないこと。

## 6. 実装の順番

**#18 と同じ順番。** ただし Step 0 が増える。

| Step | やること | 動作確認 |
| --- | --- | --- |
| **0** | `features/monitor/` に #18 と同じ骨格を作る | 14秒で4つの phase が切り替わる |
| 1 | `QuestionText` / `ChoiceGrid` / `RemainingTime` / `QuestionNumber` | 出題中の中身が出る |
| 2 | **QRライブラリを入れて `Qr` を作る** | `waiting` でQRが出る |
| 3 | `AnswerView`（正答ハイライト） | 5秒地点で正答が光る |
| 4 | `FinishedView`（アンケートQRへ差し替え） | 14秒地点で参加QRが消える |
| 5 | `CorrectEffect`（動画の口） | 動画が無くても壊れない |
| 6 | **横長レイアウトに整える** | ブラウザを全画面にして確認 |
| 7 | **文字を極端に大きくする** | §7 参照 |

**Step 0〜5 は普通のサイズで作る。** 大きくするのは最後。小さいまま作った方が、画面全体を一度に見られて開発が速い。

## 7. 85インチ対応

### 7-1. サイズを1箇所で変えられるようにする

リハで必ず調整が入る。そのとき**全ファイルを grep して回るのは避けたい。**

```tsx
// 悪い例: 各所に直書き
<p className="text-8xl">...</p>
<p className="text-7xl">...</p>
```

```tsx
// 良い例: 部品の中に閉じ込める
// parts/QuestionText.tsx の中で1回だけサイズを決める
export function QuestionText({ segments }: Props) {
  return <p className="text-8xl leading-tight">{segments.join('')}</p>
}
```

**部品ごとにサイズを1箇所に集める。** これだけで、リハの調整が「そのファイルを開いて数字を変える」で済む。

### 7-2. ブラウザで擬似確認する

手元で 85 インチは再現できないが、**近いことはできる。**

1. ブラウザを全画面（F11）にする
2. **モニタから 3〜4m 離れて見る**
3. 読めなければ、実機ではもっと読めない

完璧ではないが、明らかに小さすぎる状態は見つかる。

### 7-3. リハでのチェックリスト

- [ ] 会場の**一番後ろの席**から問題文が読めるか
- [ ] 選択肢の文字が読めるか
- [ ] 残り秒数が読めるか
- [ ] QRが**後ろの席から**スマホで読み取れるか
- [ ] 長い問題文（`textSegments` を全部連結した最大長）で画面からはみ出さないか

## 8. 落とし穴

### ⚠️ 2×2 の位置関係は「ゲームの根幹」

`four_choice` の 2×2 配置は、**会場の4つのエリアと同じ位置関係**でなければならない。

参加者は画面を見て「左上のエリアだ」と判断して**実際に移動する**。ここが左右反転していたら、200人が間違った場所に歩く。

**Figma の配置を絶対に変えないこと。** 「こっちの方が綺麗」で並べ替えない。

### ⚠️ 「第N問」の分母を出さない

「第3問」とだけ出す。**「第3問 / 全10問」にしない。**

勝ち残りの進み具合を見て**当日その場で出題数を増減する**ので、総数が決まっていない。

そして #18 と同じく、**`state.askedCount` をそのまま出す。自分で数えない。**

### ⚠️ 締切表示

残り0秒で「締切!」に切り替える。**問題文と選択肢は出したまま、タイマー部分だけ差し替える。**

この状態で司会が煽り、裏方が正答表示を押すまで待つ。**画面が変わってはいけない。**

### ⚠️ 未知の `type` で白画面にしない

#18 と同じ。`default` を必ず書く。**当日ここが白くなると、全員が何も見えなくなる。**

### 🚫 `dangerouslySetInnerHTML` 禁止

#18 と同じ。
