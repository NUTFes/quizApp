# GitHub運用ドキュメント整備 草案(決めるべきことの洗い出し)

PR・Issue・レビューまわりのドキュメントを整備するにあたり、**先に決めなければいけないこと**を洗い出したもの。
既存の [Git運用・CI_policy.md](./Git運用・CI_policy.md) が「方針」、このファイルが「方針をドキュメントとして配れる形にするまでに残っている判断」を扱う。

決定したものは `docs/` の確定版へ書き出し、このファイルには判断の経緯だけを残す(AGENTS.md §0 の2層分離)。

作成日: 2026-08-12

### 無いもの(= 今回埋める穴)

1. **`docs/` 側に GitHub運用の確定版ドキュメントが1本も無い。**
   `docs/` はメンバー配布用の完全版のはずだが、Git/GitHub の使い方はどこにも無い。
   メンバーは「clone → ブランチ → PR」の手順を読む場所を持っていない。
2. **レビューについての記述がほぼ皆無。**
   policy に「approve 1人で merge 可」「レビュワーは手元で `mise run up` して動かす」の2行があるだけ。
   レビューする側・される側が読むものが存在しない。**今回の整備の主目的はここ。**

## 1. 決めるべきこと

各項目の「推奨」は現時点でのたたき台。○×を付けていけば決まる形にしてある。

### A. ドキュメントの構成そのもの

**A-1. `docs/` に何本作るか** ★他の判断を左右する分岐点

推奨は3本:

| ファイル | 読む人 | 内容 |
|---|---|---|
| `docs/GitHub運用ガイド.md` | メンバー全員 | ブランチ〜PR〜マージの1周。本体 |
| `docs/レビューガイド.md` | レビューする人・される人 | レビューの作法 |
| `docs/Git入門.md` | Git未経験者 | clone/commit/push とは何か |

3本目の要否は**メンバーの Git 経験次第**で、まとめ役にしか判断できない。
ゼロに近いなら必須、授業等で触っているなら1本目に吸収して2本で足りる。

- [ ] 決定: 何本作るか(2本 / 3本 / その他)

**A-2. `dev_policy/Git運用・CI_policy.md` をどうするか**

確定版を `docs/` へ書き出したあと、このファイルを

- (a) 検討過程の記録としてそのまま残す
- (b) 索引だけにして中身は docs へ移す

推奨は (a)。なぜその方針にしたかの理由(初心者チーム・機械に守らせる)は判断の経緯であり、docs には結論だけを書く。

- [ ] 決定: (a) / (b)

---

### B. Issue まわり

**B-1. テンプレートを何種類にするか** ★分岐点

現状1種類(タスク)。候補は バグ報告 / 質問・相談 / hard(設計を含む)の追加。
**推奨: 「タスク」+「バグ報告」の2種類。** 初心者チームは種類が多いと選べなくなる。

- [ ] 決定: 種類と数

**B-2. Markdown テンプレのままか、Issue Forms(YAML の入力フォーム形式)にするか**

Forms は項目ごとに入力欄が分かれ必須指定もできるため、**空欄のまま起票されるのを防げる**。初心者チームには効く。
ただし書式が YAML になり、まとめ役が後から編集するコストは上がる。

- [ ] 決定: Markdown 継続 / Issue Forms へ移行

**B-3. ラベル体系**

難易度(`good first issue` / `easy` / `hard`)は policy で決定済みだが、**GitHub 上に実際に作る作業がまだ**。

決めること:
- 領域ラベル(`frontend` / `backend` / `infra` / `docs`)を足すか
- 種類ラベル(`bug` / `feature`)を足すか
- **誰が付けるか**(起票者 / まとめ役が起票時に付ける)

増やしすぎると誰も使わなくなる。**難易度3つ + 領域3〜4つに絞る**のが現実的。

- [ ] 決定: ラベル一覧を確定し、GitHub 上に作成する

**B-4. Issue の管理方法**

一覧だけで回すか、GitHub Projects(かんばん)を使うか。マイルストーンで Phase 0〜3 を切るか。
**推奨: Projects の簡易かんばん(Todo / In Progress / Done)は入れる。** 本番日が固定のスケジュールなので、進捗が一目で見える価値が高い。

- [ ] 決定: Projects を使うか / マイルストーンを使うか

**B-5. アサインの決め方**

自己申告(好きな Issue を取る)か、まとめ役が割り当てるか。
初心者は「取っていいのか」で止まりがち。**最初は割当制 → 慣れたら自己申告**の段階運用も選べる。

- [ ] 決定: 自己申告 / 割当制 / 段階運用

### C. PR まわり

**C-1. PRテンプレートを増やすか**

現状3項目。追加候補:

- セルフチェックリスト(`mise run lint` を通した / docs を更新した / 動作確認した)
- **API仕様を変えたかの確認欄** — 開発ルール2「API仕様を変えるときは `docs/API仕様書.md` を先に直す」は、テンプレのチェック項目にしないとまず守られない
- レビュワーに特に見てほしい点

増やしすぎると埋められず形骸化する。**チェックボックス3つ程度**に抑える。

- [ ] 決定: 追加する項目

**C-2. ブランチ名の規約**(食い違いイ)

policy は `feat/issue番号-短い説明`。実績は番号なし。
**推奨: 「Issue があれば番号を入れる」程度の緩さ。** Issue を立てずに直す小修正もあるため。

- [ ] 決定: 番号必須 / Issueがあれば入れる / 番号なし可

**C-3. Draft PR を使うか**

「途中まで書いたけど合ってるか見てほしい」の受け皿になる。初心者チームでは有用。
使うなら「Draft のうちはレビュー不要、Ready にしたら依頼」という**合図の意味**も決める。

- [ ] 決定: 使う / 使わない

**C-4. PR の大きさの上限**

「変更が◯行を超えたら分割を相談」のような目安を置くか。
レビューが回らなくなる最大の原因なので、目安だけでも書く価値がある。

- [ ] 決定: 目安を置くか、置くなら何行

### D. レビュー(今回の主目的・空白地帯)

**D-1. レビュワーを誰がどう決めるか** ★分岐点

選択肢: `CODEOWNERS` ファイルで自動アサイン / PR作成者が手で指名 / Slack で依頼。
policy は「まとめ役+経験があるメンバーをレビュワー既定」とだけ書いている。

**実質まとめ役1人に集中してボトルネックになるのが目に見えている。** 仕組みで分散させる設計が要る。

- [ ] 決定: 方式と、レビュワーになれる人の範囲

**D-2. レビューで何を見て、何を見ないか** ← レビューガイドの核

`docs/CI・コードチェック入門.md` に既に方針が書かれている:

> 機械的に判定できることは全部機械にやらせて、人間のレビューは「動くか・設計がいいか」だけに集中させる

これを**レビュー観点リストに落とす**。「書式の指摘は禁止(CIの仕事)」まで明記すると効く。

- [ ] 決定: 観点リストの内容

**D-3. 動作確認を必須にするか**

policy は「レビュワーは手元で `mise run up` して動かして見る」文化にする、とある。
**必須にするとレビューが重くなって滞留する。**
「画面の変更は必須、バックのロジックだけならコード読みで可」のような線引きを決める。

- [ ] 決定: 必須の範囲

**D-4. コメントの書き方** ← 初心者チームで最重要

決めること:
- **指摘の強度を区別する記法**(例: `must:` 直さないとマージ不可 / `nits:` 好みなので任意 / `ask:` 質問)
- 否定形で書かない等の原則

強度が区別されていないと、初心者は「全部直さないといけない」と受け取って萎縮する。

- [ ] 決定: 記法(prefix の種類と意味)

**D-5. レビューの返し方と再依頼**

修正したらどう知らせるか(コメント返信 / re-request review ボタン)。
レビュワーの指摘に納得できない時にどうするか。

- [ ] 決定: 手順

**D-6. レビューの期限(SLA)**

「依頼から24時間以内に一次反応」のような目安。
無いと PR が滞留し、初心者が待ちぼうけになって手が止まる。

- [ ] 決定: 目安を置くか、置くなら何時間

**D-7. 自分の PR を自分でマージしてよいか**

approve が付いたら作成者がマージするのか、レビュワーがマージするのか。

- [ ] 決定: 作成者 / レビュワー

### E. GitHub 側の設定(ドキュメントを書く前に確定が必要)

**E-1. main ブランチ保護の具体項目**

policy にある3つ: PR必須(approve 1件) / CI通過必須 / 管理者にも適用。
追加で決めること:

- force push の禁止
- マージ後のブランチ自動削除
- **Squash merge 以外を無効化するか**(GitHub 設定で merge commit と rebase merge をオフにできる。オフにしないと「squash に統一」は口頭ルールのまま)
- squash 時のコミットメッセージ既定(PRタイトルにするか)

- [ ] 決定: 設定項目一覧
- [ ] 実施: GitHub UI で設定を入れる

**E-2. CI の必須チェック名**

ブランチ保護では**ジョブ名を指定して必須化**する。現在のジョブ名は `frontend` と `backend`。
ジョブ構成を先に確定しないと、保護設定を入れ直す羽目になる。

- [ ] 決定: 必須にするジョブ名

**E-3. `ci.yml` を policy に合わせるか、policy を `ci.yml` に合わせるか**(食い違いア) ★分岐点

実質「**ESLint / Prettier をいま入れるか**」の判断。
`Git運用・CI_policy.md` の TODO にも「ESLint + Prettier の設定をルートに置き、エディタ設定もコミットする」が未完で残っている。

- [ ] 決定: 今入れる / 後回しにして policy 側を実態に合わせる

### F. 運用の周辺

**F-1. 練習 Issue を用意するか**

policy の TODO にある「clone → ブランチ → 変更 → PR → レビュー → merge を1周する練習 Issue(README に名前を足す等)」。
**ドキュメントを配るだけでは初心者は動けない。** ドキュメント整備とセットで効くので強く推奨。

- [ ] 決定・実施: 練習 Issue を作る

**F-2. 秘密情報のルール**

`ADMIN_TOKEN` / `IMPORT_TOKEN` を PR やログに貼らない、という一文。
認証実装が始まる前に書いておく。

- [ ] 決定: どのドキュメントに書くか

**F-3. AI エージェントに PR を作らせる場合の運用を書くか**

Claude Code が PR を作るなら、人間の PR と同じレビューを通すのか、コミットに `Co-Authored-By` を残すのか。
AGENTS.md がある以上、触れておく価値はある。

- [ ] 決定: 書くか / 書かないか

## 2. 進め方の提案

**E(GitHub設定)を先に確定してから、A〜D のドキュメントを書く。**
ドキュメントは設定の説明を含むため、設定が動くと書き直しになる。

そのうえで、以下の4つが他の判断を左右する分岐点。ここだけ決まれば残りは推奨案で埋めて草案を書ける。

| 分岐点 | 決めること |
|---|---|
| A-1 | `docs/` に何本作るか(メンバーのGit経験次第) |
| B-1 | Issueテンプレの種類 |
| D-1 | レビュワーの決め方(まとめ役のボトルネック回避) |
| E-3 | ESLint / Prettier を今入れるか |
