## 0. この手順書の読み方

#10 と同じ作りです。**動くものを1段ずつ育てます。**

各ステップに次の2つが付いています。

- **✅ 動作確認** … そのステップが終わった時点で、実際に何が確認できるか
- **⚠️ まだ足りない** … なぜ次のステップが必要か

この「⚠️」の部分が本体です。いきなり完成形を写すより、**「なぜこの1行が要るのか」が積み上がる**ほうが、あとで自分で書けるようになります。

### このエンドポイントだけ特別扱いする理由

`GET /api/admin/state` は、**初心者タスク T1〜T7 全部の写経元**になります（[`バックエンド初心者タスク.md`](バックエンド初心者タスク.md)）。つまり、ここに書いたコードの癖が、これから10本以上のエンドポイントに複製されます。

なので判断基準が普通のタスクと違います。

| | 普通のエンドポイント | この1本 |
| --- | --- | --- |
| 短さ | 短いほうがよい | **短さより、読んで真似できること** |
| コメント | 必要な所だけ | **「なぜこう書くか」を1〜2行ずつ** |
| 賢い書き方 | 使ってよい | **使わない。素直な書き方を選ぶ** |

合格判定は「動いた」ではなく、**キンギョ（Gold-Fish2000）が読んで『これを写経すれば T1 が作れる』と言えること**です（#11 ④）。

## 1. 何を作るのか

### ゴール

```bash
curl -s -H "Authorization: Bearer dev-admin-token" http://localhost:3000/api/admin/state
```

で、[`API仕様書.md`](../docs/実装要件/API仕様書.md) §1・§2.1 の形の JSON が返ること。認証が無ければ 401。

### 触るファイル

| ファイル | 中身 |
| --- | --- |
| `backend/internal/event/handler.go`（新規） | `RegisterRoutes` と `getState` ハンドラ |
| `backend/internal/event/model.go`（既存） | 必要なら型を直す。**たぶん直さなくてよい** |
| `backend/cmd/server/main.go` | DB 接続を作り、`event.RegisterRoutes` を1行足す |

`internal/event/model.go` には **もう構造体が両方入っています**（#8 で作成済み）。

```go
type EventState struct { ... }   // DB に保存する形
type State struct { ... }        // API で返す形
```

このステップでやるのは、**この2つの間の詰め替えと、DB から読む処理**です。

### ファイル名を `handler.go` にする理由

[`フォルダ構成_policy.md`](フォルダ構成_policy.md) の規則どおり、**役割で名前を付けます**。`state.go` でも構いませんが、`event` パッケージには今後 `show-question` `reveal` `reset` などの操作系も入るので、**「HTTP の入口はここ」**とわかる `handler.go` のほうが探しやすくなります。

`utils.go` `common.go` `main.go` のような**入れ物の名前は付けないこと**。中身の想像がつかない名前は、無関係なコードを呼び寄せます。

### なぜ `/api/admin/state` なのに `admin` パッケージではないのか

#10 でやった判断と同じ基準です。**「誰の知識か」で決めます。**

| | `admin` に置く場合 | `event` に置く場合 |
| --- | --- | --- |
| 扱う知識 | 管理者画面の都合 | **進行状態（phase・出題中の問題・経過時間）** |
| 今後 `show-question` `reveal` `reset` はどこに行くか | admin | **event** |
| state を組み立てるコードはどこに要るか | — | **event**（SSE 配信でも同じものを使う） |

`state` の中身は「イベントの進行状態」そのものです。**URL が `/api/admin/` で始まることは、置き場所の理由になりません**（`/api/admin/questions` が `question` パッケージに入るのと同じ）。

Issue #11 ②が「触ってよいファイル: `backend/internal/event/` 配下」と指定しているのもこの理由です。

## 2. 先に知っておくこと

#10 と同じく、C・JavaScript・Python の知識から辿れる形で書きます。

### 2-1. 構造体タグ `json:"phase"` とは何か

```go
type State struct {
	Phase      string    `json:"phase"`
	ServerTime time.Time `json:"serverTime"`
}
```

フィールド名の後ろのバッククォート部分を**構造体タグ**といいます。**JSON に変換するときの名前**を指定しています。

なぜ必要か。**Go は「大文字で始まる名前だけが外から見える」**という言語で、JSON 変換ライブラリも例外ではありません。

- `Phase`（大文字始まり）… 変換される
- `phase`（小文字始まり）… **変換されない。JSON に出てこない**

一方、API 仕様書が要求する JSON のキーは `phase`（小文字）です。この食い違いを埋めるのがタグです。

Python の `dataclass` に例えるとこうなります。

```python
@dataclass
class State:
    phase: str          # Python は名前をそのまま使うので、こういう仕組みが要らない
```

Python や JS では変数名とキー名が同じでよいので、この概念自体がありません。**Go は「外から見えるかどうか」を名前の大小で決めた副作用として、この仕組みが必要になった**、と理解しておけば十分です。

タグは文字列なので、**打ち間違えてもコンパイルは通ります。** `json:"phse"` と書いても何も言われず、実行して JSON を見るまで気づけません。ここが一番の事故ポイントです。

### 2-2. なぜ DB 用と API 用で構造体を2つ用意するのか

`model.go` には似た構造体が2つあります。

```go
type EventState struct {          // DB の1行に対応
	ID                uint `gorm:"primaryKey"`
	Phase             string
	CurrentQuestionID *uint
	TimeLimitSec      int
	QuestionStartedAt *time.Time
	RevealedSegments  int
}

type State struct {               // API のレスポンスに対応
	Phase             string             `json:"phase"`
	ServerTime        time.Time          `json:"serverTime"`
	TimeLimitSec      *int               `json:"timeLimitSec"`
	...
}
```

「面倒だから1つにまとめたい」と思うところですが、**まとめられません。** 中身が違うからです。

| | `EventState`（DB） | `State`（API） |
| --- | --- | --- |
| `ID` | ある（主キー） | **無い**（外に出す意味がない） |
| `CurrentQuestionID` | ある（外部キー） | **無い**。代わりに `Question` そのものが入る |
| `ServerTime` | **無い**（保存する値ではない） | ある（毎回 `time.Now()`） |
| `TotalSegments` | **無い** | ある（問題文から毎回数える） |
| `AskedCount` | **無い** | ある（`asked=true` を毎回数える） |
| `TimeLimitSec` が `waiting` のとき | `30`（設定値は残っている） | **`null`** |

**保存する値と、外に見せる値は、そもそも別物です。** 1つにまとめると「DBには要らないがAPIには要る項目」がテーブルに漏れ出したり、逆に `ID` が API に漏れたりします。

これは #13 以降でさらに効いてきます。**同じ状態から、閲覧者向けには `correctChoiceId` を抜いた別の形を作る**必要があるからです（§2.2）。DB の形と API の形を分けておかないと、この分岐が書けません。

> **この見本を写経する人へのメッセージでもあります。** 「DBの構造体をそのまま `c.JSON` に渡す」書き方を1回でも見本に入れると、それが全タスクに複製されて、**正答が閲覧者に漏れる事故**になります。

### 2-3. Go の「ゼロ値」と、`null` を表せない問題 ← ここが最重要

API 仕様書 §1 はこう決めています。

> `timeLimitSec` … **`waiting` / `finished` では `null`**

ところが Go の `int` は **`null` を表せません。** 値を入れなければ **`0`** になります。これをゼロ値といいます。

| 型 | 値を入れなかったときの値 |
| --- | --- |
| `int` | `0` |
| `string` | `""` |
| `bool` | `false` |
| `*int`（ポインタ） | **`nil`** |

C で `int x;` を初期化せずに使うと未定義の値が入りますが、**Go は必ずゼロで埋めます**。安全な代わりに、「値が 0 なのか、まだ入っていないのか」が区別できません。

JS や Python なら `null` / `None` を入れれば済みます。

```python
time_limit_sec = None    # Python: 何でも入る変数なので悩まない
```

Go でこれを表すのが**ポインタ**です。C と同じで、「指す先が無い」状態＝ `nil` を持てます。

```go
TimeLimitSec *int    // nil なら「値が無い」、そうでなければ *TimeLimitSec が値
```

そして JSON に変換すると、**`nil` は `null` になり、キーは残ります。** 実測しました。

```json
{
  "phase": "waiting",
  "serverTime": "...",
  "timeLimitSec": null,
  "questionStartedAt": null,
  "revealedSegments": 0,
  "totalSegments": 0,
  "question": null,
  "askedCount": 0
}
```

`timeLimitSec` `questionStartedAt` `question` が `null` で、**キーは8つとも残っています**。これが §1 の「キーは消えない」という要求そのものです。

### 2-4. `&30` とは書けない

`waiting` 以外のとき、`*int` に値を入れる必要があります。ところがこう書くとコンパイルエラーです。

```go
s.TimeLimitSec = &30            // ❌ リテラルのアドレスは取れない
```

C でも `&30` は書けません。理由も同じで、**アドレスは「メモリ上のどこか」を指すものなので、変数が要る**からです。

```go
limit := es.TimeLimitSec        // いったん変数に入れて
s.TimeLimitSec = &limit         // そのアドレスを渡す
```

`&es.TimeLimitSec` と直接書くこともできます（構造体のフィールドは変数なので）。ただし **`es` が指す実体を後から書き換えると JSON も変わる**ので、慣れるまでは上のように1行挟むほうが安全です。

### 2-5. `omitempty` を付けてはいけない

構造体タグには `omitempty` という指定があり、**値が空ならキーごと消す**という意味です。

```go
TimeLimitSec *int `json:"timeLimitSec,omitempty"`   // ❌ 絶対に付けない
```

これを付けると `waiting` のとき `timeLimitSec` の**キーが消えます**。API 仕様書 §1 は「キーは残る」と決めているので契約違反です。

フロント側は `state.timeLimitSec === null` で分岐する前提なので、キーが消えると `undefined` になり、**分岐が静かに壊れます**（#60 がまさにこの検出の話）。

`omitempty` を使ってよいのは、`response.go` の `details` のように**仕様が「無いときは出さない」と明記している項目だけ**です。

### 2-6. GORM とは何か

`db.First(&es, 1)` のような書き方をします。**SQL を書く代わりに、Go の関数呼び出しで問い合わせる道具**です。

Python の SQLAlchemy、JS の Prisma に相当します。C には対応物がありません（C なら libpq で SQL 文字列を組み立てます）。

実際に何が起きているかはログに出ます。

```
SELECT * FROM "event_states" WHERE "event_states"."id" = 999 ORDER BY "event_states"."id" LIMIT 1
```

**GORM は魔法ではなく、SQL を組み立てて投げているだけ**です。困ったらこのログを見れば、何が起きたか必ずわかります（`db.go` で `logger.Warn` に設定してあるので、遅いクエリとエラーが出ます）。

この見本で使うのは3つだけです。

| 書き方 | 生成される SQL |
| --- | --- |
| `db.First(&es, 1)` | `SELECT * FROM event_states WHERE id = 1 LIMIT 1` |
| `db.First(&q, id)` | 同上（`questions` テーブル） |
| `db.Model(&question.Question{}).Where("asked = ?", true).Count(&n)` | `SELECT count(*) FROM questions WHERE asked = true` |

`Where("asked = ?", true)` の `?` は**プレースホルダ**です。値を文字列連結せずに渡すことで SQL インジェクションを防ぎます。**必ず `?` を使うこと。** 文字列連結で SQL を組み立てないでください。

### 2-6b. `db.First(&es, 1)` の引数と戻り値を分解する

この書き方は Go の標準ライブラリと流儀が違うので、最初に分解しておきます。

```go
if err := db.First(&es, 1).Error; err != nil {
```

3行に開くとこうなります。

```go
result := db.First(&es, 1)   // ① *gorm.DB が返る
err := result.Error          // ② その中の Error フィールドを取り出す
if err != nil {              // ③ 判定
```

**`db.First(...)` はエラーを返しません。** 返すのは `*gorm.DB` そのもので、エラーは `.Error` フィールドから取り出します。メソッドを `.` で繋いで書けるようにするための設計です。

```go
db.Where("asked = ?", true).Order("number").Find(&list)   // 各段が *gorm.DB を返すから繋がる
```

Go の標準ライブラリは `値, err := f()` の形が普通なので、**GORM のこれは例外**です。「GORM は最後に `.Error` を見る」と覚えてください。

#### `if 初期化; 条件` の形

`if` の中でセミコロン区切りにすると、判定の前に文を1つ実行できます。C の `for (初期化; 条件; 更新)` と同じ構造で、C でもこう書きますね。

```c
if ((fp = fopen(path, "r")) == NULL) { ... }
```

こう書く利点は、**`err` の寿命を `if` の中だけに閉じ込められる**ことです。分解した形を2回続けると、2回目は `:=` が使えず `no new variables on left side of :=` で止まります。`if` の中で宣言すれば毎回が別の変数なので、その使い分けを考えずに済みます。

#### 引数 `&es` は三役を担っている

「結果を返すなら引数は要らないのでは」と思うところですが、**結果は戻り値ではなく `&es` に書き込まれます**。C の `scanf` と同じ構造です。

```c
int x;
scanf("%d", &x);      // 戻り値は成否。値は &x に入る
```

Go にジェネリクスが無かった時代に設計されたので、「呼び出し側が決めた型を返す関数」が書けず、**入れ物を先に用意してアドレスを渡す**形になっています。だから `var es EventState` を先に宣言します。

ただし `scanf` より仕事が多く、`&es` は3つの役割を持っています。

| 役割 | 具体例 |
| --- | --- |
| ① **どのテーブルを引くか** | 型が `EventState` → `event_states` テーブル |
| ② 結果の書き込み先 | `es.Phase` に値が入る |
| ③ **主キーが 0 でなければ、それも検索条件になる** | `es.ID == 1` なら `AND id = 1` が足される |

③が事故のもとです。§5 の「変数を使い回さない」を必ず読んでください。

戻り値からは `.Error` のほかに `.RowsAffected`（影響した行数）も取れます。

### 2-7. 「行が無い」をどう判定するか

`db.First` は、行が見つからないとエラーを返します。そのエラーが**どの種類か**を判定するのが `errors.Is` です。

```go
if err := db.First(&es, 1).Error; err != nil {
	if errors.Is(err, gorm.ErrRecordNotFound) {
		// 行が無かった
	}
	// それ以外（接続断など）
}
```

実測すると、`errors.Is(err, gorm.ErrRecordNotFound)` は `true` を返します。

`err == gorm.ErrRecordNotFound` と直接比較しても今は動きますが、**`errors.Is` を使ってください。** エラーは途中で包まれる（`fmt.Errorf("...: %w", err)`）ことがあり、そうなると `==` は false になります。`errors.Is` は包みの中まで見ます。

Python の `except SomeError:` に近い働きだと思えば大きく外しません。

## 3. 実装（1段ずつ）

### Step 1: 固定値を返すだけの `/api/admin/state`

**まず DB を使いません。** ハンドラが呼ばれること・認証が効くこと・ルータに登録できることだけを確かめます。

`backend/internal/event/handler.go`（新規）:

```go
package event

import (
	"net/http"

	"github.com/gin-gonic/gin"

	"github.com/naoto-anzai/quizApp/backend/internal/platform"
)

// RegisterRoutes は event パッケージのエンドポイントを登録する。
// adminToken を受け取って platform.RegisterFunc を返すのは #10 の admin と同じ形。
func RegisterRoutes(adminToken string) platform.RegisterFunc {
	return func(r *gin.Engine) {
		g := r.Group("/api/admin", platform.RequireToken(adminToken))
		g.GET("/state", getState)
	}
}

func getState(c *gin.Context) {
	c.JSON(http.StatusOK, gin.H{"phase": "waiting"})
}
```

`main.go` に1行足します。

```go
r := platform.NewRouter(
	registerEvents,
	admin.RegisterRoutes(adminToken),
	event.RegisterRoutes(adminToken),   // ← これ
)
```

> **`/api/admin` グループを2つ作ってよいのか？** よいです。Gin はルート登録時にミドルウェアの配列を確定させるので、同じプレフィックスのグループが複数あっても互いに干渉しません（#10 の PR で実測済み）。

**✅ 動作確認:**

```bash
curl -i -H "Authorization: Bearer dev-admin-token" http://localhost:3000/api/admin/state   # 200 {"phase":"waiting"}
curl -i http://localhost:3000/api/admin/state                                              # 401
```

**⚠️ まだ足りない:** 中身が嘘。DB を見ていない。

### Step 2: `main.go` で DB につなぐ

いまの `main.go` は **DB に一度も接続していません**（#9 で `platform.NewDB` は作ったが、まだ誰も呼んでいない）。

```go
func main() {
	adminToken := os.Getenv("ADMIN_TOKEN")
	if adminToken == "" {
		log.Fatal("ADMIN_TOKEN が設定されていません")
	}

	// DB 接続は起動時に1回だけ作る。
	// 失敗したら起動を止める。ADMIN_TOKEN と同じ考え方で、
	// 「サーバーが立ち上がった＝前提は満たされている」状態にする。
	db, err := platform.NewDB()
	if err != nil {
		log.Fatalf("DB に接続できません: %v", err)
	}

	r := platform.NewRouter(
		registerEvents,
		admin.RegisterRoutes(adminToken),
		event.RegisterRoutes(db, adminToken),   // db を渡す形に変える
	)
	...

```

`RegisterRoutes` の側も受け取ります。

```go
func RegisterRoutes(db *gorm.DB, adminToken string) platform.RegisterFunc {
	return func(r *gin.Engine) {
		g := r.Group("/api/admin", platform.RequireToken(adminToken))
		g.GET("/state", func(c *gin.Context) { getState(c, db) })

```

> **なぜ `db` をグローバル変数にしないのか。** 楽ですが、テストで差し替えられなくなり、「どの関数が DB を使うのか」がコードから読めなくなります。**引数で渡すと、依存が関数の形に出ます。** これは #10 で `adminToken` を引数にしたのと同じ理由です。

**✅ 動作確認:** `docker compose logs backend` に DB のエラーが出ず、起動すること。`DATABASE_URL` を空にして起動すると落ちること。

**⚠️ まだ足りない:** 接続しただけで、まだ読んでいない。

### Step 3: `event_states` を1行読む

`event_states` は **必ず1行しかない**テーブルです。マイグレーションで `CHECK (id = 1)` の制約が付いていて、初期行も入っています。

```sql
CREATE TABLE event_states (
	...
	CONSTRAINT event_states_singleton CHECK (id = 1)
);
INSERT INTO event_states (id) VALUES (1);
```

なので **`id = 1` を決め打ちで読みます**。

```go
func getState(c *gin.Context, db *gorm.DB) {
	// event_states は id=1 の1行しか無い(migration の CHECK 制約で保証)。
	var es EventState
	if err := db.First(&es, 1).Error; err != nil {
		platform.RespondError(c, http.StatusInternalServerError, "INTERNAL", "状態を読めませんでした")
		return
	}

	c.JSON(http.StatusOK, State{
		Phase:      es.Phase,
		ServerTime: time.Now(),
	})
}
```

**✅ 動作確認:**

```bash
curl -s -H "Authorization: Bearer dev-admin-token" http://localhost:3000/api/admin/state
```

→ `phase` が DB の値（初期状態なら `waiting`）になり、キーが8つとも出ること。

ここで **`timeLimitSec` `questionStartedAt` `question` が `null`、`revealedSegments` `totalSegments` `askedCount` が `0`** になっているはずです。何も代入していないのに仕様どおりの形になるのは、§2-3 のゼロ値のおかげです。

**⚠️ まだ足りない:** `phase` が `question` になっても中身が空のまま。

### Step 4: phase による null 化 ← 見本の肝

**ここが初心者が最も間違えるところ**なので、見本として一番丁寧に書きます。

```go
// buildState は DB の状態(EventState)を API の形(State)に詰め替える。
//
// ⚠️ ここが仕様の要:
// phase が waiting / finished のとき、出題に関する項目は null / 0 になる。
// ただし【キーは消さない】(API仕様書 §1)。フロントは
//   state.question === null
// で分岐するので、キーごと消えると undefined になって分岐が壊れる。
// だから omitempty は使わず、「値を入れない」ことで null にする。
func buildState(es EventState) State {
	s := State{
		Phase:      es.Phase,
		ServerTime: time.Now(),
	}

	// 出題していない phase では、ここで返して終わり。
	// TimeLimitSec などはポインタなので nil のまま = JSON では null になる。
	if es.Phase == "waiting" || es.Phase == "finished" {
		return s
	}

	// ここから先は question / answer phase のときだけ。
	limit := es.TimeLimitSec          // *int に入れるには変数が要る(&30 とは書けない)
	s.TimeLimitSec = &limit
	s.QuestionStartedAt = es.QuestionStartedAt
	s.RevealedSegments = es.RevealedSegments

	return s
}
```

ハンドラ側はこうなります。

```go
c.JSON(http.StatusOK, buildState(es))
```

> **なぜ関数に切り出すのか。** SSE（#14）でも**まったく同じ組み立て**が必要になるからです。ハンドラの中に書くと、SSE 側にコピーされて二重管理になります。**「HTTP のことをする部分」と「状態を組み立てる部分」を分ける**、というのが写経してほしい形です。

**✅ 動作確認:** DB を直接いじって phase を変え、両方の形を見ます。

```bash
docker compose exec db psql -U quiz -d quiz -c "UPDATE event_states SET phase='question', question_started_at=now(), revealed_segments=2 WHERE id=1;"
curl -s -H "Authorization: Bearer dev-admin-token" http://localhost:3000/api/admin/state

docker compose exec db psql -U quiz -d quiz -c "UPDATE event_states SET phase='waiting', question_started_at=NULL, revealed_segments=0 WHERE id=1;"
curl -s -H "Authorization: Bearer dev-admin-token" http://localhost:3000/api/admin/state
```

`question` のとき `timeLimitSec: 30`、`waiting` のとき `timeLimitSec: null` になり、**どちらもキーは8つ**であること。

**⚠️ まだ足りない:** `question` が常に `null`。出題中の問題を読んでいない。

### Step 5: 出題中の問題を引く

`event_states.current_question_id` が問題を指しています。**`null` のこともある**（まだ何も出題していない）ので、そこを必ず確認します。

```go
	// 出題中の問題を読む。current_question_id は NULL のことがある
	// (phase が question でも、まだ問題を選んでいない状態)。
	var q *question.Question
	if es.CurrentQuestionID != nil {
		var found question.Question
		if err := db.First(&found, *es.CurrentQuestionID).Error; err != nil {
			platform.RespondError(c, http.StatusInternalServerError, "INTERNAL", "問題を読めませんでした")
			return
		}
		q = &found
	}
```

`*es.CurrentQuestionID` の `*` は、**ポインタの指す先を取り出す**という C と同じ意味です。`nil` のときにこれをやると実行時に落ちる（nil ポインタ参照）ので、**必ず `!= nil` の中で書きます**。

`buildState` に渡します。

```go
func buildState(es EventState, q *question.Question) State {
	...
	s.Question = q     // nil ならそのまま null になる
	return s
}
```

```bash

curl -s -H "Authorization: Bearer dev-admin-token" http://localhost:3000/api/admin/state
```

→ `question` に問題が入り、**`correctChoiceId` も含まれている**こと（管理者向けなので正しい。§2.1）。

**⚠️ まだ足りない:** `totalSegments` と `askedCount` が 0 のまま。

	if q != nil {

### Step 7: `askedCount` を数える

「今何問目か」です。API 仕様書 §1 はこう決めています。

> `asked` が `true` の問題を数えた値で、`asked` から**毎回導出する**（この数を別途保存しない。二重管理を避けるため）

```go
	// askedCount は asked=true の件数から毎回数える(API仕様書 §1)。
	// カウンタを別途持たないのは、show-question をやり直したときや
	// reset のときに、保存した数と実際がずれるのを避けるため。
	var askedCount int64
	if err := db.Model(&question.Question{}).Where("asked = ?", true).Count(&askedCount).Error; err != nil {
		platform.RespondError(c, http.StatusInternalServerError, "INTERNAL", "出題数を数えられませんでした")
		return
	}
```

`Count` が受け取るのは **`int64`** です。`State.AskedCount` は `int` なので変換します。

```go
	s.AskedCount = int(askedCount)
```

> **`int` と `int64` は別の型**で、Go は自動変換しません。C なら暗黙に変換されるところですが、Go は「値が壊れる可能性のある変換」を必ず明示させます。

**✅ 動作確認:**

```bash
docker compose exec db psql -U quiz -d quiz -c "UPDATE questions SET asked=true WHERE number<=3;"
curl -s -H "Authorization: Bearer dev-admin-token" http://localhost:3000/api/admin/state
```

→ `askedCount: 3` になること。

**⚠️ まだ足りない:** エラーの扱いが雑（全部 500 `INTERNAL`）。

### Step 8: エラーを仕分ける

## 5. 落とし穴

### 🚫 DB の構造体をそのまま `c.JSON` に渡さない

```go
c.JSON(http.StatusOK, es)     // ❌ 絶対にやらない
```

いまは「たまたま似ている」だけです。#13 で閲覧者向け `GET /api/state` を作るとき、**`correctChoiceId` と `explanation` を消した別の形**が必要になります（§2.2 原則2・3'）。DB の構造体を直接返す書き方が見本に入っていると、それが写経されて**正答が参加者に配信されます**。

このリポジトリは public で、当日は約200人が同じ SSE を受け取ります。**隠すのはサーバー側で、フロントで隠すのでは間に合いません。**

### 🚫 `omitempty` を付けない

§2-5 のとおり。`waiting` のときにキーが消えて、フロントの分岐が静かに壊れます。

### 🚫 `askedCount` をカラムとして保存しない

`asked` から毎回数えます。保存すると、`show-question` のやり直し・`reset`・問題の削除のたびに更新漏れが起き、**当日「第4問」の次が「第4問」になる**ような壊れ方をします。

### 🚫 `First` に渡す変数を使い回さない

§2-6b ③のとおり、GORM は**渡した構造体の主キーが 0 でなければ、それも検索条件に足します**。1回読んだ変数をもう一度使うと、条件が2つになります。

実測（生成された SQL）:

```
var q question.Question
db.First(&q, 1)   → SELECT ... WHERE id = 1                 q.ID = 1 になる
db.First(&q, 2)   → SELECT ... WHERE id = 2 AND id = 1      ← 絶対に成立しない
                     結果: record not found
```

**`id = 2 かつ id = 1`** という条件になり、`record not found` が返ります。エラーの文面は「見つからない」なので、**「2問目が存在しない」と誤読します**。原因にたどり着くのが非常に難しい種類のバグです。

正しい書き方は、読むたびに新しく宣言することです。

```
var q1 question.Question
db.First(&q1, 1)   → WHERE id = 1
var q2 question.Question
db.First(&q2, 2)   → WHERE id = 2    ← 正常
```

`getState` は毎回 `var es` `var found` を新しく宣言しているので安全です。**危ないのはループの中で1つの変数を使い回すパターン**なので、#12 以降で問題一覧を回すときは特に注意してください。

### ⚠️ コンテナのタイムゾーンは UTC

実測しました。

```
コンテナ: Sun Aug 23 04:42:46 UTC 2026   TZ 未設定
ホスト  : Sun Aug 23 13:42:46 JST 2026
```

Go の `time.Now()` はコンテナのタイムゾーンに従うので、**`serverTime` は `"2026-08-23T04:42:46.123Z"` の形になります。** API 仕様書 §1 の例は `+09:00` 表記ですが、どちらも同じ瞬間を指す正しい ISO 8601 で、フロントの `new Date(...)` はどちらも解釈できます（時計ずれの補正は差分計算なので影響しません）。

ただし **ログを目視するときに9時間ずれて見える**ので、当日の障害対応で混乱します。`docker-compose.yml` に `TZ=Asia/Tokyo` を足すかどうかは PM 判断。**#11 の範囲外**なので、この手順書では変えません。

### ⚠️ `current_question_id` は `null` になりうる

`phase` が `question` でも `null` のことがあります（マイグレーションの `ON DELETE SET NULL` で、問題が消えると自動で `null` になる）。**`*es.CurrentQuestionID` を `nil` チェックなしで書くと落ちます。**

### ⚠️ `reset` で `current_question_id` を `NULL` に戻す必要がある

これは #11 ではなく **#12（進行制御API）の話**ですが、ここに書いておきます。`reset` が `phase` だけ戻して `current_question_id` を残すと、`waiting` なのに問題が紐づいたままになります。いまの `buildState` は `phase` を見て切るので JSON は正しくなりますが、**DB の状態としては嘘**なので、#12 で必ず `NULL` に戻すこと。

### ⚠️ 認証を付け忘れない

`/api/admin/state` には **`correctChoiceId` が入っています**。グループ経由で登録すれば自動で付きますが、`r.GET("/api/admin/state", ...)` と直接書くと認証を回避できます（#10 の PR で実測済み）。**必ず `g.GET` を使うこと。**

### 7-1. 「200 が返るのに、直したコードが反映されない」

**一番最初に引っかかるのがこれです。**

air はソースを保存するたびに再ビルドしますが、**ビルドに失敗すると、前回ビルドが成功したバイナリをそのまま動かし直します。** サーバーは止まりません。ルートも登録済みのまま。だから 200 が返る。**でもそれは、いま書いたコードではありません。**

`docker compose logs backend` の実例:

```
building...
internal/event/handler.go:20:30: missing key in map literal
failed to build, error: exit status 1
running...                                   ← 古いバイナリを起動し直しただけ
[GIN-debug] GET /api/admin/state --> ...event.getState
[GIN] 200 | 5.8µs | GET "/api/admin/state"   ← 200 が返る
```

覚えることは1つです。

> **200 が返ってきたことは、自分のコードが動いた証拠にならない。**

見る場所はここです。

| ログ | 意味 |
| --- | --- |
| `failed to build, error: exit status 1` | **今のコードは動いていない。** すぐ上にエラー行と行番号が出ている |
| `building...` の後にエラーが無く `running...` | 反映された |

**別の端末で `docker compose logs -f backend` を開きっぱなしにしておくこと。** 保存するたびにビルドの成否が流れるので、curl を打つ前に分かります。これをやるかどうかで、詰まる時間が何倍も変わります。
