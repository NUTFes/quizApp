# API設計完了の基準

> 2026-08-05 作成。「APIの設計はどこまで決めれば完成と言えるのか?」への回答。
> `docs/api.md` を書くとき・レビューするときの合格基準として使う。

## 完成の定義

**API設計の完成 = 「フロント担当が、バックエンドに一切質問せずに実装できる文書がある」こと**

API仕様書(`docs/api.md`)はフロント班とバック班の**契約書**。

- 読んだだけで両班が独立に作業を始められる → **完成**
- 実装中に「これどうなるんだっけ?」と聞きに行く必要がある → **未完成**

## API 1本につき決めること(6点セット)

| # | 決めること | 例 |
|---|---|---|
| ① | メソッド + パス(エンドポイント) | `POST /api/admin/show-question` |
| ② | 何をするAPIか(1行説明) | 指定した問題を出題状態にする |
| ③ | リクエストの中身(送るJSON) | `{"questionId": 5}` |
| ④ | 成功時のレスポンス(返ってくるJSON) | 下の実例参照 |
| ⑤ | 失敗時のレスポンスと条件 | 存在しないID → 404、認証なし → 401 など |
| ⑥ | 副作用(このAPIの結果、他に何が起きるか) | 全端末へSSEで新しい `state` が配信される |

「APIの名前」という独立した概念はなく、**①のメソッド+パスがそのままAPIの名前**になる。

## 実例: 「この問題を出題する」APIの完成形

`docs/api.md` に書かれるべき姿のサンプル。全APIをこの粒度で書く。

---

### POST /api/admin/show-question

指定した問題を出題状態にする(phaseを `question` に切り替え、タイマーを開始する)。

**認証**: 管理者ログイン済みであること(Cookie)。

**リクエスト**:

```json
{ "questionId": 5 }
```

**成功レスポンス** `200 OK` — 更新後の状態を返す:

```json
{
  "phase": "question",
  "currentQuestionId": 5,
  "questionStartedAt": "2026-09-13T13:05:00+09:00",
  "timeLimitSec": 30,
  "revealedSegments": 1
}
```

**エラーレスポンス** — 形は全API共通で `{"error": {"code", "message"}}`:

| 状況 | ステータス | code |
|---|---|---|
| ログインしていない | 401 | `UNAUTHORIZED` |
| questionId が存在しない | 404 | `QUESTION_NOT_FOUND` |
| phase が `finished` のとき | 409 | `INVALID_PHASE` |

**副作用**: 全接続クライアントへSSEの `state` イベントが配信される(中身は宛先ごとに出し分け → SSE仕様の節を参照)。

---

### なぜこれで「完成」なのか(6点との対応)

- **③があるから** バック班は「questionIdという数値を1個受け取ればいい」と分かり、フロント(管理者画面)班は送るコードを今すぐ書ける
- **④があるから** フロント班は**バックが存在しなくても**このJSONをモックデータにして画面を作れる。ここが並行開発の肝
- **⑤があるから** 「同期ボタンを押したけどエラーだった時、画面に何を出す?」までフロントが実装できる。エラー設計を省くと、当日「なんか動かない(理由は画面に出ない)」になる
- **⑥があるから** 「このボタンを押すとモニタも切り替わる」という**アプリ全体の因果関係**が文書上で追える。このアプリはRESTのレスポンスよりSSE配信のほうが主役なので、⑥は特に重要

## `docs/api.md` 全体としての完成条件

以下が揃った時点で完成宣言できる:

1. **REST API 全8本**を上の実例と同じ粒度で書く
   (API・データ設計policyでリストアップ済み: state / questions / questions/:id / show-question / advance-text / show-answer / reset / sync-questions)
2. **SSEの仕様**: イベント名(`state` / `timer`)と、**3宛先(管理者/モニタ/スマホ)それぞれのJSON実例**。
   「スマホに届くJSONには `correctChoiceId` というキーがそもそも無い」ことをJSON例で見せる
3. **共通ルール**を冒頭に1回だけ書く: エラーの形(`{"error": {"code", "message"}}`)・日時はISO 8601・認証方式

## 決めなくていいこと(スコープ外)

- Goの内部でどう実装するか
- DBのテーブル構造の細部
- 画面のデザイン

APIは「境界の約束」なので、境界の外(各陣営の内側)は各自の自由。
