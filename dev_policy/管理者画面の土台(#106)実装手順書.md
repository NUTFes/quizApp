## 3. STEP 2 — `/images` をプロキシに足す（PR #99 に無い追加）

コピーしてきた `vite.config.ts` には `/api` しか無い。**`/images` を足す。**

```ts
server: {
  host: true,
  port: 5173,
  proxy: {
    '/api':    { target: 'http://backend:3000', changeOrigin: true },
    '/images': { target: 'http://backend:3000', changeOrigin: true },   // ★追加
  },
},
```

### なぜ必要か

`docker-compose.yml` の `VITE_API_URL` を空（相対パス）にすると、`fetch` は
Vite が `/api` を転送してくれるので届く。しかし **画像は `fetch` ではなく `<img src>`** で、

```tsx
// frontend/src/features/*/parts/ChoiceCard.tsx
src={choice.imageUrl ?? ...}      // BASE を前置していない
```

`/images/q5.png` はページのオリジン `localhost:5183` に解決され、**Vite 開発サーバーが 404 を返す**。
本番は nginx が同一オリジンで配信するので影響しない（→ #100）。
**開発環境だけが壊れる**ので気づきにくい。

## 4. STEP 3 — 認証の仕組み

### 4-1. トークンの置き場所

```ts
// frontend/src/lib/config.ts
export const getAdminToken   = () => localStorage.getItem('adminToken') ?? ''
export const setAdminToken   = (token: string) => localStorage.setItem('adminToken', token)
export const clearAdminToken = () => localStorage.removeItem('adminToken')
```

`localStorage` に置くのは、**リロードしても再入力不要にするため**（当日の事故防止 → API仕様書 §0）。
ログイン・セッション・有効期限は無い。サーバーは環境変数の固定文字列と突き合わせるだけ。

### 4-2. 画面の4状態

```
              トークンが localStorage にあるか？
                     │
        ┌────────────┴────────────┐
       無い                        有る
        │                           │
   needsLogin                   checking  ──verify()──┐
   (LoginView)                                        │
        │                        ┌───────────────┬────┴────┐
        └── 入力成功 ────────▶  ready          needsLogin  unreachable
                                (OperationPanel) (401)      (通信不能)
```

**`AdminPage` は分岐だけを持つ。** 操作盤の中身は #107 以降。

### ⚠️ 401 と「サーバーに繋がらない」を必ず区別する

```ts
.catch((e) => {
  if (e instanceof ApiError && e.status === 401) {
    setAuthStatus('needsLogin')
    clearAdminToken()      // 分かり切った失敗をLoginViewで繰り返さない
    return
  }
  setAuthStatus('unreachable')   // 通信自体ができない
})
```

**当日この2つを取り違えると復旧できない。**
「トークンが違う」と思ってトークンを入れ直し続けている間、実際はサーバーが落ちている、が最悪。

### ⚠️ `verify()` は起動時に1回だけ

```ts
useEffect(() => { ... }, [])     // 依存配列は空
```

`cancelled` フラグでクリーンアップすること（応答が遅れて返ってきたときに
すでに別の状態になっているのを上書きしない）。

## 5. STEP 4 — エラー文言

```ts
// frontend/src/features/admin/errorMessages.ts
const ERROR_MESSAGES: Record<string, string> = {
  UNAUTHORIZED: 'トークンが正しくありません。入力し直してください。',
  ...
}
export const toMessage = (code: string): string =>
  ERROR_MESSAGES[code] ?? '処理に失敗しました。もう一度お試しください。'
```

### 🚫 サーバーの `message` を画面に出さない

API仕様書 §0 が明記している。

> `message` は**開発者向けデバッグ文言**。表示に使わない（バックが自由に変えてよい）。
> `code` は機械用。**フロントは code で分岐**し、ユーザーに見せる日本語はフロント側で持つ。

`ApiError.code` か `.status` で分岐する。

**Figmaデザインは既にある。実装がそれと合っているかを、レビュワーが目で確認できるようにする。**

3. `App.tsx` にルートを足す（`import.meta.env.DEV` の分岐の中）

### #106 で並べるもの

`LoginView` の取りうる状態を全部:

- 初期（未入力）
- 入力中 / 送信中（`busy`）
- エラー: トークンが違う（401）
- エラー: サーバーに繋がらない
- `checking`（トークン確認中）
- `unreachable`

### ⚠️ 注意点

- **`parts/PreviewFrame` はそのまま使えない。** あれは端末サイズの枠（390×844 等）で、
  管理者画面はデスクトップ幅。枠に押し込めず、幅を持たせて並べること
- **パネルは `props` で状態を受け取る純粋な表示部品にする。**
  `localStorage` や `fetch` に依存すると devプレビューが描画できない。
  通信は呼び出し側（`AdminPage` / 後の `OperationPanel`）に寄せる。
  **これは設計としても正しい方向**で、#107 以降の全パネルに効いてくる
- 🔒 **モックにトークンを書かない。** `dev-admin-token` のような開発用の値でも埋め込まない
- 🔒 **モックに本番の問題データ・正答を入れない。** このリポジトリは公開されている

## 9. 落とし穴

### 🚫 `dangerouslySetInnerHTML` は使わない

**この画面は特に危険。** `localStorage` にトークンが入っているので、
XSS が起きるとトークンごと盗まれる。

### 🚫 トークンを `console.log` しない

デバッグが必要なら `token.length` を出す。

### ⚠️ `handleSubmit` に `e.preventDefault()` を忘れない

`<form onSubmit>` で忘れると**ページがリロードされて**、入力もエラー表示も全部消える。

### ⚠️ push 先に注意

このブランチは upstream を**わざと外してある**。
`git worktree add -b <新> <dir> origin/main` の形は、新ブランチの追跡先を
`origin/main` にしてしまい、`git push` が **main へ直接 push しようとする**。

```bash
git push -u origin feat/106-admin-base     # 初回は必ず -u で明示
```
