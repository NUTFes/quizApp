# 敗者復活フェーズ(#120) 実装手順書

Issue #120「【敗者復活1/7】revival-video / revival-entry フェーズと POST /api/admin/revival を追加する」の実装手順書。

敗者復活シリーズの土台として、サーバーが「動画を見せている」「参加を受け付けている」という2つの状態を持ち、管理者操作で切り替えられるようにする。

> 前提: `origin/main` の #108（管理者画面の進行操作）と #109（問題一覧パネル）がマージ済みであること。

---

## 0. このIssueでできるようになること

現在の進行は次の4フェーズで表している。

```text
waiting → question → answer → question → … → finished
```

ここへ敗者復活用の2フェーズを追加する。

```text
answer ── revival {"to":"video"} ──> revival-video
          revival {"to":"entry"} ──> revival-entry
          show-question ─────────────> question（次の問題）
```

- `revival-video`: モニタで敗者復活動画を流す段階
- `revival-entry`: Googleフォームで敗者復活の参加を受け付ける段階

このIssueは**状態とAPIだけ**を作る。動画の配信、画面、URL設定、管理者ボタンは後続Issue #121〜#126で実装する。

## 1. なぜ `reset` を使わず、新しいAPIを作るのか

`reset` は画面を待機・終了へ変えるだけのAPIではない。次の処理で全問題の `asked`（出題済みか）を `false` に戻す。

```go
tx.Model(&question.Question{}).
    Where("asked = ?", true).
    Update("asked", false)
```

`askedCount`（今何問目か）は、`asked=true` の件数から毎回計算している。したがって第8問のあとに `reset` を使うと `askedCount=0` になり、次の問題が第1問として表示される。

敗者復活はゲーム終了ではなく途中の演出なので、専用APIは**`event_states.phase` だけを更新する**。これなら出題済み記録が8件のまま残り、次の未出題問題を出すと第9問になる。

## 2. 先にAPI契約と画面要件を直す

このリポジトリでは、API仕様書がフロントとバックの「契約書」。コードを先に変えると、後続Issueの担当者が古い4フェーズの契約を見て実装してしまうため、先に次を確定する。

### 2-1. `phase` の値

```text
waiting | question | answer | revival-video | revival-entry | finished
```

### 2-2. 遷移

- `POST /api/admin/revival {"to":"video"}` で `revival-video`
- `POST /api/admin/revival {"to":"entry"}` で `revival-entry`
- どのフェーズからでも呼べる
- `revival-entry` から既存の `show-question` を呼ぶと次の問題へ戻る
- 既存の `reset` は新フェーズからでも呼べる

### 2-3. 敗者復活中のstate

敗者復活中は問題を出していない。`waiting` / `finished` と同じく、問題関連の値を空にする。

| 項目 | 値 |
| --- | --- |
| `question` | `null` |
| `answer`（閲覧者向け） | `null` |
| `questionStartedAt` | `null` |
| `timeLimitSec` | `null` |
| `revealedSegments`（管理者向け） | `0` |
| `totalSegments`（管理者向け） | `0` |
| `askedCount` | **変更しない** |

`askedCount` まで0にしてはいけない。敗者復活は出題履歴を消す操作ではないため、たとえば第8問の直後なら `8` のまま返す。

### 2-3-1. 敗者復活中の問題一括投入は禁止する

`PUT /api/admin/questions` は全問題を削除して作り直すため、既存の `asked` をすべて失う。従来は `question` / `answer` のときだけ409で止めていたが、新しい敗者復活フェーズを条件へ加えないと、休憩中の再投入で `askedCount` が0に戻る。

禁止フェーズを4つ並べるのではなく、**`waiting` / `finished` のときだけ許可する**。許可側を限定すれば、将来さらにフェーズが増えて条件の更新を忘れても、問題データを壊す操作は自動的に拒否される。

```go
func canReplaceQuestions(phase string) bool {
    return phase == "waiting" || phase == "finished"
}
```

`question` / `answer` / `revival-video` / `revival-entry` と未知のphaseでは `false` になることを表形式テストで固定する。

### 2-4. 画面に出すもの

このIssueでは描画しないが、後続Issueが迷わないよう画面仕様を確定版へ書く。

| フェーズ | モニタ | スマホ |
| --- | --- | --- |
| `revival-video` | 敗者復活動画 | 「会場モニターをご覧ください」 |
| `revival-entry` | 敗者復活フォームのQR | 敗者復活フォームを開くリンク |

どちらも通常の参加用QR・問題番号・問題文・選択肢・タイマー・アンケートQRは表示しない。

## 3. 新しいフェーズを「問題なしstate」として扱う

`buildState` と `buildViewerState` は、DBの値をAPIレスポンスへ変換する関数。現在は `waiting` / `finished` のときだけ、初期値の `nil` / `0` のまま早く返している。

条件へ新しい2フェーズを加える。

```go
if es.Phase == "waiting" || es.Phase == "finished" ||
    es.Phase == "revival-video" || es.Phase == "revival-entry" {
    return s
}
```

閲覧者向けも同じ条件にする。構造体のJSONタグには `omitempty` が無いため、値を入れずに返せばキーは消えず `null` / `0` になる。

> `CurrentQuestionID` はDBに残っていてもよい。レスポンス組み立て時のearly return（後続処理をせず早く返すこと）により、以前の問題は外へ出ない。次に `show-question` を呼べば新しい問題IDで上書きされる。

### 自動テスト

`revival-video` / `revival-entry` の両方について、管理者向けと閲覧者向けを表形式のテストで確認する。

- `phase` は指定した値のまま
- `askedCount` は例として8のまま
- 問題、時刻、制限時間は `nil`
- 管理者向けの公開セグメント数と総セグメント数は0
- 閲覧者向けの `answer` は `nil`

このテストにはHTTPやDBを使わない。stateの出し分けという1つの責務だけを速く確認でき、CIでも外部サービスなしで動く。

## 4. `POST /api/admin/revival` を追加する

`progress.go` にハンドラを追加する。

```go
func revival(c *gin.Context, db *gorm.DB, joinURL string, b *sse.Broadcaster) {
    var req struct {
        To string `json:"to" binding:"required,oneof=video entry"`
    }

    if err := c.ShouldBindJSON(&req); err != nil {
        platform.RespondError(c, http.StatusBadRequest, "INVALID_REQUEST", "リクエストの形が不正です")
        return
    }

    var es EventState
    if ok := readEventState(c, db, &es); !ok {
        return
    }

    if err := db.Model(&es).Update("phase", "revival-"+req.To).Error; err != nil {
        platform.RespondError(c, http.StatusInternalServerError, "INTERNAL", "event_states を更新できませんでした")
        return
    }

    broadcastState(db, joinURL, b)
    getState(c, db)
}
```

### この形で守れること

- `binding:"required,oneof=video entry"` により、未指定や `hoge` は400になる
- フェーズを事前確認しないため、どのフェーズからでも呼べる
- `Update("phase", ...)` はphase列だけを更新するため、`questions.asked` に触れない
- 成功後は既存の状態変更APIと同じく、SSE配信してから更新後stateを返す

`routes.go` の管理者グループへ登録する。`RequireToken` がグループ全体に掛かっているため、新しい認証処理は書かない。

```go
g.POST("/revival", func(c *gin.Context) { revival(c, db, joinURL, b) })
```

## 5. 検証する

### 5-1. コードチェック

```bash
mise run lint
```

### 5-2. 実APIの通し確認

```bash
mise run up
mise run db:migrate
mise run db:seed
```

まず1問を出し、`askedCount=1` にする。

```bash
curl -sS -X POST http://localhost:3000/api/admin/show-question \
  -H 'Authorization: Bearer dev-admin-token' \
  -H 'Content-Type: application/json' \
  -d '{"questionId":1}'
```

動画フェーズへ移る。

```bash
curl -sS -X POST http://localhost:3000/api/admin/revival \
  -H 'Authorization: Bearer dev-admin-token' \
  -H 'Content-Type: application/json' \
  -d '{"to":"video"}'
```

次を確認する。

- HTTP 200
- `phase` が `revival-video`
- `askedCount` が `1` のまま
- `question` / `questionStartedAt` / `timeLimitSec` が `null`
- `revealedSegments` / `totalSegments` が `0`

同様に `{"to":"entry"}` を送り、`revival-entry` を確認する。閲覧者向けも確認する。

`revival-entry` のまま問題の一括投入を試し、本番途中の出題履歴を消せないことを確認する。

```bash
curl -sS -i -X PUT http://localhost:3000/api/admin/questions \
  -H 'Authorization: Bearer dev-admin-token' \
  -H 'Content-Type: application/json' \
  -d '{"questions":[{"sourceRow":2,"number":1,"type":"two_choice","difficulty":"easy","textSegments":["地球は青い"],"imageUrl":null,"choices":[{"id":"A","text":"○","imageUrl":null},{"id":"B","text":"×","imageUrl":null}],"correctChoiceId":"A","explanation":null}]}'

curl -sS http://localhost:3000/api/admin/state \
  -H 'Authorization: Bearer dev-admin-token'
```

一括投入がHTTP 409かつ `error.code=INVALID_PHASE` になり、その後も `phase=revival-entry` と `askedCount=1` が保持されること。

```bash
curl -sS 'http://localhost:3000/api/state?view=phone'
curl -sS 'http://localhost:3000/api/state?view=monitor'
```

両方で `question` と `answer` が `null`、`askedCount` が `1` のままであること。モニタ向けには契約どおり `joinUrl` のキーが残るが、表示するかどうかはフロントの責務。

不正値を確認する。

```bash
curl -sS -i -X POST http://localhost:3000/api/admin/revival \
  -H 'Authorization: Bearer dev-admin-token' \
  -H 'Content-Type: application/json' \
  -d '{"to":"hoge"}'
```

HTTP 400かつ `error.code` が `INVALID_REQUEST` になること。

最後に `revival-entry` から別の問題を出し、`askedCount=2` になること、さらに敗者復活フェーズから `reset` が従来どおり動いて `askedCount=0` になることを確認する。
