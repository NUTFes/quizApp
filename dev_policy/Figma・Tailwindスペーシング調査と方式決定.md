## 0. この文書の位置づけ

移行手順書の **Phase 1（調査）と Phase 2（方式決定）を、2段階に分けて実行するための作業文書**である。

トークンの命名方式（後述の A / B / C）を**先に決めてから調査すると、都合のいい数え方に引きずられる**。逆に、数え終わってから決めれば、方式は実データから導かれる。

したがって順序を固定する。

```
Step 1  phone / monitor / admin で、何px が何個あるかを数える  ← 方式は決めない
Step 2  3画面を突き合わせる
Step 3  A / B / C のどれを採用するか決める                     ← ここで初めて決める
Step 4  以降は移行手順書の Phase 2 後半へ
```

**Step 1 の途中で方式を決めない。** 数え終わるまでは「どの値が何個あるか」だけを見る。

## 1. Step 1: 画面ごとに px を数える

### 数える対象

Auto Layout のパディング / Item spacing（gap） / 要素間の余白。Web の `padding` `margin` `gap` に対応するもの。

**対象外**（別のトークン体系なので混ぜない）: 固定 width / height、アイコン画像サイズ、font-size、line-height、letter-spacing、border-radius、border-width、色、影、絶対座標。

### 数え方のルール

数え方がブレると Step 3 の判断が壊れるので、先に固定する。

- **コンポーネント定義は1件**として数える。同じコンポーネントを10箇所に置いても 10 にしない（使用回数が水増しされ、実際には1箇所しかない値が「よく使う値」に見えてしまう）
- 画面直下のフレームやセクションは、**その都度1件**として数える
- padding が `16px 24px` のように方向で違う場合は、**16px を1件、24px を1件**として別々に数える
- 方向（top / right / bottom / left / x / y / all）は記録するが、**集計は px 値ごとにまとめる**

### 🚫 この段階でやらないこと

- **px 値を丸めない。** `15px` と `16px` があったら、そのまま2行として記録する
- トークン名（`sm` `md` など）を書かない。Step 3 より後の仕事
- 「一般的なデザインシステムではこう」という理由で、Figma に無い値を足さない

## 2. Step 2: 3画面を突き合わせる

Step 1 の3つの表を、px 値をキーにして1枚にまとめる。

| px値 | phone | monitor | admin | 合計 | 備考 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 8 | 18 | 0 | 6 | 24 |  |
| 15 | 2 | 0 | 0 | 2 | 16 への統合候補 |
| 16 | 12 | 0 | 9 | 21 |  |
| 48 | 0 | 14 | 0 | 14 | monitor 専用 |

※ 上の数値は書き方の例。実データを入れるまで意味を持たない。

あわせて次の3つを算出する。Step 3 の判断に直接使う。

- **異なる px 値の総数**（上の表の行数）
- **2画面以上で使われている px 値の数**（重なりの大きさ）
- **1画面でしか使われていない px 値の数**

## 3. Step 3: A / B / C を決める

### 選択肢

| | 方式 | 内容 | CSS |
| --- | --- | --- | --- |
| **A** | **1スケール共有** | 全画面で同じ段を共有。monitor は大きい段（`xl` `2xl` `3xl`）を使う | `--spacing-md: 16px` |
| **B** | **画面別スケール** | 画面ごとに別トークンを持つ | `--spacing-monitor-md: 48px` |
| **C** | **役割ベース命名** | px の大小ではなく用途で命名 | `--spacing-card: 16px` |

### 既定は A

**特別な理由がない限り A を採用する。** 段が増えても構造は1本のままで、当日の微調整で壊れにくい。

B は トークン数がおよそ3倍になり、当日に「モニタだけ余白を詰めたい」となったとき、どのトークンを触るのかが毎回問い合わせになる。C は名前は読みやすいが、CSS 変数は1つの値しか持てないため、画面ごとに違う値にするには画面ごとのスコープ指定が必要になり、Tailwind のユーティリティで完結しなくなる。

**A を捨てるには、実データによる積極的な根拠が要る。** 以下がその判定基準。

### 判定

Step 2 の集計を上から順に当てはめる。

1. **異なる px 値の総数が 8 以下** → **A で確定。** 検討終了
2. **総数が 9〜12** → **A。** 段は `2xs xs sm md lg xl 2xl 3xl` の範囲に収める。収まらない分は、統合候補として PM の承認を取るか、`p-[18px]` の任意値として残す
3. **総数が 13 以上** → まだ決めない。**先に統合候補（`15px` → `16px` など）を洗い出して PM の承認を取り、統合後にもう一度数える。** その結果 12 以下になれば A
4. 統合してもなお 13 以上で、かつ **1画面でしか使われていない値が全体の 7 割を超える**（＝3画面がまったく別の余白体系を持っている）→ **A では無理。PM に報告して止まる。** B か C かはそこで相談する

### 4 に到達したら、勝手に決めずに止まる

3画面が別体系だった場合、これはトークンの命名の話ではなく **「デザインとして3画面が別物になっている」という設計の話**になる。実装側の都合で B や C を選ぶより先に、Figma 側をどう扱うかを PM が判断する必要がある。

### 判断の記録

決まったら、ここに残す。


## 4. Step 4 以降

方式が決まったら、[`Figma・Tailwindスペーシングトークン移行手順.md`](./Figma・Tailwindスペーシングトークン移行手順.md) の Phase 2 後半（トークン名の割り当て）へ進む。

決定事項として確定しているもの:

- **単位は Tailwind 既定のまま（`--spacing: 0.25rem`）。** 一時 `--spacing: 4px` に上書きしたが、2026-08-20 に撤回した（→ 対応表 §11）
- **名前は `2xs < xs < sm < md < lg < xl < 2xl < 3xl`** の小さい順。必要な段だけ使う
- **Figma は読み取り専用。** Variables の登録は PM 本人が手動で行う
