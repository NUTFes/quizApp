## なぜ最初にやるのか

「フロントとバックを並行して進めるには」の答えがこれ。
**フロントとバックの境界(API仕様)を先に文書で固定すれば、フロント班はモックデータで、バック班は仕様書だけで、互いを待たずに開発できる。**

Go採用によりフロント(TS)とのコード上の型共有はできないため、**`docs/api.md` が唯一の契約書**になる。
- 仕様変更は必ず api.md を先に直してから実装する(実装が仕様書とずれたら仕様書が正)
- フロントは api.md を見て手書きの型定義(`frontend/src/types/`)を作る
- 余裕が出たら tygo(Go構造体→TS型自動生成)を導入して手書きを置き換える

## データモデル案(GORMモデル/マイグレーションの元ネタ)

```
Question(問題)
- id            … スプシのid列と一致させる(同期のキー)
- type          … "four_choice"(2×2) | "two_choice"(左右) | "maru_batsu"(左右) | "hayaoshi"(モニタのみ順次表示)
- textSegments  … 問題文を `/` で区切った配列 ["…", "…"]。区切り不要なら要素1個。順次表示はこの配列を revealedSegments 個まで表示
- choices       … 選択肢配列 [{id, label}](JSONB列)
- correctChoiceId
- explanation   … 解説(任意。あるものだけ表示)
- difficulty    … 難易度
- order         … 出題順
- timeLimitSec  … 移動締切秒数(空ならデフォルト30)

EventState(イベント進行状態)※常に1レコード。サーバーの「現在の正」
- phase         … "waiting" | "question" | "answer" | "finished"
- currentQuestionId
- questionStartedAt   … 移動締切タイマーの起点
- timeLimitSec        … 移動締切までの秒数(デフォルト30)
- revealedSegments    … 順次表示: 現在の問題文を何区切り目まで表示したか(手動送りで increment)
```

phaseと画面の対応: `waiting`=「まもなく始まります」/`question`=出題+移動締切タイマー/`answer`=正答ハイライト+正解演出動画/`finished`=終了+アンケート(Google Form)リンク。

**v1に存在しないもの(回答機能なしのため)**: Participant / Answer テーブル、参加者登録、回答送信、二重回答防止。回答は会場のエリア移動(人力判定)で行うためアプリはデータを持たない。将来スマホ回答を復活させる場合の設計は旧版(git履歴)参照。

## REST API 案

| メソッド | パス | 用途 | 使用者 |
|---|---|---|---|
| GET | /api/state | 現在のEventState取得(初期表示・復帰用) | 全画面 |
| GET | /api/questions | 問題一覧(リスト画面) | 管理者 |
| GET | /api/questions/:id | 問題詳細 | 管理者 |
| POST | /api/admin/show-question | 指定問題を出題状態にする | 管理者 |
| POST | /api/admin/advance-text | 順次表示を1区切り進める(手動送り。N2確定で正式採用) | 管理者 |
| POST | /api/admin/show-answer | 正答表示状態にする | 管理者 |
| POST | /api/admin/reset | 進行リセット | 管理者 |
| POST | /api/admin/sync-questions | **スプシ→DB同期を実行し、結果レポートを返す** | 管理者 |

- 管理者APIは簡易認証(環境変数の共有パスワード+セッション)で保護。v1はそれで十分
- 回答系API(`POST /api/participants`, `POST /api/answers`)は**v1に存在しない**(回答はエリア移動・人力判定)

## SSE 配信仕様案

エンドポイント: `GET /api/events`(全クライアントが接続しっぱなしにするストリーム)

| イベント名 | data(JSON) | 意味 |
|---|---|---|
| `state` | EventState + 表示に必要な問題データ | 画面切り替えの唯一のトリガー。**接続直後にも必ず1回送る**(リロード復帰がこれだけで成立)。順次表示は手動送り(N2確定)なので、`revealedSegments` の更新もこのイベントで届く |
| `timer` | { remainingSec } | 移動締切までの残り時間(サーバー起点、1秒ごと)。デフォルト30秒 |

- `stats`(回答数)イベントは**v1に存在しない**(回答データがないため)
- **問題文の順次表示**: 手動送り(N2確定)。裏方が `POST /api/admin/advance-text` を押すと `revealedSegments` が1つ増え、更新後の `state` が全モニタへ配信される

### 配信の出し分け(3つの宛先)★

同じ「今の状態」でも、**接続してきた画面の種類によってサーバーが中身を変えて送る**。接続時に種類を伝える(例: `GET /api/events?view=monitor` / `?view=public`、管理者は認証済み接続)。

| 宛先 | 早押しの問題文 | 未公開の正答(question中) | 備考 |
|---|---|---|---|
| 管理者 | 含む | **含む**(プレビュー確認のため) | Cookie認証済み |
| モニタ(view=monitor) | **含む**(順次表示する) | 含まない | 会場の大画面 |
| スマホ(view=public) | **含まない**(「モニターをご覧ください」表示。手元で読めると早押しが成立しないため) | 含まない | 参加者の手元 |

- 実装は「公開用/モニタ用/管理者用」で表示データを組み立て分ける(Goなら構造体を分ける)。**クライアント側で隠すのではなくサーバーで抜く**(開発者ツールで覗けないように)
- 正答(`correctChoiceId`/`explanation`)は、どの宛先でも `phase` が `answer` になるまで公開用には入れない(管理者のみ常時可)

- **ハートビート必須**: サーバーは15〜30秒ごとにコメント行(`: ping\n\n`)を全接続に流す。リバースプロキシの無通信タイムアウトによる切断を防ぐため(→インフラ・デプロイpolicy「SSEの落とし穴」)。実装時に忘れると本番だけ動かなくなる
- クライアントはブラウザ標準の `EventSource` で受信。切断時の再接続はEventSourceが自動で行い、再接続時に `state` が届くので復帰処理は不要
- **クライアントは `state` を受けて画面を描画するだけ**、という一方向データフローを守る。フロントに進行ロジックを書かない
- Go側の実装: 接続中クライアントの一覧を持つブロードキャスタを1つ作る(goroutine + channelの定番構成)。ここはバックエンドリーダーとまとめ役のペア設計タスク

## スプレッドシート入稿→DB同期

問題データは運営メンバー(非エンジニア)がGoogleスプレッドシートで作成し、管理者画面の「同期」ボタンでDBへ取り込む。

### 方針

- **手動同期のみ**(定期cronはやらない)。押したときだけ反映+結果レポート表示。本番中に誰かがスプシを触って問題が差し替わる事故を構造的に防ぐ
- **本番実行時はDBのみ参照**。スプシは入稿ツールであり、同期時にしかアクセスしない(当日Google障害・外部ネット断でもイベントは動く)
- 認証はGoogleサービスアカウント方式(サービスアカウントのメールアドレスにスプシを閲覧共有)。認証JSONは環境変数/シークレット管理でgitに入れない

### スプシの列定義(1行=1問)

| 列 | 内容 | 必須 |
|---|---|---|
| id | 問題ID(数値。**行の並べ替え・修正があっても不変のキー**) | ✅ |
| type | four_choice / two_choice / maru_batsu / hayaoshi | ✅ |
| text | 問題文。順次表示したい位置に `/` を入れる(同期時に分割して textSegments 配列にする) | ✅ |
| choice1〜choice4 | 選択肢(typeにより使用数が変わる) | typeによる |
| correct | 正答の選択肢番号 | ✅ |
| explanation | 解説 | 任意 |
| difficulty | 難易度 | ✅ |
| order | 出題順 | ✅ |
| timeLimit | 移動締切秒数(空ならデフォルト値) | 任意 |

※ 順次表示を手動送り(N2案2)にする場合は、text列に区切り文字(例: `/`)を入れる記法を追加する(N4)。

### 同期処理の仕様

1. シート全行を取得し、行ごとにバリデーション(id重複、正答が空、typeに対して選択肢不足、order重複 など)
2. エラーが1件でもあれば**DBを変更せず**、エラー一覧(行番号+理由)をレポートとして返す
3. 全行OKなら id をキーに upsert(存在すれば更新、なければ作成)。シートから消えたidは削除ではなく無効化フラグにする(誤削除保険)
4. 同期結果(追加n件/更新n件/警告)を管理画面に表示

バリデーションの丁寧さが当日の品質を決める。バック班の独立した良タスク。

## 決定事項

| # | 項目 | 決定 |
|---|---|---|
| D1 | 正誤の公開タイミング | 正答表示フェーズでモニタに一斉表示(管理者操作。確認ポップアップ付き) |
| D2 | 移動締切タイマー切れ時の挙動 | タイマーは表示演出のみ(0になっても何も起きない)。画面遷移は常に管理者操作 |
| D3 | 早押し形式 | ✅ 自動判定はやらない(確定)。モニタのみ問題文を順次表示、判定は人力。WebSocket不要 |
| D4 | 問題データの投入方法 | ✅ スプシ→手動同期(上記)。開発時はサンプルスプシ or シードSQLで代替 |
| D5 | 順次表示の制御方式 | ✅ **手動送りで確定(2026-07-22)**。裏方操作+読み上げ合わせのため。`advance-text` API + `revealedSegments` |
| D6 | 配信の出し分け | ✅ 管理者/モニタ/スマホの3宛先でサーバーが中身を出し分ける(早押し問題文はスマホに送らない、未公開正答はどの公開向けにも送らない) |
| D7 | 正解演出・アンケート | 演出動画はanswerフェーズでモニタが再生(静的アセット)。アンケートはfinishedフェーズにGoogle Formリンク表示(集計はアプリ外、URLは `VITE_SURVEY_URL`) |
