# バックエンド基盤の進め方(PM + キンギョ用)

**「初心者タスクを配れる状態」に到達するための実行手順書。**
[`バックエンド初心者タスク.md`](./バックエンド初心者タスク.md) の前提 P1〜P5 を、上から順にやれば終わる形に割ったもの。

- **これは設計判断を含むので初心者には渡さない**(全部 `hard`)
- **書くための知識** → [`../docs/入門/Go・バックエンド入門.md`](../docs/入門/Go・バックエンド入門.md)
- 担当: PM + キンギョ(バックエンドリーダー)
- ゴール: **`GET /api/admin/state` が動き、写経元として使える状態**

---

## なぜこれを先にやるのか

初心者タスク7本(T1〜T7)は「**見本を写経して隣を作る**」設計になっている。
つまり **見本が1本も無い状態でタスクを配ると、初心者は何も参照できず必ず止まる。**

配るために必要なのは以下の5つ。これが「タスクを配るだけ」ラインの中身。

| # | 準備するもの | これが無いと何が起きるか |
|---|---|---|
| P1 | Question / State の GORMモデル + マイグレーション | 全タスクがこの型を読む。無ければ着手不能 |
| P2 | DB接続 + サンプル問題の seed | 読み取りタスクの動作確認ができない |
| P3 | 認証ミドルウェア(Bearer照合) | 管理者APIタスクが全部これに乗る |
| P4 | **見本エンドポイント `GET /api/admin/state`** | **全タスクの写経元。最重要** |
| P5 | ルータ登録・エラー返却の共通ヘルパ | 各タスクを「関数を書いて1行登録するだけ」にする |

---

## 全体の順番

依存関係があるので、この順でしか進められない。

```
STEP 0  ライブラリを入れる(go get)         ← ここで go.sum が生まれる
   ↓
STEP 1  フォルダの骨格を切る
   ↓
STEP 2  P1 モデル + マイグレーション
   ↓
STEP 3  P2 DB接続 + seed
   ↓
STEP 4  P5 共通ヘルパ(エラー・ルータ)      ← P3/P4 が乗る土台
   ↓
STEP 5  P3 認証ミドルウェア
   ↓
STEP 6  P4 見本エンドポイント GET /api/admin/state
   ↓
   ═══ ここで初心者タスクT1〜T7を配れる ═══
```

**STEP 0〜3 と STEP 4 は分担できる。** STEP 5・6 は STEP 4 に乗るので、順番待ちになる。

## STEP 0. ライブラリを入れる

**ここが最初の関門。** 現在 `backend/` は標準ライブラリのみで書かれている(→ `AGENTS.md` §4)。
Gin/GORM を `go.mod` に手書きで足すと **`go.sum` が無くて起動できない**。`go get` を実際に実行して初めて正しく入る。

```bash
cd backend

go get github.com/gin-gonic/gin
go get gorm.io/gorm
go get gorm.io/driver/postgres
go get github.com/golang-migrate/migrate/v4

go mod tidy      # 使っていない依存を消し、go.sum を整える
```

**確認**

```bash
ls go.sum                 # ← これが生まれていれば成功
go build ./...            # ← 通ること
```

- [ ] `go.sum` が生成された
- [ ] `go build ./...` が通る
- [ ] `mise run up` でコンテナが起動する(air が再ビルドできる)

> **詰まったら**: `go get` はネットワークにつながる環境で実行する。コンテナの中ではなく**WSL2のホスト側**で実行してよい(mise で go 1.25 が入っている)。

**このSTEPだけで1PR。** 「依存を入れただけ」で挙動が変わらないPRにしておくと、後のPRのレビューが読みやすい。

## STEP 2. P1 — モデルとマイグレーション

### 決めること

`docs/実装要件/API仕様書.md` §1 のデータモデルを Go の構造体に落とす。**仕様書が正**なので、フィールド名・型はそこから起こす。

### ⚠️ 最重要の注意点

`docs/実装要件/バックエンド実装要件.md` §1 のとおり、**hayaoshi(早押し)の「予約席」を最初から確保する**。

- `choices` は**空配列を許容**する
- `correctChoiceId` は **NULL を許容**する(`*int` など、ポインタかnullable型で持つ)

v1では hayaoshi は未実装だが、**後から列を足すとマイグレーションと既存データの移行が発生する**。最初からnullableで作っておけば、フェーズ2で型を変えずに済む。

### やること

1. `internal/question/model.go` に Question の構造体
2. `internal/event/model.go` に State の構造体
3. `migrations/000001_init.up.sql` / `.down.sql` にテーブル定義

**確認**

```bash
mise run db:migrate       # マイグレーションが通る
```

- [ ] `choices` が空配列を許容する
- [ ] `correctChoiceId` が NULL を許容する
- [ ] `mise run db:migrate` が通り、テーブルができている

## STEP 3. P2 — DB接続と seed

### やること

1. `internal/platform/db.go` に DB接続(`DATABASE_URL` から)
2. `cmd/seed/main.go` にサンプル問題の投入

### seed に入れるデータ

**4種類の問題形式を最低1問ずつ**入れる。読み取りタスクの動作確認で、型ごとの違いを確認できるようにするため。

| type | 何を確認できるか |
|---|---|
| `four_choice` | 選択肢4つ・2×2配置 |
| `two_choice` | 選択肢2つ・左右 |
| `arunashi` | ありなし |
| (解説あり/なしの問題を混ぜる) | 表示の出し分け |

> **⚠️ 本番の問題データは絶対に入れない。** リポジトリは public。参加者に正答が見える。

**確認**

```bash
mise run db:seed
docker compose exec db psql -U quiz -d quiz -c "SELECT id, type FROM questions;"
```

- [ ] seed が通り、4種類の問題が入っている
- [ ] 本番の問題を使っていない

## STEP 4. P5 — 共通ヘルパ(ここが初心者タスクの快適さを決める)

**初心者タスクを「関数を書いて1行登録するだけ」にするための土台。** ここを丁寧に作るほど、後が楽になる。

### 作るもの

1. **エラーレスポンスの共通ヘルパ**(`internal/platform/response.go`)

   `docs/実装要件/API仕様書.md` §0 のエラー形式に合わせる。**`code` は契約**(フロントが分岐に使う)、`message` は開発者向けで自由(→ `AGENTS.md` §6-5)。

   ```go
   // イメージ。実際の形は API仕様書 §0 に従う
   func RespondError(c *gin.Context, status int, code string, message string)
   ```

   これがあると、初心者は `RespondError(c, 404, "NOT_FOUND", "問題が見つかりません")` と書くだけでよくなる。**無いと全員が違う形のエラーJSONを書いて、フロントが壊れる。**

2. **ルータ登録**(`internal/platform/router.go`)

   各機能が `RegisterRoutes(r *gin.Engine)` を生やし、ここで1行ずつ呼ぶ形にする。
   こうすると初心者タスクは「ハンドラを書く → ここに1行足す」で済み、**同じファイルを触る場所が1行だけ**になるのでコンフリクトも最小。

**確認**

- [ ] エラーヘルパが API仕様書 §0 の形と一致している
- [ ] ルータ登録が1行で済む形になっている

## STEP 5. P3 — 認証ミドルウェア

### 仕様

`docs/実装要件/API仕様書.md` §0 と `バックエンド実装要件.md` §6 のとおり。

- `Authorization: Bearer <token>` を照合するだけ。**ログイン機能は無い**
- `ADMIN_TOKEN`(管理者API)/ `IMPORT_TOKEN`(問題投入)の2種類
- **SSEのみ `?token=` クエリ**(EventSourceがヘッダを送れないため)
- 失敗時は 401 `UNAUTHORIZED`

### ⚠️ compose の環境変数が古い

`docker-compose.yml` の backend に `ADMIN_PASSWORD=dev-password` が残っている。**確定した設計は Bearer トークンで `ADMIN_TOKEN` / `IMPORT_TOKEN`**(→ `.env.example`)。このSTEPで直す。

- [ ] `docker-compose.yml` を `ADMIN_TOKEN` / `IMPORT_TOKEN` に修正した
- [ ] 正しいトークンで通り、間違ったトークンで401が返る

## STEP 6. P4 — 見本エンドポイント `GET /api/admin/state`

**ここが本丸。** 全初心者タスクの写経元になるので、**「読んで真似できる」ことを最優先**に書く。

### 仕様

`docs/実装要件/API仕様書.md` §2.1。管理者向けのフル形(`correctChoiceId` を含む)を返す。認証必須。

### 見本として満たすべきこと

写経元なので、**初心者が必要とする要素が全部1本に入っている**状態にする。

- [ ] ハンドラ関数の書き方(引数・戻り値・`c.JSON` の形)
- [ ] DBから読む処理
- [ ] JSONへの詰め替え(構造体のタグ)
- [ ] **エラー返却**(STEP 4 のヘルパを使う)
- [ ] 認証ミドルウェアの適用のされ方
- [ ] ルータへの登録の1行
- [ ] **コメント**。「なぜこう書くか」を初心者向けに1〜2行ずつ

### ⚠️ nullable の扱いを見本に含める

`API仕様書.md` §1 のとおり、`phase` が `waiting` / `finished` のときは `question` `questionStartedAt` が `null` になるが、**キーは残す**。
ここは初心者が最も間違えるポイントなので、**見本の中で正しく処理して、コメントで理由を書く**。

**確認**

```bash
curl -s -H "Authorization: Bearer dev-admin-token" http://localhost:3000/api/admin/state | jq
curl -s http://localhost:3000/api/admin/state          # ← 401 が返ること
```

- [ ] 認証ありで仕様どおりのJSONが返る
- [ ] 認証なしで 401 `UNAUTHORIZED` が返る
- [ ] `phase: waiting` のとき `question` が `null` でキーが残っている

## PRの分け方(目安)

1タスク=1PRの原則どおり、STEPごとに分ける。全部を1つのPRにすると、レビューが不可能になる。

| PR | 内容 | 目安 |
|---|---|---|
| 1 | STEP 0(go get) | 依存追加のみ |
| 2 | STEP 1・2(骨格 + モデル + マイグレーション) | |
| 3 | STEP 3(DB接続 + seed) | |
| 4 | STEP 4(共通ヘルパ) | |
| 5 | STEP 5(認証) | |
| 6 | STEP 6(見本エンドポイント) | **一番丁寧にレビューする** |

PM自身のPRも、**approve 1件が必要**(管理者にも保護が適用されている)。ともちゃん・みゆちゃんにレビューを依頼する。
