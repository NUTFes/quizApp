**読む順番:**

## 1. 環境を動かす

```bash
mise run up            # 3つのコンテナを起動
mise run db:migrate    # テーブルを作る
mise run db:seed       # サンプル問題を5件入れる
```

確認:

```bash
curl -i http://localhost:3000/api/health          # → 200 {"status":"ok"}
curl -i -H "Authorization: Bearer dev-admin-token" \
     http://localhost:3000/api/admin/state        # → 200
```

トークンは `.env.example` に書いてある開発用の値です。**本番の値ではありません。**

### ⚠️ 最初に必ず引っかかること — 「直したのに変わらない」

**別の端末でこれを開いたまま作業してください。**

```bash
docker compose logs -f backend
```

保存するたびに air がビルドし直しますが、**ビルドに失敗すると、前回成功したバイナリをそのまま動かし続けます。** サーバーは止まりません。だから **200 が返ってきても、それが自分のコードとは限りません。**

```
building...
internal/event/state.go:20:30: missing key in map literal
failed to build, error: exit status 1     ← いまのコードは動いていない
running...                                 ← 古いバイナリを起動し直しただけ
```

| ログ | 意味 |
| --- | --- |
| `failed to build` | **反映されていない。** すぐ上にエラーと行番号が出ている |
| エラー無しで `running...` | 反映された |
| `Connection reset by peer` | ビルド中。数秒待つ |

**このログを見る習慣があるかどうかで、詰まる時間が何倍も変わります。**

## 2. 1本のタスクの流れ

```
Issue を読む
  ↓
ブランチを切る        ← 切り元に注意。下の⚠️を読むこと
  ↓
写経元を開く          backend/internal/event/state.go
  ↓
書く → curl で叩く    ← ここを何度も回す
  ↓
mise run fix          書式を自動で直す
mise run lint         CI と同じチェック
  ↓
PR を出す
```

### ⚠️ 当面、ブランチは #76 のブランチから切ってください

**ふだんは `main` から切ります。いまは違います。**

初心者タスクの写経元になる `internal/event/state.go` は、**まだ #76（進行制御）のブランチにしかありません。** main から切ると、手元に写経元が無い状態で始めることになります。

```bash
git fetch origin
git switch -c feat/78-static-images origin/feat/76-create-api--proceeding-control
```

> ブランチ名の `api--` は**ハイフン2本**です。打ち間違えやすいのでコピペしてください。

**#76 が main にマージされたら、この指示は無効になります。** マージ済みかどうかは、main に `progress.go` があるかで判定できます。

```bash
git fetch origin && git ls-tree origin/main backend/internal/event/progress.go
# 何か表示される → マージ済み。main から切る
# 何も表示されない → まだ。#76 から切る
```

#### #76 がマージされた後、自分のブランチをどうするか

**このリポジトリの PR は squash merge です。** ブランチの何十個ものコミットが、main では**1個に潰されて**入ります。中身は同じでも、**git から見ると別のコミット**です。

この状態で `git pull --rebase origin main` をすると、git は「main に無いコミット」を全部もう一度積み直そうとします。**すでに main に入っている変更を、1個ずつコンフリクトとして出してきます。**

そうなったら、まず落ち着いて中断してください。**コミットは1つも失われません。**

```bash
git rebase --abort
```

正しいのは、`--onto` で「どこから先を運ぶか」を自分で指定するやり方です。

```bash
# 分かれた地点を調べる
git merge-base origin/feat/76-create-api--proceeding-control HEAD

# その地点より後だけを main の上に置き直す
git rebase --onto origin/main <いま出た地点> <自分のブランチ名>
```

**迷ったら `git rebase --abort`、そして PM に声をかけてください。** ここで無理をしても、得るものは何もありません。

## 3. このバックエンドの形

```
backend/
├── cmd/server/main.go        … 起動するだけ。ルート登録を1行足す場所
└── internal/
    ├── platform/             … 全機能が使う共通部品
    │   ├── router.go         …   ルータの組み立て
    │   ├── response.go       …   エラー返却のヘルパ
    │   ├── auth.go           …   Bearer トークンの照合
    │   └── db.go             …   DB 接続
    ├── event/                … 進行状態（state・phase）
    │   ├── routes.go         …   どのパスをどの関数に繋ぐか
    │   ├── state.go          …   GET /api/admin/state
    │   ├── progress.go       …   進行制御(show-question ほか)
    │   └── model.go          …   DB の形と API の形
    ├── question/             … 問題データ
    └── sheetsync/            … スプレッドシートからの投入
```

**あなたのタスクは、自分のフォルダの中だけで完結します。** `main.go` に1行足す以外、他人のフォルダは触りません。だから同時に作業してもコンフリクトしません。

### 新しいエンドポイントを足す形

各フォルダは `RegisterRoutes` という関数を1つ持ちます。

```go
// internal/question/routes.go
func RegisterRoutes(db *gorm.DB, adminToken string) platform.RegisterFunc {
	return func(r *gin.Engine) {
		g := r.Group("/api/admin", platform.RequireToken(adminToken))
		g.GET("/questions/:id", func(c *gin.Context) { getQuestion(c, db) })
	}
}
```

`main.go` にはこの1行だけ足します。

```go
r := platform.NewRouter(
	admin.RegisterRoutes(adminToken),
	event.RegisterRoutes(db, adminToken),
	question.RegisterRoutes(db, adminToken),   // ← あなたが足す行
)
```

> **なぜ `db` を引数で渡すのか。** グローバル変数にすると楽ですが、「どの機能が DB を使うのか」がコードから読めなくなります。引数にすると依存が関数の形に出ます。

### 認証は自分で書かない

`r.Group("/api/admin", platform.RequireToken(adminToken))` の1行で掛かります。

**⚠️ `r.GET("/api/admin/...")` と直接書かないこと。** パスが同じでも、グループを経由しないと**認証が掛かりません**。管理者向けの API には正答（`correctChoiceId`）が入っているので、これは事故になります。

## 4. 写経元は `internal/event/state.go`

**#11 で作った `GET /api/admin/state` が全タスクの見本です。** 開いて、この4つがどこにあるか探してください。

| 探すもの | どのファイル | 何をしている行か |
| --- | --- | --- |
| `RegisterRoutes` | `routes.go` | ルートの登録とグループ認証 |
| `db.First(...)` | `state.go` | DB から1件読む |
| `platform.RespondError(...)` | `state.go` | エラーを返す |
| `c.JSON(http.StatusOK, ...)` | `state.go` | 成功を返す |

**この4つの組み合わせで、T2〜T5 は全部書けます。**

### ファイルの割り方 — `routes.go` ＋ 機能ごとのファイル

**#11 の時点では `handler.go` 1本でした。** その後 #76 で進行制御の4本が入り、割り直しました。**これから作るぶんは、最初からこの形で書いてください。**

| ファイル | 中身 | 誰が触るか |
| --- | --- | --- |
| `routes.go` | `RegisterRoutes` **だけ**。どのパスをどの関数に繋ぐか | **全員が1行ずつ足す** |
| 機能ごとのファイル | ハンドラ本体 | **その機能の担当者だけ** |

`event` パッケージがすでにこの形です。

```
routes.go     … ルート登録（5行）
state.go      … GET /api/admin/state
progress.go   … 進行制御4本
model.go      … 型
```

**理由は、名前の分かりやすさだけではありません。コンフリクトが起きないからです。**

もし3人が同時に `internal/question/handler.go` を触ると、**全員が同じファイルの同じあたりに関数を足す**ので、マージのたびにコンフリクトします。機能ごとにファイルを分けておけば、ぶつかるのは `routes.go` の**1行だけ**です。1行なら、どちらを残すか迷う余地がありません。

> **`handler.go` という名前は、もう使いません。** 「HTTP の入口」という意味しか持たず、機能が2つ入った瞬間に中身を説明しなくなるからです。**自分が足す関数が何をするのかを、そのままファイル名にしてください**（`detail.go` `list.go` `viewer.go` のように）。

## 5. エラーの返し方

```go
platform.RespondError(c, http.StatusNotFound, "QUESTION_NOT_FOUND", "questionId=99 は存在しません")
```

**`c.JSON` でエラーを自作しないこと。** 形が全 API で揃っていないとフロントが壊れます。

| 引数 | 中身 | 誰が読むか |
| --- | --- | --- |
| ステータス | `400` `401` `404` `409` `500` | ブラウザとフロント |
| **`code`** | `QUESTION_NOT_FOUND` など | **フロントが分岐に使う＝契約。勝手に変えない** |
| `message` | 自由な日本語 | **開発者だけ。** 画面には出ないので、直し方まで書いてよい |

### どのステータスを選ぶか

| 状況 | ステータス | 考え方 |
| --- | --- | --- |
| リクエストの内容がおかしい | **400** | 送った側の問題 |
| 認証が通らない | **401** | （ミドルウェアが自動で返す） |
| 指定されたものが存在しない | **404** | 送った側の問題 |
| 今の phase ではできない操作 | **409** | 状態の問題 |
| **サーバー側が壊れている** | **500** | **こちらの問題** |

**「そんな問題は無い」を 500 にしないこと。** 500 は「サーバーのバグ」という意味なので、当日ログを見る人が原因を探しに行ってしまいます。

## 6. DB の読み方（GORM）

使うのは3つだけです。

```go
db.First(&q, id)                                                   // 1件取る
db.Find(&list)                                                     // 全件取る
db.Model(&question.Question{}).Where("asked = ?", true).Count(&n)  // 数える
```

### `.Error` を最後に見る

`db.First(...)` は**エラーを返しません。** `*gorm.DB` を返し、エラーは `.Error` フィールドにあります。

```go
if err := db.First(&q, id).Error; err != nil {
	...
}
```

「行が無い」かどうかは `errors.Is` で判定します。

```go
if errors.Is(err, gorm.ErrRecordNotFound) {
	platform.RespondError(c, http.StatusNotFound, "QUESTION_NOT_FOUND", ...)
	return
}
```

### `?` を必ず使う

```go
db.Where("asked = ?", true)               // ✅
db.Where("asked = " + userInput)          // 🚫 SQLインジェクション
```

### 🚫 読み込み先の変数を使い回さない

**これは必ずどこかで踏みます。**

GORM は、渡した構造体の**主キーが 0 でなければ、それも検索条件に足します**。

```go
var q question.Question
db.First(&q, 1)   // → WHERE id = 1        ここで q.ID = 1 になる
db.First(&q, 2)   // → WHERE id = 2 AND id = 1    ← 成立しない
                  //    結果: record not found
```

`record not found` が返るので、**「2番の問題が存在しない」と誤読します。** 原因にたどり着くのが非常に難しい種類のバグです。

**読むたびに `var` で新しく宣言してください。** ループの中で1つの変数を使い回すのが一番危険です。

### SQL を見る

何が起きているか分からなくなったら、GORM が組み立てた SQL がログに出ます。

```
SELECT * FROM "questions" WHERE "questions"."id" = 2 AND "questions"."id" = 1 ORDER BY ... LIMIT 1
```

**GORM は魔法ではありません。** 困ったらこれを見れば必ず分かります。

## 7. DB の型と API の型は別物

**これがこのプロジェクトで一番大事な約束です。**

```go
c.JSON(http.StatusOK, q)     // 🚫 DBの構造体をそのまま返さない
```

理由は3つあります。

1. **形が違う。** 一覧（#80）では `textSegments`（配列）→ `textPreview`（文字列）、`imageUrl` → `hasImage`（真偽値）に変わります
2. **出してはいけないものが混ざる。** 閲覧者向け（#81）では `correctChoiceId` と `explanation` を消す必要があります
3. **DB の都合が漏れる。** `ID` や外部キーは API には要りません

なので**API 用の構造体を別に作って、詰め替えます。** `internal/event/state.go` の `buildState` がその見本です。

### ⚠️ キーを消さない

```go
TimeLimitSec *int `json:"timeLimitSec,omitempty"`   // 🚫 omitempty を付けない
```

`omitempty` は「値が空ならキーごと消す」指定です。フロントは `state.question === null` で分岐するので、**キーが消えると `undefined` になって分岐が静かに壊れます。**

**`null` にしたいときは、ポインタ型にして値を入れない**でください。それで JSON は `null` になり、キーは残ります。

### ⚠️ 空の配列は `null` になる

```go
var list []Item          // これを返すと JSON では null
list := []Item{}         // これなら []
```

仕様は `{"questions": []}` と決めています（`null` ではない）。**必ず0件で試して確認してください。**

## 8. テスト付きタスク編（#82 T6 向け）

このタスクだけ HTTP も DB も触りません。代わりに**テストを書くことが成果物の半分**です。

### テーブル駆動テスト

Go の定番の書き方です。**入力と期待値を表にして、ループで回す**だけ。

```go
func TestValidate(t *testing.T) {
	tests := []struct {
		name  string          // 何を確かめるテストか
		input Input           // 入れるもの
		wantErrCount int      // 期待するエラーの件数
	}{
		{"正常な4択", Input{Type: "four_choice", Choices: 4, ...}, 0},
		{"4択なのに選択肢3個", Input{Type: "four_choice", Choices: 3, ...}, 1},
		{"hayaoshi は v1 未対応", Input{Type: "hayaoshi", ...}, 1},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got := Validate(tt.input)
			if len(got) != tt.wantErrCount {
				t.Errorf("エラー件数 = %d, 期待 = %d (中身: %v)", len(got), tt.wantErrCount, got)
			}
		})
	}
}
```

**新しいパターンを増やすときは、表に1行足すだけ**です。ここが表形式にする理由です。

### 実行

```bash
docker compose exec backend go test ./internal/sheetsync/... -v
```

`-v` を付けると、どのケースが通ったか1件ずつ出ます。

> **`mise run test` はまだありません。** テストを使うタスクが今回初めてなので、必要なら `mise.toml` に追加を提案してください。

## 9. CI を通す

**PR を出す前に必ず流してください。**

```bash
mise run fix     # 書式を自動で直す（gofmt / Prettier / ESLint）
mise run lint    # CI とまったく同じチェック
```

バックエンドで見られるのはこの3つです。

| チェック | 落ちる理由 |
| --- | --- |
| `gofmt -l .` | 空白・改行が整っていない。**`mise run fix` で直る** |
| `go vet ./...` | 怪しい書き方。**本物のバグのことが多い**ので中身を読むこと |
| `go build ./...` | コンパイルエラー |

### ⚠️ push する直前に流すこと

「さっき通ったから大丈夫」で push すると落ちます。**最後にコミットしたあと、もう一度流してください。**

`go vet` の例:

```
log.Fatal call has possible Printf formatting directive %v
```

これは `log.Fatal` に `%v` を渡しているという指摘です。`log.Fatal` は書式を解釈しないので `%v` がそのまま出力されます。`log.Fatalf` が正解 —— こういう「動くけど間違っている」を拾ってくれます。

## 10. PR の出し方

書き方は [`開発フローガイド.md`](../docs/ガイドライン/開発フローガイド.md) ⑤ にあります。ここでは**API タスク特有の部分**だけ。

  | python3 -c "import sys,json;d=json.load(sys.stdin);print(len(d), sorted(d))"

## 11. 絶対に守ること

**このリポジトリは public です。** 誰でも読めます。

| 🚫 やってはいけないこと | なぜ |
| --- | --- |
| **本番の問題文・正答をコミットする** | コミットした瞬間、参加者に正答が見える。**サンプルは全部架空にすること** |
| **トークンを PR・Issue・ログに貼る** | `dev-admin-token` は公開済みの開発用なので可。**本番トークンは絶対に不可** |
| **`log.Printf` でトークンを出す** | 必要なら `len(token)` を出す |
| **`?token=` を通常APIで受け付ける** | アクセスログとブラウザ履歴に残る（SSE だけ例外） |
| **正答をフロントで隠す** | 開発者ツールで見える。**サーバーが送らない**のが唯一の方法 |

**もしトークンをコミットしてしまったら、隠さずすぐPMに言ってください。** 無効化して作り直せば済みます。黙っているほうが被害が大きくなります。

## 12. 詰まったら

| 症状 | まず見るところ |
| --- | --- |
| 直したのに変わらない | **`docker compose logs backend` の `failed to build`**（§1） |
| `Connection reset by peer` | air がビルド中。数秒待つ |
| 401 が返る | `g.GET` で登録しているか。トークンより先にこれ |
| 404 が返る | パス。グループのプレフィックスと結合される |
| JSON のキー名が変 | 構造体タグの打ち間違い。**コンパイルは通るので目で確認** |
| キーが消える | `omitempty` を付けていないか。フィールドが小文字始まりでないか |
| `null` にしたいのに `0` | ポインタ型にする |
| `[]` にしたいのに `null` | スライスを `[]T{}` で初期化する |
| `record not found` が変 | **変数を使い回していないか**（§6） |
| DB の中身を見たい | `docker compose exec db psql -U quiz -d quiz -c "SELECT * FROM questions;"` |

**30分詰まったら質問してください。** 詰まった時間は成果になりません。聞かれた側も、どこが分かりにくいかを知れて助かります。
