## 前提と方針

- 本番はローカルの**オンプレサーバー**。既存のサブドメイン公開基盤に合流する(ゼロから公開経路を作らない)
- 参加者は会場でQRコード→**自分のモバイル回線**でアクセス(既存アプリが外部公開できている実績が保証)

## SSE特有の落とし穴(本番だけ動かない事故の防止)

SSEは「接続を開きっぱなしで流し続ける」通信のため、普通のWeb向けデフォルト設定のリバースプロキシと相性問題が2つある:

1. **バッファリング**: プロキシが応答を溜めてから送る設定だと、イベントが即座に届かない(=全端末の画面が切り替わらない)。該当サブドメインの設定で無効化が必要(nginxなら `proxy_buffering off`)
2. **無通信タイムアウト**: 「60秒データが流れない接続は切断」が一般的なデフォルト。問題と問題の間で全員の接続が切れる。**対策はGo側で15〜30秒ごとにコメント行(ハートビート)を流すこと**(API・データ設計policyのSSE仕様に組み込み済み)。プロキシ設定に依存しない安全策なので必ず実装する

症状が「ローカルでは動くのに本番だけ画面が切り替わらない」になるため、知らないと当日デバッグ不能になる。**本番サブドメインでのSSE疎通確認を、リハーサルより前の早い段階で1回やる**こと(Hello Worldデモを本番経路に一度通すのが理想)。

## 本番のコンテナ構成

```
リバースプロキシ(既存・運用者管理)
   │ quiz.○○○.jp へのアクセスを振り分け
   ▼
nginx(本アプリのコンテナ)── /     → フロントのビルド済み静的ファイルを配信
   │                        /api/ → backendへ中継(SSE用のbuffering off設定込み)
   ▼
backend(Go)──── db(PostgreSQL)
```

開発時の3コンテナ(frontend/backend/db)と違い、本番はフロントが「Viteでビルドした静的ファイル+nginx配信」になる(`docker-compose.prod.yml` で定義)。

## 開発環境と本番環境の分け方

「分けるやり方がわからない」への回答。やることは3つだけ:

1. **設定値を全部 環境変数にする**(コードに書き込まない)
   - `.env.example` に一覧、開発は `.env`、本番はサーバー上の `.env.prod`
   - 例: `DATABASE_URL`, `ADMIN_PASSWORD`, `SPREADSHEET_ID`, スプシ認証JSON
2. **composeファイルを分ける**
   - 開発: `docker-compose.yml`(bind mount + ホットリロード)
   - 本番: `docker-compose.prod.yml`(ビルド済みイメージ・mount無し・restart: always・上記のnginx構成)
   - 起動: `docker compose -f docker-compose.prod.yml up -d`
3. **本番だけの手順を `docs/deploy.md` に書く**(デプロイ=作業手順書があること)

## デプロイ方式

v1は**手動デプロイで十分**(CDは作らない):

```
本番サーバーにSSH → git pull → docker compose -f docker-compose.prod.yml up -d --build → migrate実行
```

これを `mise run deploy`(本番サーバー上で実行するタスク)にまとめる。自動化(GitHub Actionsからのデプロイ)は動いてから考えるv2。
※ Q2の結果、既存インフラに標準のデプロイ流儀がある場合はそちらに従う。
