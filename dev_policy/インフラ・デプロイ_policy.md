## 前提と方針

- 本番はローカルの**オンプレサーバー**。既存のサブドメイン公開基盤に合流する(ゼロから公開経路を作らない)
- 参加者は会場でQRコード→**自分のモバイル回線**でアクセス(既存アプリが外部公開できている実績が保証)
- 環境は **開発(各自ローカル)/ 本番(オンプレ)** の2つ。ステージングは作らない(本番機で本番前にリハーサルすることで代替)
- **フロントとAPIは1サブドメインに同居させ、パスで分岐する**: `quiz.○○○.jp/` → フロント静的ファイル、`quiz.○○○.jp/api/` → Go。別サブドメインに分けるとCORS設定(ブラウザのセキュリティ機構への対応)が必要になり、初心者チームの定番の詰まりポイントになるため

## 🔴 最優先: Proxmox の「CT」は VM ではない

**Proxmox の CT は LXC コンテナ**であり、VM とは前提が違う。

| | VM | **CT(LXC)** |
|---|---|---|
| カーネル | 専用のものを持つ | **ホストと共有する** |
| 中で Docker を動かす | 普通に動く | **設定が要る。既定のままでは動かない** |

**CT の中で Docker を動かすには、CT 側の設定に `nesting=1` が必要**(多くの場合 `keyctl=1` も)。無いと `docker compose up` がそもそも起動しない。さらにホストのストレージが **ZFS だと overlayfs が使えず**、`fuse-overlayfs` への切り替えが要る。

これは当日ではなく**デプロイ初日に判明して止まる**種類の問題なので、最初に潰す。

### CT で Docker が動かせない場合の選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A | CT に Go バイナリと PostgreSQL を直接入れて systemd で動かす | ❌ **非推奨**。開発が compose なので本番だけ構成が変わり、「ローカルでは動くのに」が起きる |
| B | Docker が動く CT(nesting有効)をもらう | ✅ 本命 |
| C | VM をもらう | ✅ 次善。確実だが資源を食う |

**開発と本番で構成を揃えることを優先し、B を第一希望として交渉する。**

### ✅ 検証結果(2026-08-25)

**VMID 201 で実際に確認し、非特権CT + `nesting=1,keyctl=1` で Docker が問題なく動いた。**
この節の懸念は解消し、**上の A/B/C の交渉は不要**になった。

| 検証項目 | 結果 |
|---|---|
| Docker デーモン起動(非特権CT) | ✅ `hello-world` 完走 |
| 永続ボリュームを持つコンテナ | ✅ PostgreSQL 16 が `ready to accept connections` |
| Storage Driver | ✅ **`overlayfs`**(containerd snapshotter)。`vfs` フォールバックなし |
| ホストのストレージ | ✅ **lvmthin。ZFSではない**ため `fuse-overlayfs` は不要 |

> `docker info` の表示が `overlay2` ではなく **`overlayfs`** なのは、新しい Docker が
> containerd のイメージストアを使っているため。名前が違うだけで中身は同じ OverlayFS。

## 🔴 もう1つの制約: thin pool の空き容量

2026-08-25 に判明。**Docker が動くかより先に、置ける容量があるかで詰まる。**

ホスト `pve03` のストレージは `pve/data`(lvmthin, 54.18GB)1本で、**全ゲストが共有している**。

| 時点 | プール使用率 | プールの残り | quiz-stg の実消費 |
|---|---|---|---|
| CT 作成前 | 68.33% | 約 17.9GB | — |
| Docker 導入後 | 70.87% | 約 15.8GB | 1.37GB |
| **アプリ デプロイ直後** | **78.96%** | 約 11.4GB | **5.57GB** |
| **prune + fstrim 後** | **72.37%** | 約 15.0GB | **2.16GB** |

VG の未割り当ては 14.75GB(プール拡張に使える)。

### 見積もりに使う数字は「定常 2.2GB」ではなく「ピーク 5.6GB」

差の約 3.4GB は multi-stage ビルドの `golang:1.25` / `node:22` とビルドキャッシュ。
`deploy.sh` の `docker image prune -f` は宙ぶらりんのイメージしか消さないので**残り続ける**。
`docker system prune -af` で回収できるが、**次のデプロイで再取得されてまた膨らむ**。

したがって **1CT あたり 5.6GB を占有するものとして計画する**。12GB 枠はこれでも妥当。

**thin pool が 100% に達すると、そのプール上の全ゲストが同時に書き込み不能になる**(自分のCTだけでなく他の利用者のCTも巻き添え)。しかも autoextend の閾値が未設定で、その保険が無い。

### 決定

- **検証用CTと本番CTは並存させない。** 検証が済んだら quiz-stg を破棄し、`infra/create-ct.sh` から本番CTを作り直す(スクリプトが同一なら再現性は担保される)
- rootfs は **12GB**。ビルド時ピーク 5.6GB(48%使用)に対して十分。4GBメモリでもビルドは通った
- **`docker system prune -af` の後、ホストで `pct fstrim <VMID>` を必ず実行する。**LXCでは中でファイルを消してもプールの消費は減らず、fstrim で初めて返る

### 運用者への報告事項(依頼ではなく情報提供)

- `pve/data` が 72.37%(検証CT 1台込み)。VG に 14.75GB の未割り当てがあるので、プール拡張の余地がある
- `thin_pool_autoextend_threshold` が未設定で、満杯時に全ゲストが巻き添えになる構成
- **CT 101(mitomen-playground)が自ディスクの 98.10% を使用中**

3つ目は自分たちの都合ではない。**相乗りする側がホスト全体の健康状態を報告する**形になるので、依頼全体の通りが良くなる。

## 🔴 Q6 の書き換え: SSH アクセス権ではなく「経路が無い」

当初 Q6 は「SSHアクセス権を**誰が**もらえるか」という権限の話だと考えていたが、**前提が違った**。

校内ネットワークの外から Proxmox ホストへ SSH が通らず、**現状の唯一の入口は Cloudflare Zero Trust 経由の PVE GUI**。CT は同じ内側にいるので、CT への SSH も同様に通らない。

**これは policy に書いたデプロイ方式そのものが成り立たないことを意味する:**

```
CTにSSH → git pull → docker compose up -d --build   ← 「CTにSSH」ができない
```

### 当面の回避策(リハーサルまではこれで進められる)

**受信(inbound SSH)が塞がれているだけで、送信(outbound)は生きている。**CT から GitHub も Docker Hub も見えることを確認済み。したがって:

```
PVEのGUI → ホストのShell → pct enter <VMID> → git pull → docker compose up
```

で全部完結する。`.env.prod` もヒアドキュメントの貼り付けで作れる。

つらいのは、ログを追う・ファイルを取り出す・複数人で作業する、といった点。**当日の障害対応をブラウザのコンソールだけでやるのはかなり厳しい。**

### 運用者への依頼(Q2 とセットで聞く)

> Proxmox GUI と同じ Zero Trust 経由で、**CT への SSH アクセスも公開**していただけませんか。手元からは `cloudflared access ssh` で繋ぎます。

**新しい穴を開ける依頼ではなく、既に導入済みの仕組みに1件足す依頼**なので通りやすい。運用者から見ると Q2(Cloudflareの繋ぎ方)と同じ作業なので、まとめて聞くのが効率的。

## Cloudflare 固有の落とし穴

Cloudflare は「守ってくれる」機能が既定で有効になっていることがあり、**それがそのまま本アプリの障害要因になる**。

### 1. 無通信 100 秒で切断される

Cloudflare は**約100秒データが流れない接続を切る**。プラン設定で変更できない。

→ **Go 側で 15〜30 秒ごとにハートビート(コメント行)を流すことが必須。**プロキシ設定に依存しない唯一の安全策なので、これは実装で担保する(API・データ設計policy の SSE 仕様に組み込み済み)。

### 2. Bot Fight Mode / WAF / Rate Limiting

**会場で約200台がほぼ同時に同じURLへ接続する**ので、Cloudflare 側から見ると攻撃と区別がつかない。

- チャレンジ(JS判定)が出ると、**`EventSource` はそれを通過できない**ため SSE が全滅する
- 組織の共有ドメインの場合、**既に Rate Limiting ルールが掛かっている可能性がある**
- **「I'm Under Attack」モードは絶対に有効にしない**

→ Q3 で `quiz.` サブドメインだけ除外できるか確認する。

### 3. キャッシュ

`/api/*` が Cloudflare にキャッシュされると、全端末が同じ古いJSONを見続ける。SSE 応答には次を付ける。

```
Cache-Control: no-cache
X-Accel-Buffering: no
```

加えて **Cloudflare 側の Cache Rule で `/api/*` を Bypass に**する(Q4)。

## SSE特有の落とし穴(本番だけ動かない事故の防止)

SSEは「接続を開きっぱなしで流し続ける」通信のため、普通のWeb向けデフォルト設定のリバースプロキシと相性問題が2つある:

1. **バッファリング**: プロキシが応答を溜めてから送る設定だと、イベントが即座に届かない(=全端末の画面が切り替わらない)。該当サブドメインの設定で無効化が必要(nginxなら `proxy_buffering off`)
2. **無通信タイムアウト**: 「60秒データが流れない接続は切断」が一般的なデフォルト。問題と問題の間で全員の接続が切れる。**対策はGo側のハートビート**(上記)

症状が「ローカルでは動くのに本番だけ画面が切り替わらない」になるため、知らないと当日デバッグ不能になる。**本番サブドメインでのSSE疎通確認を、リハーサルより前の早い段階で1回やる**こと。

> **これは #77(SSE配信)の完成を待たなくてよい。**中身が空でも、`text/event-stream` が Cloudflare を越えて流れ続けることさえ確認できれば、上記のリスクはほぼ消える。**最優先で通す。**

## 🔴 フロントに `localhost:3000` が焼き込まれる事故

**一番やらかしやすい。**`frontend/src/lib/config.ts`:

```ts
export const BASE: string = import.meta.env.VITE_API_URL
if (!BASE) { throw new Error('VITE_API_URL が設定されていません。...') }
```

**Vite の環境変数は「ビルドした瞬間の値」がJSに文字列として埋め込まれる。**実行時に読み直さない。本番ビルド時に `VITE_API_URL=http://localhost:3000` のままだと、**参加者のスマホが自分自身の3000番を叩きに行って全滅する。**

しかも `if (!BASE) throw` があるため、**空文字にして相対パス(`/api/...`)にする逃げ道が塞がれている。**

| 案 | 内容 | 評価 |
|---|---|---|
| **A-1** | `config.ts` を「未設定なら相対パス(`''`)」に直す | ✅ **推奨**。同一サブドメイン構成なので `/api/state` で正しく届き、**ビルド時に本番URLを知る必要がなくなる** |
| A-2 | ビルド時に `VITE_API_URL=https://quiz.○○○.jp` を必ず渡す | 手順を毎回守る必要があり、間違えても**ビルドは成功してしまう** |

**A-1 を採る。**「手順を守る」ではなく「間違えられない形にする」ほうが当日の安全性が高い。

> ✅ **2026-08-25 対応済み。**`frontend/src/lib/config.ts` を
> `export const BASE: string = import.meta.env.VITE_API_URL ?? ''` に変更し、`throw` を削除した。
> `api.ts` / `useEventState.ts` のパスは全て `/api/...` 始まりなので、相対パスでそのまま届く。
> `frontend/Dockerfile.prod` は **意図的に `VITE_API_URL` を渡さない**。

## 開発環境と本番環境の分け方

やることは3つ:

1. **設定値を全部 環境変数にする**(コードに書き込まない)
   - `.env.example` に一覧、開発は `docker-compose.yml` に直書き、本番はサーバー上の `.env.prod`
   - 例: `DATABASE_URL`, `ADMIN_TOKEN`, `IMPORT_TOKEN`, `SPREADSHEET_ID`, `GOOGLE_CREDENTIALS_JSON`
   - **`.env.prod` は git に入れない。**パーミッションは `600`
2. **composeファイルを分ける**
   - 開発: `docker-compose.yml`(bind mount + ホットリロード)
   - 本番: `docker-compose.prod.yml`(ビルド済みイメージ・mount無し・`restart: always`・上記のnginx構成)
   - 起動: `docker compose -f docker-compose.prod.yml up -d`
3. **本番だけの手順を `docs/ガイドライン/デプロイ手順.md` に書く**(デプロイ=作業手順書があること)

### トークンの扱い

- **本番の `ADMIN_TOKEN` / `IMPORT_TOKEN` はイベント直前に発行し、終了後に無効化する**(使い捨て)
- 開発用と本番用は**必ず違う値**にする
- SSE は仕様上トークンがURLに載るため、**ログ・履歴・スクショからの漏洩を前提**に設計する
- **管理者画面のパス `/backstage-0248` は秘密ではない**。トークンだけが秘密

## デプロイ方式

v1は**手動デプロイで十分**(CDは作らない)。

**2026-08-25 更新: SSH が通らないことが判明したため、入口を `pct enter` に変更した。**
また CT に mise を入れる必要が無いよう、`mise run deploy` ではなく**シェルスクリプト**にした。

```
PVEのGUI → ホストのShell → pct enter <VMID> → bash /opt/quizApp/infra/deploy.sh
```

`infra/deploy.sh` の中身:

1. `git pull --ff-only`
2. `docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build`
3. **マイグレーション**
4. 疎通確認(`/`、`/api/health`、SSE のハートビートまで)
5. 不要イメージの削除(→ ホストで `pct fstrim`)

自動化(GitHub Actionsからのデプロイ)は動いてから考えるv2。ただし**現状 SSH が通らないので、CD を作るにも先に Q6 の解決が要る**。

### デプロイ専用ブランチは作らない(2026-08-25 決定)

`production` のようなデプロイ用ブランチは**作らない**。`Git運用・CI_policy.md` で GitHub Flow
(main + 作業ブランチのみ、中間ブランチなし)を採用しているため、それに従う。

デプロイブランチの動機は普通2つあるが、どちらもこの構成では別の手段で満たせる:

| 動機 | ブランチを作らずどう満たすか |
|---|---|
| main が不安定な時に本番を守りたい | **当日は `git pull` しない(凍結する)**。ブランチを分けても凍結の判断は結局必要 |
| 何が動いているか特定したい | **タグを使う。**ブランチはポインタが動くので特定できない。タグは動かない |

そして**コストが実在する**: 初心者チームだと `main` へのマージと `production` へのマージの
二段階を必ず誰かが忘れ、症状が「**直したはずのバグが本番に残っている**」という
原因にたどり着きにくい形で出る。

**代わりに: 本番・リハーサルはタグを指定してデプロイする。**

```bash
git tag -a event-YYYY-MM-DD -m "本番"; git push origin event-YYYY-MM-DD
REF=event-YYYY-MM-DD bash infra/deploy.sh
```

CTスナップショットが「設定ごと戻す」手段なのに対し、タグは「コードだけ戻す」手段として
補完関係になる。デプロイ結果は CT の `/opt/DEPLOYED_REF` に記録される。

**再検討するのは CD を入れる時**(「このブランチに push されたら本番へ」というトリガーが
必要になるため)。ただしそれには先に Q6(SSH経路)の解決が要る。

> ⚠️ **マイグレーションの順序について。** policy では当初「アプリ起動**前**に流す」としていたが、
> compose で1つのCTに同居させる構成では、`migrate` コマンドが backend イメージの中にあるため
> **コンテナ起動 → マイグレーション → 利用開始** の順になる。守るべきは
> 「**利用者がアクセスする前にスキーマが揃っていること**」なので実質的な要件は満たしている。

## Proxmox だからこそ使える保険: スナップショット

**CT のスナップショットをイベント前に取っておくこと。**Proxmox を使う最大の利点。

- **リハーサル完了時点**で1つ
- **当日の朝、問題データ投入後**に1つ

「設定をいじって壊した」時に、**数十秒で丸ごと戻せる**。`pg_dump` と違い DB だけでなく設定ごと戻るため、当日の復旧手段としては最も確実。**`pg_dump` と併用する**(スナップショットは戻しすぎるので、データだけ戻したい時に `pg_dump` が要る)。
