## A. そのまま実装Issueにできるもの

### A-1. 本番環境で画像が配信されない

**背景**
調査済みで、原因は3つとも特定できている。

| 場所 | 現状 | 問題 |
| --- | --- | --- |
| `backend/Dockerfile.prod:34-36` | `server` / `migrate` / `migrations` しかコピーしていない | `backend/static/` がイメージに入らない |
| `docker-compose.prod.yml:77-78` | ボリュームは `db-data` のみ | 画像を永続化する場所が無い |
| `frontend/nginx.conf:24-40` | `location` は `/` `/index.html` `/assets/` `/api/` の4つ | `/images/` が無いので配信経路が存在しない |

`API仕様書.md` §6 は「問題・選択肢画像はサーバーの `GET /images/...` で配信する」と
決めているが、**本番構成がその契約を満たしていない**。

**なぜ気づきにくいか**
`backend/internal/question/import.go:169` の `imageExists` は、
画像が無くても `warnings` を返すだけで**取り込み自体は成功させる**(§6の仕様どおり)。
そのため本番では「投入は成功しているのに全画像が warning」という状態になり、
当日その場で原因を切り分けるのは難しい。

**やること**
- `Dockerfile.prod` に `static/` を含める、または compose 側でボリュームマウントする
  (どちらにするかは「画像を再デプロイなしに差し替えたいか」で決まる)
- `docker-compose.prod.yml` に画像用ボリュームを追加
- `nginx.conf` に `location /images/` を追加し、バックエンドへプロキシする
- **`client_max_body_size` が未設定 = 1MB上限**。画像投入(A-2)を見据えて併せて引き上げる

**参照**: `API仕様書.md` §6 / `backend/internal/question/import.go:183`

### A-2. 画像投入API

**背景**
今の入稿手段は「サーバーの静的フォルダへ手動配置」(§6)。実際には
サーバーへ直接置くか、GitHubにコミットして pull するしかなく、**当日の運用では回らない**。

**先にやること**

§6 の「入稿はサーバーの静的フォルダへの手動配置」という一文も書き換えになる。

**依存**: A-1(配信経路とサイズ上限)

### A-3. 画像投入UI(管理者画面)

**やること**
A-2 のAPIを叩く画面。問題投入(スプシ同期)と並ぶ位置に置く。

**着手前に分かっている作業**(#103 を書く過程で判明)

1. **`frontend/src/lib/api.ts` の `request` では multipart を送れない。**
   `body` があると `Content-Type: application/json` を固定し、必ず `JSON.stringify` する作りになっている。
   `FormData` を `JSON.stringify` すると `{}` になってしまう。multipart 用の経路を足す必要がある。
   なお **`FormData` を送るときは `Content-Type` を自分で設定してはいけない**。
   ブラウザが `boundary=----XXXX` 付きで自動生成する必要があり、手で書くと boundary が欠けてサーバーがパースできない。

2. **413(サイズ超過)は `code` で分岐できない。**
   nginx が `client_max_body_size` で弾くとレスポンスは nginx のHTMLページになり、
   このアプリのJSONエラー形式にならない。`api.ts` は `res.json().catch(() => null)` があるため
   クラッシュはしないが、`code` は `'UNKNOWN'` になる。**`ApiError.status === 413` で分岐する**こと。

3. **一覧API(`GET /api/admin/images`)が先に要る。**
   当日サーバーに触らない以上、UIから見えない画像は誰にも見えない。

**依存**: A-2(#103) / 画像一覧API / A-4(管理者画面の構造が決まってから)

**メモ**: #20 に含めず**独立したIssueにする**ことを推奨。
#20 は既に `hard` で、操作盤・認証UI・問題一覧・プレビューを1本に抱えている。

## B. 実装だが、先に決めることがあるもの

### B-1. 出題時のSE(効果音)

**現状**
`docs/実装要件/` に**音に関する記述が1つも無い**。完全な新規要件。

**決めること**

1. **どこで鳴らすか。**
   「出題ボタンを押したときに鳴らす」だと、鳴るのは**管理者のPC**。
   会場に流すなら、モニタ画面が `phase` の `question` への遷移を検知して鳴らす形になる。
   どちらを指しているかで実装場所が変わる。

2. **モニタ画面の起動時に1クリックを挟むことを許容するか。**
   ブラウザは**ユーザー操作なしに音を再生できない**(autoplay policy)。
   モニタ画面はSSEで自動的に切り替わるため、そのままでは無音になる。
   回避するには、画面を開いた裏方に1回クリックさせる(「開始」ボタン等)必要がある。
   これは運用手順にも影響する。

3. **会場音響と分担するか。**
   振り返りでは「全部の音響とくっつけなくてもよい」「『いぇーい』等はアプリに持ってこない」
   という方向が出ている。アプリが担当する音を先に列挙して確定させる。
