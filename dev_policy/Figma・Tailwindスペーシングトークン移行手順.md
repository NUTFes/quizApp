この文書は、これまでの会話を読んでいないエージェントが、Figma上でpx値だけが指定されている余白を調査し、Tailwind CSSの名前付きトークンへ移行するための引き継ぎ書である。

## 1. 目的

現在のFigmaでは、パディングやAuto Layoutの要素間隔が `8px`、`16px`、`24px` のような具体的な数値で指定されており、`xs`、`sm`、`md`、`lg`、`xl` などの共通名はまだ決まっていない。

次の順序で整理する。

1. Figmaで実際に使われている余白のpx値を読み取る。
2. 使用回数と用途を整理し、名前付きスペーシングトークンの対応案を作る。
3. quizAppのTailwind CSSへトークンを定義し、対象コードを名前付きクラスへ置き換える。
4. Figmaへ手動反映できる対応表をユーザーへ渡す。
5. 対応表を見たユーザーが、最後にFigma Variablesを設定する。

## 2. 最重要制約

### Figmaは読み取り専用

この作業でエージェントがFigmaを変更してはいけない。

- Figma Variablesを作成・変更しない。
- ノード、コンポーネント、Auto Layout、パディング、gapなどを変更しない。
- Figmaへの書き込みツールを呼ばない。
- 最終的なFigma側の反映は、ユーザー本人が対応表を見ながら行う。

読み取り時は `figma-design-to-code` の手順に従い、対象ノードに対して最初に `get_design_context` を使用する。取得内容は参考資料として扱い、生成されたコードをそのまま貼り付けない。

### px値を勝手に丸めない

たとえばFigmaに `15px`、`16px`、`17px` がある場合、すべてを自動的に `md = 16px` へ統合してはいけない。統合すると見た目が変わるため、次のどちらかにする。

1. 別トークンまたは任意値として正確な値を維持する。
2. 「16pxへ統合する候補」として対応表に記載し、ユーザーの承認後に変更する。

承認されていない正規化によって、既存のFigmaデザインと実装をずらさないこと。

## 3. 現在分かっているプロジェクト情報

- リポジトリ: `/home/naoto/quizApp`
- フロントエンド: React + TypeScript + Vite
- Tailwind CSS: `4.3.3`
- Tailwindの入口: `frontend/src/index.css`
- 現在の `index.css` は基本的に `@import 'tailwindcss';` のみで、`xs`、`sm`、`md`、`lg`、`xl` などの独自スペーシングトークンは未定義。
- リポジトリのコマンドは原則として `mise run <task>` を使用する。
- 作業方針・調査結果は、確定前なのでまず `dev_policy/` に置く。ユーザー承認前に確定版の `docs/` へ昇格させない。

2026-08-19時点のセッションではFigmaアプリが未接続だった。作業を再開するエージェントは、その時点の接続状態を改めて確認すること。

## 4. 作業開始に必要な入力

次の2点が揃うまで、Figmaの値を推測したりTailwindトークンを確定したりしない。

1. Figmaへの読み取り接続
2. 調査対象となるページまたは最上位フレームの、`node-id=...` を含むFigma URL

ファイルだけのURLでノードIDがない場合は、対象フレームを選択した状態のURLをユーザーへ依頼する。空のノードIDや推測したノードIDを使わない。

## 5. 今回の調査対象

最初の調査対象は「スペーシング」に限定する。

### 対象に含める

- Auto Layoutの上下左右パディング
- Auto LayoutのItem spacing / gap
- セクション間、カード間、要素間の余白
- Web実装で `padding`、`margin`、`gap` に対応する値

### 対象に含めない

- 固定のwidth / height
- アイコンや画像のサイズ
- font-size / line-height / letter-spacing
- border-radius
- border-width
- 色、影、透明度
- 絶対配置の座標

これらは別のトークン体系になるため、スペーシングと混ぜない。ユーザーが明示的に範囲を広げた場合のみ追加する。

## 6. 実施手順

### Phase 1: Figmaを読み取り、px値を洗い出す

対象フレームを `get_design_context` で読み取る。大きすぎてタイムアウトする場合は、画面やコンポーネント単位の小さいフレームへ分割して読み取る。

各スペーシングについて次を記録する。

- px値
- 種別: padding / gap / margin相当
- 方向: all / x / y / top / right / bottom / left
- 使用しているページ・フレーム・コンポーネント名
- 可能ならFigma node ID
- 使用回数
- 用途の傾向

調査結果は、作業用ファイルとして次へ記録する。

`dev_policy/Figma・Tailwindスペーシング対応表.md`

表の形式:

| 現在のpx値 | 使用数 | 種別・方向 | 主な使用箇所 | トークン案 | 扱い |
| ---: | ---: | --- | --- | --- | --- |
| 8px | 18 | gap / padding | ボタン内部、近い要素間 | `sm` | そのまま採用候補 |
| 15px | 2 | padding-x | 特定カード | 未定 | 16pxへの統合候補。未承認 |

Figmaに存在しない値を、一般的なデザインシステムという理由だけで追加しない。

### Phase 2: トークン対応案を決める

名前は原則として、値の小さい順に次を使用する。

`2xs < xs < sm < md < lg < xl < 2xl`

必要な段階だけを採用し、名前を増やしすぎない。`ss` や `ll` はTailwind標準ではなく意味が伝わりにくいため、新規設計では上記の一般的な名前を優先する。ただし、Figmaや既存ルールですでに別の命名が確定している場合は、その名前を維持する。

判断基準:

- 複数箇所で繰り返す値はトークン候補にする。
- 同じpx値がpaddingとgapの両方で使われても、スペーシングとして同じ意味なら同一トークンでよい。
- 一度しか使わない特殊値は、無理にトークンへ追加せず `p-[18px]` などの任意値として残す候補にする。
- 近い値の統合は「提案」と「確定」を分ける。
- トークン名ではなく、実際の使用分布を見て値を決める。

最終的な対応案には、少なくとも次を含める。

| Figma Variable案 | px値 | Tailwindテーマ変数 | 使用可能になるクラス例 |
| --- | ---: | --- | --- |
| `spacing/sm` | 8px | `--spacing-sm` | `p-sm`, `gap-sm`, `mt-sm` |
| `spacing/md` | 16px | `--spacing-md` | `p-md`, `gap-md`, `px-md` |

この表の値は例であり、実データを読む前に確定してはいけない。

### Phase 3: Tailwind CSSへ実装する

ユーザーが対応案を確認し、見た目を変える正規化が必要な場合は承認した後、`frontend/src/index.css` の `@theme` に定義する。

例:

```css
@import 'tailwindcss';

@theme {
  --spacing-xs: 4px;
  --spacing-sm: 8px;
  --spacing-md: 16px;
  --spacing-lg: 24px;
  --spacing-xl: 32px;
}
```

実際の値と段階数はFigma調査結果から決める。上記をそのまま採用しない。

対象コードに既存の任意値がある場合は、対応する名前付きクラスへ置き換える。

```tsx
// 変更前
<div className="flex gap-[8px] px-[16px] py-[8px]">

// 変更後の例
<div className="flex gap-sm px-md py-sm">
```

対象画面やコンポーネントがまだ実装されていない場合は、スペーシング整理だけを理由に画面全体を新規実装しない。`@theme` の定義と対応表まで作り、画面実装時に使える状態にする。既存コンポーネントがある場合は、その既存構造を再利用する。

Tailwindのテーマ変数はCSS変数であるだけでなく、対応するユーティリティクラスを生成する。クラス名は文字列結合で動的生成せず、`p-sm`、`gap-md` のような完全な文字列で書く。

### Phase 4: コードを検証する

最低限、次を確認する。

1. 対象範囲の全px値が対応表に載っている。
2. 対応表にあるトークンと `@theme` の定義が一致している。
3. コード内で使ったクラス名が定義済みである。
4. 未承認のpx正規化が入っていない。
5. Figmaが一切変更されていない。
6. CIと同じチェックが成功する。

基本コマンド:

```bash
mise run lint
```

必要に応じて、対象コード内に残る任意のスペーシング値も検索する。ただし、固定幅・文字サイズ・角丸など、今回の対象外のpx値まで機械的に置き換えない。

### Phase 5: ユーザーへFigma反映用の資料を渡す

ユーザーへ次を報告する。

- 採用したトークン名とpx値
- 各値の主な使用箇所
- 統合しなかった特殊値
- ユーザー判断待ちの正規化候補
- 変更したコードファイル
- 実行した検証と結果
- Figma Variablesへ登録するときの名前

Figma側では、ユーザーが対応表を見ながら `spacing/xs`、`spacing/sm` などのVariablesを作り、既存の数値指定へ手動で割り当てる。エージェントはこの反映操作を代行しない。

## 7. 完了条件

次のすべてを満たしたら完了とする。

- 対象Figmaフレームで使われるスペーシング値を洗い出した。
- px値ごとの使用数と代表的な使用箇所が分かる。
- Tailwindトークンとの対応表がある。
- `frontend/src/index.css` の定義と対応表が一致している。
- 既存実装がある範囲では名前付きクラスへ置き換えられている。
- 未承認の見た目変更がない。
- lint、format、typecheckが成功している。
- Figmaに変更を加えていない。
- ユーザーがFigmaへ手動反映できる情報が揃っている。

## 8. 中断してユーザーへ確認する条件

次の場合は推測で進めず、ユーザーへ確認する。

- Figmaへの読み取り接続がない。
- URLに `node-id` がない。
- 調査対象のページ・フレームが特定できない。
- 近いpx値を統合しないとトークン数が多くなりすぎる。
- 対応案によって既存デザインの寸法が変わる。
- 対象画面が未実装で、スペーシング整理を超えた画面実装が必要になる。
- 既存のデザイントークンや別の命名規則が見つかった。

## 9. 禁止事項

- Figmaを先に変更する。
- Figmaのpx値を見ずに一般的な値だけでトークンを決める。
- 近いpx値を説明なく丸める。
- Figmaから返されたコードをそのまま貼り付ける。
- 既存コンポーネントを確認せず、同等のコンポーネントを新規作成する。
- スペーシング作業に、色・文字・角丸・固定サイズの全面的なトークン化を混ぜる。
- ユーザーの依頼なしにコミット、push、PR作成を行う。
