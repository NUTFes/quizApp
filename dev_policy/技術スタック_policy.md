# 技術スタック policy

> 2026-07-20 更新: バックエンドを Go に決定(バックエンド人材のGoアウトプットの場を兼ねるため)。
> リアルタイム同期は SSE + REST(案B)を採用。問題データはGoogleスプレッドシート入稿→手動同期に決定。
> 同日、フロントエンドを Vite + React + TypeScript で確定(Next.js不採用の理由は下記)。

## 方針

- バックエンドは **Go**。技術的必然ではなく「Goを学びたい/アウトプットしたい人材がいる」ことが選定理由(教えたい人がいる技術が最強)。公式チュートリアル修了者がバックエンドリーダーを担う。
- フロントエンドは TypeScript。枯れていて日本語情報が多いものを選ぶ。
- リアルタイム同期は **SSE(Server-Sent Events)+ REST**。双方向WebSocketは早押し機能(v2)をやると決めたときに追加する。

## 決定スタック

| レイヤ | 採用 | 理由 |
|---|---|---|
| フロントエンド | **React + Vite + TypeScript** ✅確定 | React学習済みメンバーの知識がそのまま使える(Viteは開発サーバー+ビルド道具であり、書くコードは素のReact)。Next.js不採用の理由は下記 |
| ルーティング | React Router | SPAの標準 |
| スタイリング | Tailwind CSS | CSS設計の議論を省略できる。初心者がコピペで進めやすい |
| バックエンド | **Go + Gin** | Goの中で日本語教材・入門記事が最も多いフレームワーク。標準net/httpでも書ける規模だが、初心者の写経元の多さでGin |
| リアルタイム配信 | **SSE(サーバー→クライアント)** | ブラウザ標準EventSourceが自動再接続してくれるため自前実装が最小。回答送信は通常のPOST |
| DB | **PostgreSQL**(Dockerコンテナ) | 標準的。開発・本番(オンプレ)で同じものを使う |
| ORM | **GORM** | Goで情報量最多。メンバーは最初SQLをほぼ書かずに済む。マイグレーションは golang-migrate |
| 問題データ入稿 | **Googleスプレッドシート → 管理画面の同期ボタンでDBへ取り込み** | 非エンジニアの運営メンバーが問題を作れる。本番実行時はDBのみ参照(スプシ障害の影響を受けない) |
| ランタイム管理 | mise | Go・Node・pnpmのバージョン固定。`mise install` で全員同じ環境 |
| コンテナ | Docker Compose | frontend / backend / db の3コンテナ(→ フォルダ構成_policy) |

## リアルタイム同期の方式(このアプリの技術的な核)

このアプリの本質は「**管理者の操作で、モニタ(+作るならスマホミラー)の画面が一斉に切り替わる**」こと。
※2026-07-20のゲーム形式確定(勝ち残り×移動・回答機能なし)により、クライアント→サーバー方向の通信は管理者操作のみになった。SSE採用の妥当性はむしろ上がっている(配信は完全に一方向)。

| 方式 | 概要 | 評価 |
|---|---|---|
| ポーリング | 各端末が数秒ごとにAPIへ問い合わせ | 切り替えに数秒ラグ。残り時間と相性が悪い |
| **SSE(採用)** | サーバー→クライアントの一方向プッシュ。回答はPOSTで送る | 本設計は「サーバーが状態の唯一の正、クライアントは描画するだけ」の一方向フローなので、これで要件を満たせる。EventSourceの自動再接続で復帰処理も薄い |
| WebSocket | 双方向 | Goでは自前実装が増える(gorilla/websocket + 接続管理)。早押し(ミリ秒計測)をやるv2で追加検討 |

**設計の大原則(変わらず): サーバーが「現在のイベント状態」(何問目・出題中/正答表示中・残り秒数)を唯一の正として持ち、クライアントは受信して描画するだけにする。** リロード復帰(要件R6)も途中参加(R2)も「接続時に現在状態をもらう」だけで実現できる。

## Next.js を採用しなかった理由(記録)

フロント経験者の候補として挙がったが、以下の理由で不採用とした:

1. **Nextの強み(SSR/SEO/初回表示高速化)を使う場面がない。** QRコードから入る会場限定SPAでSEO無関係。リアルタイム同期(SSE受信での画面切り替え)は100%ブラウザ側の仕事
2. **本番の常駐サーバーが増える。** NextはNode.jsサーバーが本番でも動き続ける。Viteならビルド成果物はただの静的ファイルで、本番に常駐するのは「Go + 静的ファイル配信」のみ。オンプレ運用・障害対応が軽い
3. **学習の追加概念(App Router / Server Components 等)が必要。** Reactを学習済みのメンバーがそのまま書き始められるViteの方が、学習リソースをGo側に回せる

将来SEOが要るWebサイト案件が来たらNextを検討すればよい。本案件では出番なし。

## TypeScriptのスキル差への対応(決定)

チーム状況: まとめ役はTS自走可、フロントメンバーはReact学習済みだがTS経験は浅い可能性あり。

- **「型を書く人」と「型を使う人」を分担する。** 型定義(`frontend/src/types/api.ts`)とSSE/APIクライアント(`src/lib/`)はまとめ役が書く。TS力が必要な場所はほぼここに集約される
- メンバーが書くのは `features/` 内のコンポーネント。propsで受け取ったデータの表示が中心で、React学習済みの書き方がそのまま通じる。型は補完とエラー検出でメンバーを守る側に働く(api.mdを暗記しなくても正しいフィールド名でしか書けない)
- 最初は tsconfig を過度に厳しくせず、ESLintで型注釈を強制しない。「TS=JSに補完が付いたもの」という体感から始める

## Go採用に伴う注意点(TS統一案から失われるもの)

1. **フロントとの型共有ができない** → `docs/api.md` のAPI仕様書が唯一の契約になる。仕様書の精度・更新規律をTS案より一段丁寧にやる(→ API・データ設計_policy)。余裕が出たら tygo でGo構造体→TS型の自動生成を導入(バック班の良いタスク)
2. **フロント知識の流用が効かない** → バックエンドリーダー(Goチュートリアル修了者)の最初のタスクを小さな完動品(`GET /api/questions` のミニサーバー)にし、パターンを確立してから他メンバーに展開する。SSE基盤はまとめ役とペアで設計する
3. 学ぶ言語が2つになる → メンバーは最初にフロント班/バック班を決め、片方の言語に集中させる
