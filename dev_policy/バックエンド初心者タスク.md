# バックエンド 初心者タスク集

> `docs/API仕様書.md`(契約)と `docs/バックエンド実装要件.md` をもとに、初心者メンバーに渡せる粒度まで割ったタスク。
> そのままGitHub Issueにコピーして使う。順番は上から推奨。各タスクは1機能フォルダ内で完結する(コンフリクトしにくい)。

## 前提: この2つが揃ってから初心者タスクを配る(Phase 0・まとめ役+リーダー担当)

初心者タスクは「見本を写経して隣を作る」設計。そのため**見本と土台**を先に用意する必要がある。以下は設計判断を含むので初心者には渡さない(`hard`):

| # | 準備するもの | なぜ先に必要か |
|---|---|---|
| P1 | Question / EventState の GORMモデル + マイグレーション | すべてのタスクがこの型を読む。**choicesは空配列・correctChoiceIdはNULLを許容**して作る(→実装要件§1) |
| P2 | DB接続 + サンプル問題のseed(`cmd/seed`) | 読み取りタスクの動作確認に中身のあるデータが要る |
| P3 | 認証ミドルウェア(`Authorization: Bearer` 照合) | 管理者タスクが全部これに乗る |
| P4 | **見本エンドポイント `GET /api/admin/state` を1本完成させる** | これが全初心者タスクの**写経元**になる。ハンドラの書き方・JSON返却・エラーの形の実例 |
| P5 | ルータ登録とエラーレスポンス共通ヘルパ(`internal/platform`) | 各タスクは「関数を書いて1行登録するだけ」にする |

SSE基盤・phase遷移ロジック(show-question等の状態変更)・投入の全置換処理は`hard`。リーダー+まとめ役が担当する。

## タスク一覧(難易度順)

各Issueに必ず書く4点: **①ゴール ②触ってよいファイル ③写経元 ④動作確認方法**(タスク分割policyのテンプレ)。

### T1 `good first issue` — GET /api/admin/verify

- **①ゴール**: 認証トークンが正しければ `200 {"ok": true}`、無ければ `401 UNAUTHORIZED` を返すAPIを作る。トークンの照合は既存の認証ミドルウェア(P3)がやってくれるので、**通過してきたら `{"ok": true}` を返すだけ**。
- **②触ってよいファイル**: `internal/admin/` 内に1ファイル追加+ルータに1行登録。
- **③写経元**: P4の `GET /api/admin/state` のハンドラ(返すJSONを差し替えるだけ)。
- **④動作確認**: `curl -H "Authorization: Bearer 正しいトークン" localhost:3000/api/admin/verify` で `{"ok":true}`、トークンを変えると401。
- 最初の1本に最適。バックエンドの「関数を書く→登録する→curlで叩く」の1周を最小構成で体験する。

### T2 `good first issue` — GET /images/... 静的画像配信

- **①ゴール**: サーバーの画像フォルダに置いたファイルを `GET /images/ファイル名` で配信する(認証なし)。仕様書§6。
- **②触ってよいファイル**: ルータ設定に静的配信を1行足す(`internal/platform` のルータ登録部)。
- **③写経元**: Gin公式ドキュメントの `router.Static` の例。
- **④動作確認**: 画像を1枚置いて、ブラウザで `localhost:3000/images/test.png` が表示される。
- Ginの静的配信を1行で済ませる練習。コードはほぼ書かない。

### T3 `easy` — GET /api/admin/questions/:id(1問の詳細)

- **①ゴール**: URLのidに対応する問題を仕様書§1のフル形(correctChoiceId・explanation含む)で返す。**idが存在しなければ `404 QUESTION_NOT_FOUND`**。
- **②触ってよいファイル**: `internal/question/` 内。
- **③写経元**: P4の見本+GORMの `First` の使い方(実装要件やGORM入門)。
- **④動作確認**: seedしたidで叩くと問題が返る。存在しないid(例: 9999)で404とエラーの形 `{"error":{"code":...}}`。
- **学ぶこと**: URLパスパラメータの受け取り、GORMで1件取得、「無い場合」をエラーの形に変換する(Goの `if err != nil` の実戦)。ここが「読み取り+エラー処理」の基本形。

### T4 `easy` — GET /api/admin/questions(問題一覧)

- **①ゴール**: 全問題を仕様書§4.1の一覧形で返す。各問題は `textPreview`(textSegmentsを結合した全文)と `hasImage`・`asked` を持つ。0件なら `{"questions": []}`。
- **②触ってよいファイル**: `internal/question/` 内(T3と同じフォルダなので、T3の人が続けてやってもよい)。
- **③写経元**: T3+GORMの `Find`(全件取得)。
- **④動作確認**: seedした件数だけ返る。`textPreview` がセグメント結合済みになっている。
- **学ぶこと**: 全件取得と、DBの形→APIレスポンスの形への**詰め替え**(専用の構造体を作る)。「DBの型とAPIの型は別物」を体で理解する good な題材。

### T5 `easy`(ペアレビュー推奨)— GET /api/state?view=monitor|phone(閲覧者向け出し分け)

- **①ゴール**: 見本のフルstate(P4)から、閲覧者に**送ってはいけないものを抜いた**stateを返す。抜くもの=正答情報・difficulty・totalSegments・未公開セグメント、および **question phase では `explanation`**(仕様書§2.2)。`view=phone` は `joinUrl` も抜く。
- **②触ってよいファイル**: `internal/event/` 内(見本stateの整形部分の隣)。
- **③写経元**: P4の `GET /api/admin/state`。**これをコピーして「削る」のがこのタスク**。
- **④動作確認**: `?view=monitor` と `?view=phone` を叩き、レスポンスに `correctChoiceId` の**キー自体が無い**ことを確認(nullではなく、存在しない)。
- **学ぶこと**: このアプリの心臓「ずるができない仕組み」。**クライアントで隠すのではなくサーバーで抜く**の実装。設計の肝なのでレビューを厚めに。

### T6 `easy`(テスト付き)— 問題投入バリデーション関数

- **①ゴール**: 「問題1件のデータを受け取り、問題なければOK・ダメなら理由を返す」**純粋関数**を作る。HTTPもDBも触らない。チェック内容は実装要件§2の表(type別のchoices数・correctChoiceIdの存在・arunashi書式 `ラベル:項目/項目`・hayaoshiはv1エラー・number重複 等)。
- **②触ってよいファイル**: `internal/sheetsync/` 内のバリデーション1ファイル+そのテストファイル。
- **③写経元**: なし(ここは自分でロジックを書く)。ただし**Tour of Goのテーブル駆動テスト**の形をそのまま使う。
- **④動作確認**: **テストを書いて通す**(正常な問題・各エラーパターンを1件ずつ)。これがこのタスクの成果物の半分。
- **学ぶこと**: 入力→出力が明確な関数の設計とテスト。**HTTP/DBを知らなくても書ける**ので、環境構築で出遅れた人にも渡せる保険タスク。ここが後で投入APIの検品部に組み込まれる。

> **T7(残り人数の手入力更新)は廃止しました**(2026-08-13)。
> `remainingPlayers` と `POST /api/admin/remaining-players` を仕様から削除したため(→ API仕様書 変更履歴 第5版)。
>
> **⚠️ これにより「安全な書き込み系タスク」が1本も無くなりました。** 残る書き込みAPIは phase 遷移(`show-question` / `advance-text` / `show-answer` / `reset`)と問題投入だけで、いずれも `hard` です。
> 初心者に書き込みを経験させたい場合は、**`advance-text`(`revealedSegments += 1`)を `easy` として切り出す**のが候補になります。処理は加算1行で、エラーも「phaseが違えば409」「全部表示済みなら何もせず200」の2つだけなので、遷移APIの中では最も単純です。

## 依存関係と配り方

```
P1〜P5(まとめ役+リーダー)完成
        │
        ├─ T1 verify ─────┐  ← まず全員これで1周体験
        ├─ T2 images       │
        │                  ▼
        ├─ T3 詳細 ──> T4 一覧    (問題フォルダ担当)
        ├─ T5 出し分け            (eventフォルダ・ペアレビュー)
        └─ T6 検品関数            (独立・環境なしでも着手可)
```

- **最初の配り方**: 各人にまず T1 を渡して「1周」させる(登録→curl確認の型を体に入れる)。そのあと T3/T4、T5、T6 を希望や進度で振り分け。
- T3→T4 は同じ `internal/question/` なので同一人物が続けると効率がよい。
- T6 は独立していて環境構築を待たないので、**手が空いた人・環境で詰まっている人の待避先**に使える。
- **タスクは6本になった**(T1〜T6)。`easy` 以下を10個以上そろえる目安(→ タスク分割・進め方_policy)には足りないので、フロント側のタスクで補うか、`advance-text` の切り出しを検討する。
- ここに無い show-question / advance-text / show-answer / reset / 投入の全置換 / SSE は `hard`。T1〜T6で全員が「ハンドラの型」を掴んだ頃に、リーダーとペアで着手する2周目タスクになる。

## Issue化のときの注意

- 各タスクの「③写経元」は、P4の見本が完成してからでないと書けない。**Phase 0が終わるまでIssueの本文③は空欄で起票し、見本完成後に追記**でよい。
- 難易度ラベル(`good first issue` / `easy` / `hard`)を必ず付ける(タスク分割policy)。
- 1タスクが `docs/API仕様書.md` のどの節に対応するかをIssueに明記する(実装中に仕様を見に行く癖をつける)。
