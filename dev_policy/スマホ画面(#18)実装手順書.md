## 0. まず、これだけ理解してほしいこと

このアプリは、**サーバーが「今どの画面を出すか」を全端末に配っている**。参加者のスマホは**それを映すだけ**。

```
裏方が管理画面で「この問題を出す」を押す
        ↓
サーバーが state（今の状況）を全端末に配る
        ↓
スマホ画面が state を見て、表示を切り替える   ← あなたが作るのはここ
```

だから**あなたが作る画面にボタンは1つも無い。** ページ遷移も無い。`state` を受け取って、その中身に応じた見た目を返すだけ。

そして **`state` を受け取る仕組みは、もう他の人が作り終えている。** あなたは `useViewerState()` と呼ぶだけでよい。

> 心配しなくていいこと: SSE、リロード対応、途中参加、再接続。全部 `useViewerState()` の中で処理済み。

## 2. 何を作るのか

`state.phase` が4つの値を取る。**それぞれに対応する画面を作る。**

| phase | 出すもの |
| --- | --- |
| `waiting` | 「まもなく始まります」 |
| `question` | 第N問 / 問題文 / 選択肢 / 残り時間 / 会場マップ |
| `answer` | 第N問 / 問題文（全部） / 選択肢（正答をハイライト） / 解説（**ある問題だけ**） |
| `finished` | アンケート誘導 |

## 4. フォルダ構成（これで作る）

**迷わなくていいように決めてある。この通りに作る。**

```
frontend/src/features/phone/
├── PhonePage.tsx          … phase を見て4つのどれかを出すだけ。薄く保つ
├── WaitingView.tsx        … 「まもなく始まります」
├── QuestionView.tsx       … 出題中
├── AnswerView.tsx         … 正答発表中
├── FinishedView.tsx       … アンケート誘導
└── parts/                 … 上の View から使う部品
    ├── QuestionNumber.tsx … 「第3問」
    ├── QuestionText.tsx   … 問題文
    ├── ChoiceList.tsx     … 選択肢の並び（2×2 / 左右 を切り替える）
    ├── ChoiceCard.tsx     … 選択肢1つ
    ├── RemainingTime.tsx  … 残り秒数 / 「締切!」
    └── VenueMap.tsx       … 会場マップ
```

### なぜこう分けるのか

**① `PhonePage` を薄くする理由**

phase の分岐と、各画面の中身を同じファイルに書くと、すぐに 300 行を超えて読めなくなる。`PhonePage` は「交通整理だけ」にする。

**② `question` と `answer` を分ける理由**

似ているが、出すものが違う（タイマー vs 解説、ハイライトの有無）。1つにまとめて `if` を大量に書くより、分けて**共通部分を `parts/` から呼ぶ**方が読みやすい。

**③ `parts/` を作る理由**

`QuestionText` と `ChoiceList` は `question` と `answer` の**両方で使う**。片方だけ直して食い違うのを防ぐ。

**④ もう1つ、技術的な理由がある（重要）**

React のフックは**条件分岐の中で呼べない**。`useRemainingTime` は `question` のときだけ必要だが、こう書くとルール違反でエラーになる。

```tsx
// 🚫 これはできない
if (state.phase === 'question') {
  const remaining = useRemainingTime(...)   // ← フックを if の中で呼んでいる
}
```

`QuestionView` という**別のコンポーネントに分けると、その先頭で普通に呼べる**。

```tsx
// ✅ QuestionView.tsx の中なら OK
function QuestionView({ state }: Props) {
  const remaining = useRemainingTime({ ... })   // 先頭で無条件に呼んでいる
  ...
}
```

**コンポーネントを分けるのは、見た目の整理だけでなくフックのためでもある。**

## 5. すでにあるもの（使い方）

### 5-1. `useViewerState()` — state を受け取る

```tsx
import { useViewerState } from '../../lib/useEventState'

const state = useViewerState()   // ViewerState | null
```

**最初は `null` が返る**（まだサーバーから届いていない）。必ず先に処理する。

```tsx
if (state === null) return <p>読み込み中…</p>
```

### 5-2. `ViewerState` の中身

```ts
type ViewerState = {
  phase: 'waiting' | 'question' | 'answer' | 'finished'
  serverTime: string                 // タイマー計算用
  timeLimitSec: number | null        // タイマー計算用
  questionStartedAt: string | null   // タイマー計算用
  askedCount: number                 // 「第N問」の N
  question: {
    number: number
    type: 'four_choice' | 'two_choice' | 'arunashi' | 'hayaoshi'
    textSegments: string[]           // 問題文。連結して表示する
    imageUrl: string | null
    choices: { id: string; text: string; imageUrl: string | null }[]
  } | null
  answer: {
    correctChoiceId: string | null
    explanation: string | null
  } | null
}
```

**`question` も `answer` も `null` になりうる。** `state.question.type` と書くと落ちる。必ず `null` を先に処理する。

### 5-3. `useRemainingTime()` — 残り秒数

```tsx
import { useRemainingTime } from '../../lib/useRemainingTime'

const remaining = useRemainingTime({
  serverTime: state.serverTime,
  timeLimitSec: state.timeLimitSec,
  questionStartedAt: state.questionStartedAt,
})
// remaining は number（秒）。0 より下にはならない
```

### 5-4. モックデータ

`lib/mock/phone/` に用意されている。§1-3 の自動再生で使われる。

## 7. 実装の順番

**⚠️ いきなり Figma 通りに作らない。まず「動く汚い画面」を作り、あとから見た目を寄せる。**

見た目とロジックを同時に作ると、崩れたときにどちらが原因か分からなくなる。

### Step 1: phase の分岐だけ作る（見た目ゼロ）

まず4つの View を、**文字1行だけ**で作る。

```tsx
// WaitingView.tsx
export function WaitingView() {
  return <div>waiting</div>
}
```

同様に `QuestionView` `AnswerView` `FinishedView` も作る。そして:

```tsx
// PhonePage.tsx
import { useViewerState } from '../../lib/useEventState'
import { WaitingView } from './WaitingView'
import { QuestionView } from './QuestionView'
import { AnswerView } from './AnswerView'
import { FinishedView } from './FinishedView'

function PhonePage() {
  const state = useViewerState()

  if (state === null) return <p>読み込み中…</p>

  switch (state.phase) {
    case 'waiting':
      return <WaitingView />
    case 'question':
      return <QuestionView state={state} />
    case 'answer':
      return <AnswerView state={state} />
    case 'finished':
      return <FinishedView />
  }
}

export default PhonePage
```

**✅ 動作確認:** 14秒間で `waiting → question → answer → question → answer → finished` と文字が変わる。

**ここが一番大事なステップ。** これが動けば、あとは各 View の中身を埋めるだけになる。

### Step 2: `QuestionText` を作る

問題文は `textSegments` という**配列**で来る。連結して表示する。

```tsx
// parts/QuestionText.tsx
type Props = { segments: string[] }

export function QuestionText({ segments }: Props) {
  return <p>{segments.join('')}</p>
}
```

> なぜ配列なのか: 早押し問題で「少しずつ表示する」ため。スマホでは常に全部つなげて出す。

**✅ 動作確認:** `question` のとき問題文が出る。

### Step 3: `ChoiceCard` と `ChoiceList` を作る

まず1つ分。

```tsx
// parts/ChoiceCard.tsx
import type { Choice } from '../../../types'

type Props = { choice: Choice; isCorrect?: boolean }

export function ChoiceCard({ choice, isCorrect = false }: Props) {
  return (
    <div className={isCorrect ? '（正答のスタイル）' : '（通常のスタイル）'}>
      {choice.text}
    </div>
  )
}
```

次に並べ方。**type によって配置が変わる。ここがこの画面の肝。**

| type | 配置 | 理由 |
| --- | --- | --- |
| `four_choice` | **2×2** | **会場の4エリアと同じ位置関係。**参加者はこれを見て移動する |
| `two_choice` | **左右** | ○×も同じ（text が「○」「×」なだけ） |
| `arunashi` | **左右** | |
| `hayaoshi` | 選択肢なし | フェーズ2。§8 参照 |

```tsx
// parts/ChoiceList.tsx
export function ChoiceList({ question, correctChoiceId }: Props) {
  const layout =
    question.type === 'four_choice'
      ? 'grid grid-cols-2'   // 2×2
      : 'grid grid-cols-2'   // 左右（2つしか無いので同じ書き方で並ぶ）

  return (
    <div className={layout}>
      {question.choices.map((c) => (
        <ChoiceCard key={c.id} choice={c} isCorrect={c.id === correctChoiceId} />
      ))}
    </div>
  )
}
```

**✅ 動作確認:** 4択で2×2、あるなしで左右に並ぶ。

> 自動再生には `four_choice` と `arunashi` しか入っていない。`two_choice` を見たいときは、`lib/useEventState.ts` の `VIEWER_STEP` を**一時的に**書き換えて確認する。**確認したら必ず戻すこと**（`lib/` は触ってはいけないファイル）。

### Step 4: `RemainingTime` を作る

```tsx
// QuestionView.tsx
const remaining = useRemainingTime({
  serverTime: state.serverTime,
  timeLimitSec: state.timeLimitSec,
  questionStartedAt: state.questionStartedAt,
})

const isClosed = remaining <= 0
```

**⚠️ 残り0秒になったら「締切!」に切り替える。** 問題文と選択肢は**出したまま**、タイマー部分だけを差し替える。

```tsx
// parts/RemainingTime.tsx
export function RemainingTime({ remaining, isClosed }: Props) {
  if (isClosed) return <p>締切!</p>
  return <p>{remaining}</p>
}
```

この状態で司会が煽り、裏方が正答表示を押すまで待つ、という進行になっている。

**✅ 動作確認:** モックは `questionStartedAt` が過去なので、すぐ「締切!」になるはず。数字が減るのを見たいときは、モックの `questionStartedAt` を現在時刻に近い値へ**一時的に**書き換える。

### Step 5: `QuestionNumber` と `VenueMap` を作る

```tsx
// parts/QuestionNumber.tsx
export function QuestionNumber({ count }: { count: number }) {
  return <p>第{count}問</p>
}
```

**🚫 絶対にやってはいけないこと: 自分で数を数える。**

```tsx
// 🚫 これは禁止
const [count, setCount] = useState(0)
useEffect(() => { setCount((c) => c + 1) }, [state.question])
```

途中から QR で参加した人の端末は、**別の数字を表示してしまう**。`state.askedCount` をそのまま出すこと。

**会場マップ**（どのエリアがどの選択肢か）は Figma を見て作る。state に依存しない**静的な表示**。**画面上部など「触らない場所」**に置く。

**✅ 動作確認:** 「第3問」と出る（モックの `askedCount` が 3）。

### Step 6: `AnswerView` を作る

`question` とほぼ同じだが、違いが3つ。

| | question | answer |
| --- | --- | --- |
| 問題文 | 表示 | **全部表示**（早押しでも全文） |
| 選択肢 | 通常 | **正答をハイライト** |
| タイマー | 表示 | **出さない** |
| 解説 | — | **ある問題だけ**表示 |

```tsx
// AnswerView.tsx
const explanation = state.answer?.explanation

return (
  <div>
    <QuestionNumber count={state.askedCount} />
    <QuestionText segments={state.question?.textSegments ?? []} />
    <ChoiceList question={state.question} correctChoiceId={state.answer?.correctChoiceId ?? null} />
    {explanation && <p>{explanation}</p>}
  </div>
)
```

**⚠️ 解説は「ほとんどの問題で無い」。** `{explanation && ...}` で囲み、**無いときにレイアウトが不自然にならないか**を必ず確認する。自動再生の 5秒（解説あり）と 11秒（解説なし）を見比べること。

**✅ 動作確認:** 5秒地点で正答がハイライトされ解説が出る。11秒地点で解説が出ず、レイアウトが崩れていない。

### Step 7: `WaitingView` と `FinishedView`

```tsx
// WaitingView.tsx
export function WaitingView() {
  return <p>まもなく始まります</p>

```

```tsx
// FinishedView.tsx
import { SURVEY_URL } from '../../lib/config'

export function FinishedView() {
  return (
    <div>
      <p>ご参加ありがとうございました</p>

```

**⚠️ `waiting` と `finished` では「第N問」を出さない。** この2つでは `askedCount` が必ず `0` になるため、「第0問」と表示されてしまう。

**✅ 動作確認:** 0.3秒地点と14秒地点。

## 8. 仕様の落とし穴（作る前に読む）

### 🚫 操作要素をゼロにする

**ボタン・入力・リンクを1つも置かない**（`finished` のアンケートリンクだけは例外）。

参加者は「見るだけ」。押せるものがあると、押した人が「何か起きるはず」と誤解する。

### ⚠️ 知らない `type` が来ても白画面にしない

`type` は将来増える可能性がある。`switch` で全部書いて `default` を忘れると、**画面が真っ白**になる。当日それが起きると復旧できない。

```tsx
// 必ず用意する
default:
  return <p>この問題はモニターをご覧ください</p>
```

### ⚠️ `hayaoshi`（早押し）の扱い

早押しは**フェーズ2で v1 では出ない**が、形だけ来る可能性がある。

早押しでは **`textSegments` が空配列で届く**（手元で先に読めると早押しが成立しないため、サーバーが送らない）。このとき問題文の代わりに**「モニターをご覧ください」**を出す。

### 🚫 `dangerouslySetInnerHTML` は使用禁止

問題文や解説を `dangerouslySetInnerHTML` で出さないこと。**このリポジトリでは全面禁止。**

### ⚠️ 正答は「隠す」のではなく「届かない」

`question` の間、`state.answer` は `null` で届く。正答をサーバーが送っていない。

つまり **`display: none` で隠す実装をしてはいけない**（そもそも隠すデータが無い）。`state.answer` が `null` のときは何も描かない、が正しい。

### ⚠️ 画像のパス

`imageUrl` は `/images/q5.png` のような**サーバー上のパス**で届く。そのまま `<img src="/images/q5.png">` と書くとフロントの開発サーバーを見に行って 404 になる。

`lib/config.ts` の `BASE` を前に付ける必要がある。

```tsx
import { BASE } from '../../lib/config'
<img src={`${BASE}${choice.imageUrl}`} alt="" />
```

> 実際に画像が出るかはバックエンドができてからでないと確認できない。**壊れてもレイアウトが崩れないこと**だけ確認しておく。

### ⚠️ `alt` を空にする理由

問題の画像に `alt="選択肢Aの画像"` のような説明を入れると、**画像を見せない意図が壊れる**場合がある。装飾的な画像は `alt=""` でよい。迷ったら Issue で相談。

- [ ] 3つの type（four_choice / two_choice / arunashi）で配置が変わる
- [ ] 未知の type を入れても白画面にならない
- [ ] 解説なしの問題でレイアウトが不自然にならない
- [ ] `waiting` / `finished` で「第N問」が出ていない
- [ ] 操作要素が1つも無い（アンケートリンクを除く）
- [ ] `lib/` `types/` `App.tsx` を変更していない（config.ts の `SURVEY_URL` を除く）
- [ ] `mise run lint` が通る
- [ ] **before / after のスクショを PR に貼る**

## 10. PR の出し方

```bash
git add frontend/src/features/phone/
git commit -m "スマホ画面の実装"
git push -u origin feat/18-phone-screen
```

GitHub で PR を作る。本文に書くこと:

- 何を作ったか
- **スクリーンショット**（4つの phase 分）
- 迷った・判断した点（レビュアーが一番見たい部分）
- 未確認のこと（画像表示など、バックエンド待ちのもの）

**🚫 自分でマージしない。** 必ずレビューを受ける。

## 11. 詰まったら

**30分考えて分からなかったら聞くこと。** 1人で3時間溶かすより、聞いて10分で解決する方がプロジェクトにとって良い。

聞くときに書くこと:

1. 何をしようとしたか
2. 何が起きたか（エラーメッセージはそのまま貼る）
3. 何を試したか

### よくあるつまずき

| 症状 | 原因 |
| --- | --- |
| 画面が真っ白 | `state.question.type` のように `null` チェックを飛ばしている。ブラウザのコンソールを見る |
| state が `null` のまま | `VITE_USE_MOCK=true` が効いていない。`mise run down && VITE_USE_MOCK=true mise run up` |
| `Rendered fewer hooks than expected` | フックを `if` の中で呼んでいる（→ §4 の④） |
| 余白のクラスが効かない | `p-md` のような**存在しないクラス名**を書いている。Tailwind はエラーを出さず無視する。数字で書く（`p-4`） |
| 型エラーが出る | `types/` を直したくなるが**触らない**。Issue にコメントする |
