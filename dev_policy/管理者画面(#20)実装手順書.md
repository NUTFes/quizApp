# 管理者画面(#20) 実装手順書

Issue #20 の担当者向け。

**前提: #18 #19 が終わっていること。** ただしこの画面は**性質がまったく違う**。前2つが「見るだけ」なのに対し、これは**操作する画面**。

まず [`スマホ画面(#18)実装手順書.md`](./スマホ画面\(#18\)実装手順書.md) の §1（環境）と §3（触ってよいファイル）を読むこと。

## 0. この画面の位置づけ

**当日、裏方が1人でこれだけを操作して進行を回す。**

使うのは情報局員なので、**自分たちが使いやすいように設計してよい。** ただし勘違いしないこと。

> **「身内用だから雑でいい」は禁止。**
> 当日焦っている状態で使うものなので、むしろ**使いやすさ優先。**

想像してほしい状況。200人が待っている。司会が「では次の問題!」と言った。あなたが作ったこの画面で、**3秒以内に正しいボタンを押さなければならない。**

その状況で押し間違えないか。それがこの画面の評価基準。

### 一番怖い事故

**誤操作で正答が漏れること。** これが起きるとクイズが成立しなくなり、リカバリーできない。

だから「正答を表示」ボタンだけは**確認ポップアップを1回挟む**（§6）。

## 4. 認証（最初に作る）

### 4-1. 仕組み

パスワードでログインする仕組みは**無い**。**トークンを貼り付けて保存するだけ。**

```
裏方がトークンを入力
   ↓
localStorage に保存
   ↓
以降、API を叩くときに自動で Authorization ヘッダに載る
```

保存先は `localStorage` の `adminToken` キー。**読み出す関数はもうある。**

```ts
// lib/config.ts
export const getAdminToken = () => localStorage.getItem('adminToken') ?? ''
```

### ⚠️ 書き込む関数が無い

`lib/config.ts` に**保存側の関数が無い**。このイシューで足してよい（**PMに一言入れてから**）。

```ts
// lib/config.ts に足す
export const setAdminToken = (token: string) => localStorage.setItem('adminToken', token)
export const clearAdminToken = () => localStorage.removeItem('adminToken')
```

> `lib/` は本来「触ってはいけないファイル」。ここは例外として扱う。

### 4-2. 画面の流れ

```tsx
// AdminPage.tsx のイメージ
const [authed, setAuthed] = useState<boolean | null>(null)

useEffect(() => {
  if (!getAdminToken()) { setAuthed(false); return }
  verify()
    .then(() => setAuthed(true))
    .catch(() => setAuthed(false))
}, [])

if (authed === null) return <p>確認中…</p>
if (!authed) return <LoginView onSuccess={() => setAuthed(true)} />
return <DashboardView />
```

`verify()` は成功なら `{ ok: true }`、トークンが違えば `401 UNAUTHORIZED` を投げる。

### 4-3. 🔒 セキュリティ（必ず守る）

- **🚫 トークンを `console.log` しない。** デバッグしたければ `token.length` を出す
- **🚫 トークンを PR・Issue・スクショに写さない。** スクショを撮るときは入力欄を空にするか隠す
- **🚫 トークンを画面に表示したまま放置しない。** 入力欄は `type="password"` にする
- **もし漏らしたら、隠さず即 PM に報告する。** 本番トークンは当日直前に発行して使い捨てにする運用なので、早く言えば差し替えるだけで済む

## 5. モックで開発する

バックエンドがまだ無いので、`VITE_USE_MOCK=true` で開発する（#18 §1-3 と同じ）。

```tsx
import { useAdminState } from '../../lib/useEventState'
const state = useAdminState()   // AdminState | null
```

`AdminState` はスマホ・モニタと少し違う。

```ts
type AdminState = {
  phase: 'waiting' | 'question' | 'answer' | 'finished'
  serverTime: string
  timeLimitSec: number | null
  questionStartedAt: string | null
  revealedSegments: number     // 今どこまで表示したか
  totalSegments: number        // 全部で何区切りあるか
  askedCount: number
  question: Question | null    // ← 正答・解説・難易度が入っている
}
```

**`question` には `correctChoiceId` が入っている。** 管理者だけが正答を受け取れる（サーバーが出し分けている）。

### ⚠️ 用意されていないモックが2つある

| 無いもの | 影響 |
| --- | --- |
| `getQuestions()` の問題一覧 | 問題一覧が作れない |
| 各APIの成功/失敗レスポンス | エラー処理が試せない |

**自分で仮のデータを作って開発してよい。** ただし:

- **`features/admin/` の中に置く**（`lib/mock/` は #14 の担当領域）
- ファイル名で仮だと分かるようにする（例: `parts/__devFixtures.ts`）
- **🚫 本番の問題データと正答は絶対に置かない。** このリポジトリは公開されている。架空の問題だけを使う
- PR に「これは開発用の仮データ」と明記する

## 6. 「正答を表示」の確認ポップアップ

**このイシューで一番重要な要件。**

```tsx
// ControlPanel.tsx のイメージ
const [confirming, setConfirming] = useState(false)

<button onClick={() => setConfirming(true)}>正答を表示</button>

{confirming && (
  <ConfirmDialog
    message="正答をモニタに表示します。よろしいですか?"
    onConfirm={() => { setConfirming(false); showAnswer().catch(...) }}
    onCancel={() => setConfirming(false)}
  />
)}
```

### 守ること

- **確認は「正答を表示」だけ。** 他のボタンには付けない。全部に確認が出ると、裏方が読まずに押すようになり、確認の意味が消える
- **キャンセルが押しやすい位置にあること。** 焦って連打したときに「はい」に当たらないように
- `window.confirm()` でも要件は満たせるが、**Figma にダイアログのデザインがあるならそれに従う**

### なぜここだけ特別なのか

他のボタンは押し間違えてもリカバリーできる。

| 操作 | 押し間違えたら |
| --- | --- |
| 出題 | 別の問題を出し直せばよい |
| 次を表示 | 1区切り進むだけ |
| リセット | 出し直せばよい |
| **正答を表示** | **もう戻せない。** 200人が正答を見てしまった |

## 7. エラー処理

### 7-1. `error.code` で分岐する

**`message` を画面に出してはいけない。** `message` は開発者向けで、内容が変わりうる。

**ユーザーに見せる日本語はフロントが持つ。**

```ts
// errorMessages.ts
export const ERROR_MESSAGES: Record<string, string> = {
  UNAUTHORIZED: 'トークンが正しくありません。入力し直してください。',
  QUESTION_NOT_FOUND: 'その問題は見つかりませんでした。一覧を更新してください。',
  INVALID_REQUEST: '入力内容が正しくありません。',
  INVALID_PHASE: 'いまの進行状況ではこの操作はできません。',
  SYNC_VALIDATION_ERROR: '問題データに不備があります。下の一覧を確認してください。',
}

export const toMessage = (code: string) =>
  ERROR_MESSAGES[code] ?? '処理に失敗しました。もう一度お試しください。'
```

**`??` のフォールバックを必ず用意する。** 知らない code が来ても画面が壊れないように。

### 7-2. 使い方

```tsx
import { ApiError } from '../../lib/api'

showAnswer().catch((e) => {
  if (e instanceof ApiError) {
    setError(toMessage(e.code))
  } else {
    setError('通信に失敗しました。ネットワークを確認してください。')
  }
})
```

### 7-3. ⚠️ 当日に効く表示

- **エラーは消えないようにする。** トーストで3秒後に消えると、裏方が見逃す
- **どのボタンが失敗したか分かるようにする。** 画面の隅に赤文字が出るだけだと、何が起きたか分からない
- **押している間はボタンを無効化する。** 二度押しで二重に送るのを防ぐ

## 8. 貼り付け投入UI

### 8-1. これは何か

問題データをスプレッドシートから取り込む機能。本来は GAS がサーバーへ直接送るが、**それが使えない事態の保険**として、人間がコピペで投入する経路も作る。

```
GAS がJSONを画面に出す → 裏方がコピー → この画面のテキストエリアに貼る → 送信
```

### 8-2. 作るもの

```tsx
// ImportPanel.tsx のイメージ
const [text, setText] = useState('')

const submit = () => {
  let parsed
  try {
    parsed = JSON.parse(text)
  } catch {
    setError('JSONとして読み取れませんでした。コピーし直してください。')
    return
  }
  putQuestions(parsed.questions ?? parsed)
    .then(setResult)
    .catch(handleError)
}
```

### 8-3. ⚠️ `details` を必ず表示する（最重要）

投入に失敗したとき、サーバーは**どの行が悪いかを全部まとめて**返してくる。

```ts
export class ApiError extends Error {
  readonly code: string
  readonly status: number
  readonly details: { sourceRow: number; reason: string }[]
}
```

**この `details` を画面に出さないと、この機能は使い物にならない。**

```tsx
{error && <p>{error}</p>}
{apiError?.details.map((d) => (
  <li key={d.sourceRow}>{d.sourceRow}行目: {d.reason}</li>
))}
```

`sourceRow` は**スプレッドシートの行番号**。裏方はこれを見てシートの該当行を直す。

> `details` が出ないと「2件の問題が不正です」しか分からず、**どこを直せばいいか分からないまま当てずっぽうで再送**することになる。当日の直前にこれが起きると詰む。

### 8-4. 成功時も表示する

```ts
type ImportResult = {
  imported: number        // 何件入ったか
  importedAt: string      // いつ入れたか
  warnings: { sourceRow: number; reason: string }[]   // エラーではないが注意
}
```

**`warnings` も `details` と同じ形。** 同じ表示部品が使える（`ImportResultView.tsx`）。

**最終投入日時と件数を画面に残す。** 当日「ちゃんと入ってるっけ?」を確認するため。

### 8-5. ⚠️ 全置換であることを伝える

投入は**全置換**（それまでの問題は全部消える）。エラーがあれば**1件も入らない**。

裏方が誤解しないよう、画面に明記する。

> 「送信すると、現在の問題データはすべて置き換わります」

## 10. 落とし穴

### ⚠️ 秒数の入力欄

- **空でよい**（空なら 30秒がサーバー側で適用される）
- 範囲は **5〜120秒**。範囲外を送ると `INVALID_REQUEST` で弾かれる
- **空欄を `0` として送らないこと。** 空なら `showQuestion(id)` と、第2引数を省略して呼ぶ

```tsx
// 空文字なら undefined を渡す
const sec = input === '' ? undefined : Number(input)
showQuestion(id, sec)
```

### ⚠️ 「次へ」方式にしない

問題は**一覧から選んで出す**。「次の問題へ」ボタンにしない。

ボタンを2回押しても、同じ問題を2回出すだけで事故にならない。**連打耐性のための設計。**

### ⚠️ 難易度は日本語で表示する

データは `easy` / `normal` / `hard` で来る。**画面には「簡単」「普通」「難しい」と出す。**

当日焦っている裏方が読むものなので、英語のまま出さない。

### ⚠️ 出題済みの問題が分かるようにする

`QuestionListItem.asked` が `true` なら出題済み。**一覧で潰して見せる**（グレーアウトなど）。

同じ問題を2回出す事故を防ぐため。

### ⚠️ リセットの `to`

`reset('waiting')` と `reset('finished')` の2つがある。**どちらに戻すかを選ばせる。**

`finished` は「クイズ終了」に飛ばす操作。誤って押すと進行が終わるので、**`waiting` を既定にする。**

### 🚫 `dangerouslySetInnerHTML` 禁止

#18 #19 と同じ。**この画面は特に危険。** localStorage にトークンが入っているので、XSS が起きるとトークンを盗まれる。
