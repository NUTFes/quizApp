## 0. 進め方の方針

### バックエンドを待たない(モックファースト)

`フロントエンド実装要件.md` §8 のとおり、**バックエンド完成を待たずに作る**。
仕様書のJSON実例をそのままモックデータにして、固定の state を流す。

> **⚠️ モックは「仕様書に書かれたJSONと1文字も違わない形」で作ること。**
> ずれるとバック結合時に全部やり直しになる。

### 難しい順に並んでいない

STEP4(SSE)が一番難しいが、**STEP1〜3を先にやることで、STEP4を書くときに必要な材料が揃う**ようにしてある。飛ばさず順にやる。

### 詰まったときの原則

- **30分詰まったら止める。** 調べ方は [`React・TypeScript入門.md`](../docs/入門/React・TypeScript入門.md) §11
- 動かないまま先に進まない。**各STEPの「動作確認」を必ず通してから次へ**

## STEP 1. 型定義 — 仕様書を型に翻訳する

**ここが全ての土台。** 型が正しければ、以降はエディタが間違いを教えてくれる。

### やること

`src/types/` に、`API仕様書.md` §1 のデータモデルをそのまま型として書く。

- `Question`(問題)
- `State`(現在の状態。アプリの中心)
- `Choice`、`Phase` など必要な補助型

### ⚠️ 守ること

`フロントエンド実装要件.md` §1 より:

- **キーは常に存在し、値が `null` / `[]` になる。** だから `?`(Optional)ではなく **`| null`** で書く
- `type` は**ユニオン型**で書く(`'four_choice' | 'two_choice' | 'arunashi'`)
- **`hayaoshi` も型には入れておく**(フェーズ2で実装するが、型に無いと後で全部直すことになる)

```ts
// ✅ 正しい
type State = {
  phase: Phase
  question: Question | null
  questionStartedAt: string | null
  revealedSegments: number
  totalSegments: number
}

// ❌ 間違い(「キーが無いかもしれない」の意味になる)
type State = { question?: Question }
```

### 動作確認

- [ ] `API仕様書.md` §1 の全フィールドが型に入っている
- [ ] `pnpm typecheck` が通る
- [ ] 仕様書のJSON実例を、その型の変数に代入してみて型エラーが出ない

## STEP 2. モックデータ + APIクライアント層

### やること

1. **モックデータ**(`src/lib/mock/`)
   `API仕様書.md` のJSON実例を、そのまま TypeScript のオブジェクトにする。

2. **APIクライアント**(`src/lib/api.ts`)
   `fetch` をまとめる薄い層。`import.meta.env.VITE_API_URL` を使う。
   管理者APIには `Authorization: Bearer` を付ける(トークンは `localStorage` から)。

   > **API・HTTPが初めてなら、先に [`../docs/入門/API・fetch入門.md`](../docs/入門/API・fetch入門.md) を読む。**
   > 10本のAPIが「何をするので、どう書くか」を1本ずつ説明してある。
   > 書く順番は同ドキュメント §7(**骨組みを先に作り、`request` の中身は最後**)。

### モックに用意する組み合わせ

**4フェーズ × 問題形式**を最低限そろえる。これが後の全画面の動作確認に使われる。

| モック | 用途 |
|---|---|
| `waiting` | 開始前(`question` が `null`、キーは残る) |
| `question` × `four_choice` | 2×2配置 |
| `question` × `two_choice` | 左右配置 |
| `question` × `arunashi` | 左右配置 |
| `answer`(解説あり / なし) | 正答表示と解説の出し分け |
| `finished` | アンケート誘導 |

### ⚠️ 守ること

- **仕様書のJSONと1文字も違わない形**にする(`フロントエンド実装要件.md` §8)
- モックデータにも **STEP1 の型を付ける**。型が付いていれば、仕様とのズレをエディタが検出する

### 動作確認

- [ ] 各モックが STEP1 の型に適合する(`pnpm typecheck` が通る)
- [ ] `waiting` のモックで `question` が `null` になっている

## STEP 3. ルーティングと3画面の骨組み

### やること

`src/App.tsx` で React Router を設定し、3つのページの**空の箱**を作る。

| パス | 画面 | ファイル |
|---|---|---|
| `/` | スマホ(参加者ミラー) | `src/features/phone/` |
| `/monitor` | モニタ(85インチ) | `src/features/monitor/` |
| `/admin` | 管理者(裏方) | `src/features/admin/` |

> **⚠️ 管理者のパスは推測されにくいものにする**(`フロントエンド実装要件.md` §7)。`/admin` そのままにしない。

中身は「モニタ画面です」程度の文字でよい。**ここでは配線だけ通す。**

### ⚠️ 本番配信では「どのURLでも index.html を返す」設定が要る

React Router は**ブラウザの中だけ**で URL を解釈する。サーバーには `index.html` が1枚あるだけで、`/monitor` というファイルは存在しない。

そのため、ブラウザが `/monitor` を**直接リクエスト**すると(URL直打ち・ブックマーク・リロード)、配信サーバーは「そんなファイルは無い」と **404 を返し、画面が真っ白になる**。

- **開発中は気づけない。** Vite の開発サーバーはこの転送を最初からやってくれるので、`pnpm dev` では絶対に再現しない
- 発症するのは本番配信に載せた後。**当日モニタ用PCで `/monitor` をブックマークから開いて真っ白**、が最悪のシナリオ

対策は配信側の設定で、**存在しないパスへのリクエストを全部 `index.html` に転送する**(SPAフォールバック)。呼び方はサービスごとに違う。

| 配信方法 | 設定 |
|---|---|
| Nginx | `try_files $uri /index.html;` |
| Vercel / Netlify | 全パスを `/index.html` に rewrite |
| `vite preview` | 標準で対応済み |

> **STEP 3 の時点では設定不要**(まだ本番配信が無い)。ただし**デプロイ作業をするときに必ず思い出すこと。** 検証は `pnpm build && pnpm preview` で `/monitor` を直接開けばよい。

### 動作確認

- [ ] 3つのURLを開いて、それぞれ違う文字が出る
- [ ] **`pnpm build && pnpm preview` して、`/monitor` を直接開いても真っ白にならない**
- [ ] `pnpm build` が通る

## STEP 4. SSE接続の共通実装 ★一番難しい

**ここがフロントの心臓。** 各画面はこれを1行呼ぶだけで state を受け取れるようにする。

### 作るもの

`src/lib/useEventState.ts` — カスタムフック。

```tsx
// 使う側はこうなる、という完成イメージ
const state = useEventState('monitor')
```

### 必要な知識

[`React・TypeScript入門.md`](../docs/入門/React・TypeScript入門.md) の §3(useEffect)・§4(カスタムフック)・§5(EventSource)。**書く前に3節とも読む。**

### ⚠️ 契約上の必須実装

`フロントエンド実装要件.md` §2 より:

- 接続URL: モニタ `?view=monitor` / スマホ `?view=phone` / 管理者は `?token=` 付き
- **再接続に成功したら、必ず `GET /api/state` を1回叩いて再描画してから受信を再開する**
  (切断中の取りこぼし対策。**これはフロント側の必須実装**)
- `ping` イベントは無視してよい
- **`useEffect` の後片付けで `es.close()` を必ず呼ぶ**(呼ばないと接続が増え続ける)

### モックでの進め方

バックのSSEはまだ無い。**まずモックを流すダミー実装で画面側を完成させ**、後から本物のEventSourceに差し替える。
差し替え口をこのフックに閉じ込めておけば、**変更はこのファイル1つで済む**。

### 動作確認

- [ ] モックのstateがフックから返る
- [ ] 画面を離れると後片付けが動く(コンソールログなどで確認)
- [ ] 接続が二重に張られていない(開発者ツールのNetworkタブで確認)

## STEP 5. タイマー計算

### やること

`src/lib/useRemainingTime.ts` — 残り秒数を返すカスタムフック。

`フロントエンド実装要件.md` §3 の式をそのまま実装する。

```
時計ずれ = 手元の現在時刻 - 受信したserverTime   ← state受信のたびに更新
残り秒数 = timeLimitSec - (手元の現在時刻 - 時計ずれ - questionStartedAt)
```

### ⚠️ 守ること

- **0になっても何も起こさない。** 0のまま表示する。遷移はすべて裏方の操作
- `setInterval` の後片付け(`clearInterval`)を忘れない

### 動作確認

- [ ] 端末の時計を数分ずらしても、表示される残り秒数が変わらない(`serverTime` 補正が効いている)
- [ ] 0で止まり、マイナスにならない

> **ここは純粋な計算なので、テストが最も安く効く場所。** 1本書いておくとよい。

## STEP 6. スマホ画面(一番単純)

**ここで「stateを見て表示を切り替える」書き方を掴む。** 以降の2画面は同じことの繰り返しになる。

### 仕様(`画面・要件.md` §6 / `フロントエンド実装要件.md` §7)

- **操作要素ゼロ。** ボタン・入力を一切置かない。すべて自動で切り替わる
- リロード・途中参加は STEP4 の共通実装が面倒を見る(画面側に特別な処理は不要)

### 作る内容

phase ごとの表示を分ける。

| phase | 表示 |
|---|---|
| `waiting` | 「まもなく始まります」 |
| `question` | 問題文 + 選択肢 + タイマー |
| `answer` | 正答 + 解説(ある問題だけ) |
| `finished` | アンケート誘導(`VITE_SURVEY_URL`) |

### type別の表示ルール(`フロントエンド実装要件.md` §6)

| type | 配置 |
|---|---|
| `four_choice` | **2×2**(会場の4エリアと同じ位置関係) |
| `two_choice` | **左右**(○×も同じ) |
| `arunashi` | **左右** |
| 未知のtype | **フォールバック表示**(白画面にしない) |

問題文は `textSegments` を先頭から連結して表示(全typeで同じ処理)。

### 動作確認

- [ ] 4つのモック(waiting / question / answer / finished)で正しく切り替わる
- [ ] 3つのtypeで配置が変わる
- [ ] 未知のtypeを入れても白画面にならない

## STEP 7. モニタ画面(主役)

会場の85インチ大画面。**このアプリの主役。**

### 仕様(`画面・要件.md` §6 / `フロントエンド実装要件.md` §7)

- 右上に参加用QR(`joinUrl` から生成)を**常時固定表示**(途中参加者向け)
- `answer` フェーズ: 正答ハイライト + 正解演出動画(企画側制作の静的アセット)
- `waiting`: 「まもなく始まります」+ QR大きめ
- `finished`: アンケート誘導
- 問題文の**順次表示**(`revealedSegments` / `totalSegments`)

### ⚠️ 85インチという特殊要件

**会場の後ろの席から読めるか**が唯一の合格基準。文字サイズは実機で確認するまで分からない。
Tailwind の `text-6xl` `text-8xl` あたりを試しながら調整する。**通しリハーサルで必ず実機確認する。**

### 動作確認

- [ ] `four_choice` が2×2で、会場のエリア配置と同じ位置関係になっている
- [ ] `revealedSegments` を変えると表示される問題文が増える
- [ ] QRが常時出ている

## STEP 8. 管理者画面(操作盤)

裏方1人が当日操作する画面。**事故を防ぐことが最優先。**

### 仕様(`フロントエンド実装要件.md` §4・§7)

**認証UI**
- 起動時に `GET /api/admin/verify` → 401ならトークン入力画面
- トークンは `localStorage` に保存し、全リクエストの `Authorization: Bearer` に付ける
- **リロードしても再入力不要にする(当日の事故防止)**
- どのAPIでも401が返ったらトークン入力画面に戻す

**操作**
- 問題リストから**選んで出題**(「次へ」方式にしない)
- 出題時の**秒数入力欄**(任意・空なら30秒)
- **「正答を表示」だけは確認ポップアップを1回挟む**(誤操作で正答が漏れるのが最悪の事故)
- 「次を表示」/「リセット」/ 残り人数入力
- 貼り付け投入UI(GASが使えない事態の保険)
- 現在モニタに映っている内容のプレビュー

**エラー表示**
- `error.code` で分岐し、**日本語文言はフロントが持つ**(`message` は表示に使わない)

### 動作確認

- [ ] トークン未入力で入力画面が出る
- [ ] リロードしても再入力を求められない
- [ ] 「正答を表示」で確認ポップアップが出る
